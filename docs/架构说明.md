## 关键设计决定

### 1. 拼缝存的是"位移"，不是"删掉的像素"

`Seam` 的核心字段是 `IntPoint Offset` = **后一段原点相对前一段原点的整数位移**。

- 竖排紧接：`Offset = (0, 前段高)`
- 纵向重叠 200 行：`Offset = (0, 前段高 - 200)`

于是"去掉后一张与前一张重复的内容"不需要真的删任何像素——位移本身就把重叠表达清楚了，
画布上自然只留一份。**少一处"删像素"就少一处可能删错**。

`AutoOffset` 与 `ManualOffset` 分开存，所以"恢复自动""取消本次调整""每次有效移动使 ✓ 失效"
这些要求都能实现；如果只存一个值，自动建议被覆盖后就再也找不回来了。

### 2. 片段（Segment）与源图（SourceImage）分两层

切分会把一张图分成两段独立移动/删除，状态栏替换又会让多个片段引用同一张源图。
把"是哪张图"与"取它哪一块"分开，切分/删除就不需要动源图记录，符合"原图不被覆盖"。

### 3. 撤销栈存的是"项目文件的字节"

`Project.Mutate()` 在改动前把 `ProjectFile.Serialize(Doc)` 的字符串压栈。
好处是**只有一份序列化实现**：不会出现"撤销正常、存盘丢参数"这种两套代码才有的分裂 bug。
快照只有几 KB（纯参数、无像素），所以 80 步历史几乎不占内存。

### 4. Core 不碰磁盘也不碰屏幕

Core 只定义 `ISourceResolver` 与 `IImageEncoder` 两个接口，实现由 App 注入。
于是 Checks 可以塞一个 `MemoryResolver` 就把"导入 → 布局 → 匹配 → 清理 → 导出"
整条链路在内存里跑完，不需要文件、不需要窗口。

这也是**零 NuGet 依赖**能成立的前提：Core 是 net8.0，不引用 System.Drawing。

### 5. 清理的幂等性靠"检测画面"与"显示画面"分开

`CleanupPlanner` 检测时调 `CanvasComposer.RenderForDetection`，它**只应用用户裁边**，
忽略上一轮清理写入的补丁。

不这么做会形成反馈环：上一轮的结果被算进下一轮的检测输入 → 每点一次"应用预览"就多改一层。
这一条对滚动条仍然成立。第十四轮末次起还有一层历史要记：当时"裁剪固定带"会写进
`Segment.AutoCrop`（与用户的 `EdgeCrop` 分开存，正是为了绝对赋值、重跑不叠加），
并由 cleanup 组那格「裁剪方式重复运行不叠加」守住——**该字段、该处理方式与那格判据都已随功能下线**，
见 README「第四十改」。

### 6. 拖动预览不写参数

`StitchCanvasControl` 拖动期间调 `CanvasLayout.Build(doc, overrides)` 生成一份临时布局，
参数一个字都不改；松手才 `Project.Mutate` 提交一条历史。

于是：一次拖动 = 一条可撤销记录（需求 §5.2），取消拖动 = 丢掉临时布局，不需要回滚任何东西。

第七轮之后这里多了一条约束：临时布局里塞进去的位移同样要过模式的轴规则
（`CanvasLayout.Build` 在累加坐标前 `StitchAxes.Enforce` 一次），
所以"拖动预览"和"最终像素"不可能一个错开、一个不错开。

### 7. 长截图只允许纵向位移，且这条规则只有一个出处

长截图是**同一页面纵向滚动**得到的连拍，物理上不存在左右位移。
一旦允许横向挪 N 像素，重叠带里那一份内容就会左右错开 N 列：
后一段盖住 `x∈[N, W+N)`，前一段在 `x∈[0, N)` 又露出来，同一段内容在成品里出现两次，
画布还凭空变宽 N——缩略图上看不出来，导出后才藏不住。

所以 `Model/StitchAxes` 是全项目唯一回答"哪根轴能动"的地方，五个下游各自引用它而不是各自判断：

| 落点 | 用它的哪一面 | 为什么放这儿 |
| --- | --- | --- |
| `CanvasLayout.Build` | `Enforce(mode, offset)` | **最后一道闸**：旧项目文件、别处写进来的参数、忘了走模式参数的分析都拦得住，像素只认这里 |
| `Seam.ApplyManual(offset, mode)` | `Enforce` + 返回 `ManualApply(Applied, RejectedHorizontalShift)` | 写入前就归零，不给"绕过界面把 X 塞进参数"留口子；被丢掉的量如实报出来 |
| `CanvasLayout.TightOffset` / `EffectiveOffset` | 轴 + 紧接量 | 界面显示的 X/Y、日志、判据共用同一个"生效值"，不再三处各算一遍 `before.Rect.Height` |
| `MatchOptions.For(mode)` | `LockHorizontal` | 模式是唯一依据，传进来的锁位会被覆写（防"多处同值漂移"） |
| `StitchCanvasControl.ConstrainDrag` | `Enforce(档位)` + `Enforce(点)` | 方向键与鼠标拖动都走这一个折算；公开它是为了让电池直接量这条通路 |

**匹配量出 `dx≠0` 时不假装没看见**：`Refine` 在同一次距离扫描里同时给出
"dx=0 这一列的最优"（采纳，用来定重叠与 offsetY）与"不限横向的最优 dx"（只作证据）。
结果里 `Offset.X = 0`、`DetectedHorizontalShift` 保留原值，状态降级 `! 需检查`，
原因是新增的 `SeamCause.HorizontalShiftLocked`，文字直说"请人工确认截图宽度或拼缝"。
悄悄归零会留下一个左右错开半列的成品，而用户只会觉得"哪里怪怪的"却查不出原因。

**参数原值与生效值是两个概念**：`Seam.ResolveOffset(tight)` 给参数里存的原值，
`Seam.EffectiveOffset(tight, mode)` / `CanvasLayout.EffectiveOffset(seam)` 给真正生效的值。
所以"从竖拼切到长截图"只让 X 不生效、不改写用户存的 7，切回去它还在。

**重叠到底去没去掉，用整数对账**：`CanvasLayout.DescribeSeam` 返回 `SeamGeometry`
（`Overlap` 是从画布落位**量**出来的，`ReportedOverlap` 是分析声称的，两者必须相等；
`FormulaHolds` 检查 `offsetY = 前段长 − 重叠`；`PairExtent` 检查 `总高 = H1 + H2 − 重叠`），
`MeasureDedup()` 给出全链总账 `Σ各段长 − Σ重叠 = 画布主轴长`。
右侧拼缝面板把"去重账"这一行直接显示给用户，日志每版参数记一次 `layout.seam`。
"把第二张整张画到 offsetY 下面"这种假去重会在 `OverlapMatchesReport`、`FormulaHolds`、
总账、以及"重叠那一行在成品里出现几次"四处同时露出来。

### 8. 鼠标手势只由"点着什么"决定（第八轮）

画布上并排住着两类意图：**看**（平移、缩放）与**改**（调这条拼缝）。
之前用"是否选中了某条拼缝"当分流条件，于是用户点过一次拼缝之后，
按在画布任何位置都在拖那条缝，整个画布推不动——这是"改"抢走了"看"的入口。

现在的分层是：

```
OnMouseDown ─┬─ Shift+左键 / 中键 ────────────→ PanCanvas   （只动视口）
             ├─ 点选切分 / 框选进行中 ─────────→ SplitClick / BandPick
             ├─ HitTestSeamEditRegion 命中 ─────→ PendingSeamClick →（越过阈值）MoveSeam
             └─ 其它一切 ─────────────────────→ PanCanvas
```

三条实现要点：

1. **`SelectedSeamId` 不参与判定**。它是"状态栏与右侧面板该显示哪条缝"的状态，
   与"这次按下点在哪"无关；把它当开关就是那个缺陷的根源。
2. **命中区不止那条线**：`HitTestSeamEditRegion` 返回 `(SeamId, SeamHitKind, Before|After)`，
   `SeamHitKind` 第十二轮起是三档 `CutLine` / `AlignmentAdjust` / `OverlapBand`
   （第八轮那两档 `SeamLine|OverlapBand` 已被取代，因为"带里拖"分成了"换内容来源"与"改对齐"两件事）。
   蓝线容差 9 设备像素、带边箭头把手 10 设备像素、带内整块可点（用户圈出的"红框"就是那块），
   带外一律回落平移。线优先于带——压在线上语义最明确，不该因为它的带也盖着这里就报成带命中。
   `Side`（抓的上方还是下方那张）只进提示与日志，**不擅自改写"固定侧"下拉框**。
3. **override 只做转发**，实体是 public 的 `MousePress` / `MouseMoveTo` / `MouseRelease` / `ApplyWheel`，
   电池量的就是产品同一条链，不在工装里复述优先级。

一处必须写下来的几何冲突（需求一.5 与一.6 不可同时成立）——**第九轮之后这条只适用于位移档**：
`CanvasLayout` 永远把最左上角归到 (0,0)——导出必须紧贴内容、不许留空白；
于是**视口不动时，画布顶端那一段必然钉在屏幕上**（`device = (origin − TopLeft) × zoom`，
顶端 origin 恒为 0）。所以"固定后一段时拖动，前一段位置改变"这件事，
在视口冻结的实现里物理上不可见——能看到的只有后一段在反向动。
两条需求里选其一的话就等于偷偷作废另一条，所以这里的取舍是：

- 默认档（固定前一段）严格守一.5：视口一字不动，判据把 `TopLeft` 与 `Zoom` 都钉住；
- 固定后一段则给视口做**纯显示补偿**：`TopLeft = 起点 + (生效位移 − 起点位移)`，
  绝对赋值（不累积取整漂移），于是后一段在屏幕上原地不动、前一段跟手；
  补偿不写参数、不动 `Revision`、不进撤销栈，拖回原位时补偿量自动归零。
- 两侧都被判据当成正反对照量（`canvas/固定前一段：后一段在动，前一段与视口都不动` 与
  `canvas/固定后一段：前一段跟手，后一段在屏幕上原地不动`），
  所以哪天有人把补偿"顺手去掉"或把默认档"顺手加上补偿"，都会当场红。

**长截图（裁切档）没有这个冲突**：拖**蓝线**是**高度守恒**的——前一段多留几行、后一段就少留几行，
总重叠与画布总高一字不动，后面所有段的原点也不动。于是"拖蓝线不许动视口"与
"要看见哪一份被换掉"在裁切档里同时成立。
第十二轮给裁切档补了第二条手势（拖红箭头/带里 = 改对齐），它**会**改画布高，
所以 `FixedSide` 在裁切档里重新有了含义——它决定这次手势写的是"哪一侧的行号"
（固定前一段 ⇒ 带首不动、带尾挪；固定后一段 ⇒ 带尾不动、带首挪）。
但"屏幕上看起来是哪张图在动"仍受下面这个事实约束，第八轮的补偿只保留在竖拼/横拼：
布局永远把最左上角归到 (0,0)，所以累计链前面的段会一起被重新归一（详见"诚实缺口"第 6 条）。

日志侧对应两条自查：`canvas.pan.*` 里 `revision_changed` 必须 False；
拼缝编辑两档（`seam.slide.*` / `seam.edit.*`）里，**只有"抓上方那张"那一趟**允许 `viewport` 不等于
`viewportBefore`（那是本轮的纯显示补偿），抓下方那一张与位移档都必须相等。

### 第十轮补：一个事实只留一处出口（编译跑通后补的三条规则）

第一次真编译 + 全量电池（139 格）暴露的不是零散 bug，而是"同一个事实有两处真相"这一族。三条落定：

1. **长截图里 Y 与裁切账谁说了算，写在 `CanvasLayout.Build` 的同一处**：
   `OverlapLength > 0` 时 Y 只是裁切算出来的**结果**（`EffectiveOffset` 从落位反量），
   只有 `OverlapLength == 0 且两侧裁切量都是 0` 时才由 Y **反推**去重量。
   为什么必须带这个限定：不加的话，有人绕开 setter 把 b/t 裸写成 0（O 仍记 60），
   Y 反推会把这 60 行"补"回来 —— 用另一个参数把坏参数洗白，
   这个形状正是 `guard/自动档蓝线被写到带外时修补回到自动结论那一格` 当场红出来的。
2. **反序列化是按 JSON 顺序逐个走 setter，落库的是中间态**：所以"自动档"的裁切量不是可信来源，
   `NormalizeAlignment()`（第十二轮起；原名 `NormalizeCrops()`）对自动档只认 `AutoCutY` 这一个意图字段，
   手动档才保住用户的蓝线。**这条规则第十二轮又红了一次**：兼容用的那对别名都往 `CutY` 写，
   于是 `b=10` 与 `t=10` 谁后到谁说了算——修法不是排顺序，是**删掉一个写入口**（见下面第十二轮那节）。
3. **清理与裁切互相报账**：固定带选"裁掉"后重叠本身变短，`CleanupPlanner` 在同一条可撤销记录里
   把 O 改成 `O − 顶带 − 底带`；因为固定带检测器故意读未含 AutoCrop 的画面，
   这一步必须**绝对赋值**（`Seam.CleanupBandRemoved` 记着上一轮扣了多少），否则重跑一次清理就再扣一次。
   真机 17 张连拍的实测代价：不改则成品从 27838 行被算成 18702 行（吃掉 9136 行真内容）。

日志字段的写法也收在一处：`SeamEditTrace.Fields()` 与 `SeamGeometry.ToString()` 里所有布尔走 `Low()`
输出小写 `true/false`。C# 的 `bool.ToString()` 给 `True/False`，而判据与人 grep 都按小写比 ——
大小写混在一行里时，`height_changed=false` 这种"正反对照"永远读不到，只会红成一格"日志没证明"。
裁切档的手势日志第十二轮起分成两族（`seam.cut.*` 只改切点、高度守恒；`seam.alignment.*` 只改对齐、
高度会变），`height_changed` 当时正是它们的区分标志 ——
**【这一句到第四十一改作废：两档并成一条滑动手势，`seam.slide.*` 里 `height_changed` 本来就该是 True，
因为"把那张图挪 d 行"物理上就是要重算带高。取而代之的区分标志是新增的 `line_device_moved`
（两趟都必须 False）与 `grabbed`（After／Before 分开）。】**
两趟各自的 `cut_changed` / `alignment_changed` 仍然相反：抓下方那张两个都 True（O 与 Cut 对消），
抓上方那张只有 `alignment_changed` 为 True（带内行号根本不动），判据见
`align/滑动两趟的日志各自齐备且互不覆盖`。

### 第十一轮补：一帧预览该做多少事（画布卡顿的四个根因）

用户报"整个画布非常卡、拖动和滚轮不流畅"。量下来不是"某处慢"，而是**四件事都在按鼠标事件计数做**：

| 高频路径 | 原来每帧做 | 现在 |
| --- | --- | --- |
| `MouseMoveTo` | 同步重摆布局 + 重画 + 记日志 | 只更新累计位移，`BeginInvoke` 排队，一帧最多一遍 |
| `UpdatePreviewCut` | `_renderRevision++` ⇒ 瓦片缓存**整块**清空 | `TileCache.DropRegion(带区)`，带外继续复用 |
| `MainForm.Dragging` | `UpdateSeamList()`（清空重建 16 行 + 状态栏文字） | 不挂——预览期间参数根本没变，提交时 `_project.Changed` 已经在刷 |
| `DiagnosticLog` | 每行 `File.AppendAllText`（一次开、一次关） | 一个开着的 `StreamWriter` + 缓冲；`*.preview` 不单独刷盘 |

三条要记住的规则：

1. **失效粒度不许粗于变化粒度**。切点移动是高度守恒的：带在画布上的位置
   `= 前段起点 + 前段基准高 − 前段顶裁 − O + 间隙`，与切点无关；带外任意一行的取数来源
   也与切点无关（后一段整体挪多少，它的顶裁就少多少，两笔账互相抵掉）。
   所以"只丢带区那几块瓦片"是**可证明**的，而 `crop/切点预览只改带内瓦片：带外逐字节相同`
   把带外逐块比了字节、并要求带内必须不同（异本标记），这条推理才不是靠注释成立。
   - **守恒只属于切点那一个手势，别当成两个手势共同的性质**（第十八改量出来的）。拖红箭头改的是
     重叠：多 1 行重叠 ⇒ 画布矮 1 行 ⇒ **带顶往下每一行**的源行号都挪 1 行，所以那里的"带外"压根不存在。
     8 段链实测 Δ1／Δ3／Δ8／Δ40 四档一致：带以上同 1、跨带变 2、带以下变 5，且带以下每块顶行的
     源行号正好挪 delta 行 ⇒ 产品的作废形状（min(带顶A,带顶B) → 画布底）丢 7 块正好是该变的 7 块。
     判据 `align/拖对齐时带以下每一块瓦片的内容确实变了：作废范围已是最小`，反证
     `guard/拖对齐若只丢带区那几块则屏上会留上一帧的像素`。
     这一条同时关掉了一整族设想："把缓存键换成内容身份（段号＋源矩形）就能让拖动途中少重算几块"——
     **键跟着内容每帧一起变，命中 0 块**；真留得住的只有带以上，而那几块本来就已经留住。
2. **合并的是"什么时候做"，不是"做什么"**。控件没有窗口句柄时（电池的工装）`BeginInvoke` 会抛，
   所以 `QueuePreviewFrame` 就地执行**同一个** `RunPreviewFrame`——判据量的与屏幕上跑的
   是同一套折算，不存在"测的是一套、上线是另一套"。累计位移在移动事件里就地更新，
   排队只并掉重复的重算，所以"丢中间帧"不会丢输入（那格最后钉住切点仍等于 round(100/zoom)）。
3. **性能类判据必须读计数，且自带"这一帧确实有东西"的自证**。
   `FullInvalidations`、`TileRenders`、`PreviewFramesForTest`、`DiagnosticLog.AppendRequests`
   四个数一起看；只看"整块清空 0 次"会退化成空判据——**视口里根本没瓦片时它也是 0**。

顺带一条与卡顿无关但同批暴露的接线缺陷：**双向同步必须有旗**。
画布选中拼缝 → 主窗口把列表高亮同步过去 → 列表的 `SelectedIndexChanged` 又回调
`SelectSeam(scrollIntoView: true)` → 视口被推走 + 一次整块 `RefreshChrome()`。
"列表→画布"是用户点了列表，"画布→列表"只是同步高亮，这两件事共用一个事件，
不加 `_syncingSeamSelection` 这一面旗就会互相触发。

## 长截图的去重：从"盖住"改成"裁掉"（第九轮）


需求七的验收式只有一行：`最终导出高度 = Σ各图高度 − Σ各重叠`，且每个重叠像素只出现一次。
实现这条有两条路，本项目现在走的是第二条：

1. **位移法（旧）**：两段都按完整尺寸落位，后一段按 `offsetY = H1 − O` 盖住前一段的尾部。
   算式上高度是对的，但**两份副本都进了像素**，成品里那一截内容只是"被盖住了"。
   代价有三处：① 任何逐段取数的通路（差异视图、检测取数、分段导出）会拿到重复内容；
   ② 用户无法回答"这 O 行要哪一份"——谁在上面完全由绘制顺序决定；
   ③ "去掉了重叠"这件事只能靠事后比对参数与落位才发现（`SeamGeometry` 那本账就是这么来的）。
2. **裁切法（现）**：把重叠带切成两半，`b = BeforeCropBottom` 是前一段尾部真裁掉的行数、
   `t = AfterCropTop` 是后一段头部真裁掉的行数，`b + t = O`。
   于是 `sourceRectBefore = (0,0,w,H1−b)`、`sourceRectAfter = (0,t,w,H2−t)`，
   两段**首尾相接、不再相交**，去重从"绘制顺序"升级为**结构性质**。

关键的几个设计决定：

- **不变式曾经做进 setter，第十二轮起它是公式的结果**。第九轮的写法是 `OverlapLength` /
  `BeforeCropBottom` / `AfterCropTop` 三个 setter 都保住 `b + t = O`（改一侧补另一侧、越界就夹），
  只有私有 `WriteCrops` 碰后备字段。第十二轮把核心字段缩到 `AlignmentOffset` + `CutY` 之后，
  `b`/`t` 变成派生读数（`t = clamp(CutY, 0, O)`、`b = O − t`），"账不平"这个形状从"setter 拦住"
  升级成**根本写不出来**。副作用也记一笔：属性 setter 调方法、方法又写属性会无限递归，
  这类环在重构时最容易踩到（第九轮踩过一次）。
- **默认档 `b=O, t=0` 与旧写法逐字节相同**（老写法里后一张本来就把前一张那 O 行盖掉了）。
  这条等价性让重构是行为保持的（`crop/默认切分与旧的覆盖式落位逐字节相同`，
  参照实现是测试里独立复现的"完整尺寸 + offsetY + 覆盖"），也顺带让 v1 项目文件
  （根本没有这两个字段）补成默认档之后成品不变。
- **落位阶段不读位移**。裁切档的第二遍只用"前一段裁短之后的可见底边"推原点，
  所以"把第二张整张画在下面"这种实现**没有代码路径可走**。
  `EffectiveOffset` 在裁切档里改成"从落位反量出来的数"，界面显示的 Y 与像素落位因此是同一个值。
- **夹取顺序**：先按前一段剩余量夹它的底，再按夹完之后的剩余量夹后一段的顶。
  于是坏参数（O 写得比图还高）只会让裁切量变小，既裁不出负尺寸也不会让总账不平——
  但必须让界面看得见（`CropsAppliedAsRequested`）。
- **红框读同一条出处**：`BandCanvasRect` 在裁切档里从裁切账摆出 `[切点−t, 切点+b)`
  （位移档仍取两段矩形之交）。第八轮那套命中区是拿 `before.Rect ∩ after.Rect` 算的，
  裁切档里两段不相交 → 交集恒空 → 红框与可点区会凭空消失，这就是必须换出处的原因。
- **调试层是另一条取数**：被丢掉的那一份已经不在任何布局矩形里，所以重影对比只能靠
  `CanvasComposer.RenderDebugSource`（绕过布局与补丁）拿。它只服务屏幕，
  导出/预览/布局都不经过它——`crop/调试取数不进出成品的那条合成通路` 量的就是这句话。

## 长截图换了一次地基：公共坐标 + 一条蓝线（第十二轮）

上面那节（第九轮）把去重从"盖住"改成了"裁掉"，这是对的方向，但它仍然把**两个凭空分配的数字**
（`b`、`t`）当作核心状态，只是要求它们加起来等于重叠。需求否掉的正是这一层：
长截图不是"把两张完整图片上下移动后重叠"，也不是"把重叠长度分给两张图"，而是
**先通过像素对比定下两张图在公共坐标里的相对位置，再用一条蓝色裁切线决定蓝线以上由图1提供、
蓝线以下由图2提供**。所以这一轮不是修 bug，是把核心数据结构换掉。

### 现在只有两个状态量

```
Seam.AlignmentOffset : IntPoint   // 图2 相对图1 的位移；长截图里 X 恒 0
Seam.CutY            : int        // 蓝线，重叠带内的行号（0 = 整带取图2）
```

`AlignmentOffset.Y` 以"紧接落位"（两段首尾相接、零重叠）为零点，所以 `Y = −重叠行数`。
其余全是**派生读数**：`OverlapLength = −Y`、`AfterCropTop = clamp(CutY, 0, O)`、
`BeforeCropBottom = O − AfterCropTop`、`CutPosition = AfterCropTop`。
`b + t = O` 于是从"setter 里的契约"降级成"公式的定理"——不需要谁去守住它，也就写不出不满足它的状态。
`CutY` 本身允许存带外的值（那是用户输入或旧文件的原话），但**每个出口都夹**：
读出口夹、布局夹、账上用 `RequestedAfterCrop`（裸值）与 `CutPosition`（生效值）的差把它标出来。

### 布局的推导顺序（`CanvasLayout.Build` 裁切档分支）

```
1  Rect1 = 前段完整矩形 @ 累计原点                    ← 完整尺寸，不裁
2  Rect2 = 后段完整矩形 @ Rect1.Bottom + gap − 重叠    ← 与 Rect1 必然相交
3  OverlapRect = Rect1 ∩ Rect2                        ← 重叠带（带的位置只由对齐决定）
4  cut = OverlapRect.Top + clamp(CutY, 0, OverlapRect.Height)
5  topTrim[后]  = cut − OverlapRect.Top               ← 蓝线以下才归它，所以顶部要裁掉这么多
   bottomTrim[前] = OverlapRect.Bottom − cut          ← 蓝线以上归它，所以底部要裁掉这么多
6  可见原点 = 完整原点 + topTrim → 画布包围盒、Origin、SourceRect 全从这一行推
```

`PlacedSegment` 因此同时挂着两套矩形：`FullRect`/`FullSourceRect`（第 1–2 步那两张完整矩形，
界面与日志要用）与 `Rect`/`SourceRect`（第 6 步裁完的可见矩形）。
**`Origin` 仍然是可见原点**，这一句决定了本轮改动波及多小：`CanvasComposer`、`TileRenderer`、
`ExportEngine` 三头读的都还是可见矩形，它们不需要知道蓝线的存在——蓝线只在第 5 步被折算成两段各自的
裁切量。需求 §五 那条"不许先完整渲染两张再靠绘制顺序覆盖"因此是**结构上**成立的：
可见矩形两两不相交（`crop/长截图里任意两段的矩形都不相交`），任何一个公共坐标只可能有一个像素来源。

### 一条手势、一族日志（第四十一改）

| 手势 | 命中（按判定顺序） | 写什么 | 画布高 | 缓存失效范围 | 日志前缀 |
| --- | --- | --- | --- | --- | --- |
| 点「调整」把手 | `AdjustHandle`（骑在蓝线正中，先于线判定） | **什么都不写**，只开关微调档 | 不变 | 这一层重画 | 无（不开流水账） |
| 压着蓝线拖 | `CutLine`（线 ±9 设备像素） | 抓**下方**那张：`O −= d` 且 `Cut −= d` | 会变 | 带区那几块 | `seam.slide.*` |
| 在带里拖 | `AlignmentAdjust`（带边 10 像素把手）/ `OverlapBand` | 抓**指针那一侧**那张：线上方 `O += d`、线下方同 `CutLine` | 会变 | 带首 → 画布底 | `seam.slide.*` |
| 微调档里点带外 | `hit=null` 但选中缝落得下 | 点选上方／下方那张 ⇒ 之后 `↑↓` 每次挪它 1 源像素 | 会变 | 带首 → 画布底 | `seam.slide.*`（键盘那趟前缀同） |
| 平移画布 | 带外 / Shift+左键 / 中键（且微调档关着） | 只 `Viewport.TopLeft` | 不变 | 视口 | `canvas.pan.*` |

旧的 `seam.cut.*` 与 `seam.alignment.*` 两个前缀**已并成 `seam.slide.*`**（两档手势并成一条的直接后果）；
位移档（竖拼／横拼）仍走 `seam.edit.*`。同一族里"抓下方那张"与"抓上方那张"两趟的字段恰好相反，
判据钉的就是这个相反（`align/滑动两趟的日志各自齐备且互不覆盖`）：共用一个 changed 标志、
或者第二趟把第一趟的 before/after 复用了，都会当场红。

**新增的六个读数**是这一轮的承重墙（`lineCanvasRowBefore/After`、`lineDeviceBefore/After`、
`line_device_moved`、`grabbed`）。理由很具体：滑动这一档里 O 与 Cut 都在动，画布高也在动，
"蓝线没被拖走"这句话**在旧的那三列里读不出来**——必须直接记下蓝线的画布行号与过了视口换算的
设备行号，判据才不必替实现做算术（需求七那句"不许只报两个 offset"同一个理由）。

对齐手势提交时走 `Seam.ApplyAlignment(deltaRows)`，它只碰 `AlignmentOffset`，
并把带变短导致的后果如实回报：`AlignmentApply(Applied, Overlap, CutPosition, RejectedRows,
CutWasClamped, CutRejectedRows)`。蓝线被挤出带时**夹到带边并回状态栏**，不静默吞。
**第十二轮那句"停在同一行号上"在第十三轮改成了按比例换算**（见下一节），
`CutWasClamped` 随之收窄成"只算带真装不下"，换算不再谎报成夹取。

## 第十三轮补：屏幕上的固定侧，与真窗口的帧耗时

第十二轮把数据模型与导出都收干净了，但需求里那两件事仍然只有"字段级"证据：
用户拖动时**固定的那张图真的钉在屏幕上看不到动**、**界面真的不卡**。本轮补的就是这两条。

### 一条躲不掉的几何事实：改本缝对齐只动 Rect2

`CanvasLayout.Build` 是从上往下累计原点的：`Rect2 = Rect1.Bottom + gap − 重叠`。
所以**第 i 条缝的对齐只改第 i+1 段的落位**，Rect1 的位置只由它上面那条链决定。
两个结论直接决定了固定侧怎么做：

- `Fixed=Before`（界面写"固定前一段"）本来就**不需要任何补偿**——Rect1 在画布坐标里一动不动，
  视口也不许动（动了就是偷偷补偿，判据会红）。
- `Fixed=After`（"固定后一段"）要求的是**图2 在屏幕上不动**，而画布坐标里动的恰恰是 Rect2，
  再加上"包围盒永远把左上角归到 (0,0)"这条归一化——两者叠加，用户看到的就是固定侧在漂。

### 补偿只做在显示层，且必须绝对赋值

`StitchCanvasControl.ApplyFixedSideAnchor` 在本轮出现三处（预览、提交、按下时记基准）：

```
anchor = ScreenAnchorRow(layout, seam) = DescribeSeam(seam).Rect2.Y
δ      = anchor − _dragAnchorBase                 // _dragAnchorBase = 按下那一刻的 Rect2.Y
Viewport.MoveTopLeftTo(_dragViewportBase + (0, δ))  // 绝对赋值，X 恒取按下时的原值
```

三个细节都是承重的：

- **基准取自"按下那一刻"**，不是上一帧。增量式补偿会把浮点/取整误差累进视口，
  拖一趟来回就永久漂移；绝对赋值天然可逆，取消手势时 `MoveTopLeftTo(_dragViewportBase)` 一句话收回。
- **只改视口**：不写参数、不 `Project.Mutate`、不进撤销栈，日志单独走
  `seam.alignment.fixed_side`（带 `reason`/`compensation`/`mutated=false`/`undoPushed=false`），
  这样"为什么按了没反应/为什么画面整体挪了"能从账上讲清楚。
- **顺序**：先补偿视口、再 `FillCropGeometry` 填 trace，否则 `rect2DeviceAfter` 记的是补偿前的数，
  判据与日志就会各说一套。

守卫 `guard/固定后一段若撤掉显示补偿则图2 在屏上会漂` 把这三行注释变成可红的断言：
撤掉补偿必须读到 Rect2 设备 Y 跟着漂。

### 蓝线的保存语义：行号 ⇒ 带里的相对位置

`Seam.SetOverlap` 与 `ApplyAlignment` 现在共用一个私有 `ScaleCut(old, oldO, newO)`
（`(old*newO + oldO/2) / oldO`，整数四舍五入、`long` 防溢出）。
关键顺序是**先换算再夹**：`ScaleCut` 吃的是 `CutY` 的裸值（允许是带外的那个数），
夹取只在 `Math.Clamp(…, 0, o)` 这一处。若先夹再换，带外那次写入会被"洗白"成带边，
`CutWasClamped` 就再也报不出来。

### 帧测量：控件自己记，判据读计数

`OnPaint` 拆成计时壳 + `PaintCore`，`RecordFrame` 进环形样本（4096 条），
派生出 `LastFrameMs` / `MaxFrameMs` / `FramePercentileMs(95)` / `Fps` / `CacheHitRate` /
`FrameAvgMs`，并按阶段累计（取数 / 棋盘 / 贴图）。`MouseMoveTo` 计 `MouseMoveCount`、
记 `LastInputTicks`（"UI 队列延迟"就是下一次 Paint 与上一次输入之差）。
这些读数的消费者是状态栏（每 500ms 刷一次）与 `--gui` 那几条阈值，不是电池——
电池里的 `crop/100 次鼠标移动只换几帧预览` 量的是**派发策略**（有没有整块清缓存、有没有逐帧写日志），
两者不可替代。

### 显示层三处提速，红线是"成品字节不变"

| 改动 | 为什么安全 |
| --- | --- |
| 瓦片 `RgbaImage` → GDI 位图缓存，**以实例引用为键** | 引用相等 ⇒ 内容变了必换新实例、必失效，不可能留着上一帧像素；修订号一变整表 `Dispose`（控件 `Dispose` 同样清，GDI 句柄不受托管堆回收保证） |
| `DrawTiles` 尊重 `g.VisibleClipBounds`，反算回画布矩形取交后再决定派发哪几块 | 只减少"画到屏幕外的块"，逐块内容与顺序不变 |
| 拖动途中 `InterpolationMode.Bilinear`，静止回到 `HighQualityBilinear` | 只影响显示缩放；导出通路从不读屏幕 |

P95 从 62ms 降到 22–24ms 是靠分阶段读数定位到"贴图"那一段，**没有动过任何阈值**。

### F8 调试层：把"哪张图在动"和"卡在哪一段"画在同一屏上

`DrawDebugHud` 是需求 §六 那批开关的落地，**一个开关开全**：绿框=Rect1、黄框=Rect2、
白半透明=OverlapRect、蓝线=CutY、红箭头=可拖对齐区（这五样与「重影对比」走
`DrawAlignmentOverlay` **同一个画法、同一批颜色**——两套画法迟早会漂，所以只留一份），
灰虚线=画布边界、**灰实线=视口当前可见范围**（需求六那句"Viewport 边界：灰色"），
紫虚线=三块命中区
（整条带 / 蓝线上下 9 设备像素 / 带首尾 10 像素把手），再加 11 行读数
（Rect1、Rect2、OverlapRect、CutY 及其比例、AlignmentOffset+固定侧、Viewport+缩放+画布高、
瓦片数/渲染数/整块清数/命中率、帧最近·最大·P95·FPS·**分阶段**、Paint/鼠标/预览帧/修订号）。
它与 `ShowDebugHud=false` 的唯一差别就是屏幕像素：
判据 `align/关掉调试层不改对齐、蓝线、导出字节与命中区` 四项各量一次，
另加一把正向对照（打开前后两帧屏幕取样必须有差异）——少了它，"只影响显示"可能只是"什么都没画"。

**这一层自己不是零成本，读数写在这里**：本机 `--gui --hud` 的 P95 是 35–39ms（第十四轮实测见 README「验证状态分三档」与 §三 的诚实缺口，已把这一档的代价拆成"读数层自己"与"画布"两本账），
比关着它（19–23ms）贵 +12~17ms/帧。为它削过两处（笔刷从"每帧 new"改成进程级缓存、
11 行文字压成一张 10Hz 重建的面板位图），剩下的就是"多画一层框 + 一层半透明填充"本身的钱。
所以需求五那几条阈值是**关着它**过的，"开着调试层也流畅"不作为结论。
它存在的意义仍是让"卡顿发生在哪个阶段"不用靠猜——上表那三处提速就是这么定位到的。

### `--gui`：真窗口的性能工装，不并入电池

`checks/LongStitch.Checks/GuiPerfHarness.cs`：STA 线程 + 真 `MainForm` + `PostMessage`
投真鼠标消息，17 张 1179×2556（优先 `test/` 里的真截图，缺料才在 `%TEMP%` 造合成图并在结论里明写），
长截图模式、缩放 35%、来回拖 100 次 ±10 设备像素。全部阈值过了退 0（条数随档位变：
第十四轮加了"静止帧不许重算完整布局"一条，开着读数层时再加"面板重建不超过 10Hz 预算"一条，
于是关着 9 条、开着 10 条），有失败退 1，
跑不起来退 2 并打 NOT-RUN。它刻意**先结清拖动阶段的读数再松手**——松手那次提交本来就允许整块清缓存，
混进拖动阶段会让一条设计行为替实现背债。

帧耗时这一条**对同机负载敏感**（本机同一份代码读到过 17–21ms 与 84–156ms），所以工装把归因证据一起打出来：
逐帧样本（撞上回收那一帧带 `*`）、拖动期间 gen0/gen2 增量、预览重算次数与总耗时（这段在鼠标消息里、
不在 `OnPaint` 里，帧样本天生量不到）、以及**最慢那一帧**（不是最后一帧）的分阶段拆分。
"每 100 次移动 ≤ 10 帧"按需求原话的分母折算，`--moves` 调大只是多取样本。

### 为什么兼容字段差点又造出第二个真相

为了读得懂第九~十一轮存的项目文件，`BeforeCropBottom` / `AfterCropTop` 这对旧名字保留了。
本轮发现**两个都往 `CutY` 写**——于是反序列化时 JSON 里谁先出现谁说了算，
落库的是"顺序的产物"。这就是需求 §七 那句「不能让多个字段互相覆盖」点名的形状，
只不过它藏在"看起来只有一个真字段"的重写之后。处理：`BeforeCropBottom` 改纯派生（无写入口），
`AfterCropTop` 是唯一写入口，`NormalizeAlignment()` 在非手动档把蓝线交回 `AutoCutY`。
守卫 `guard/蓝线与对齐若共用一个字段则两条手势会互相顶掉` 负责让这一族错误写法在将来再次红出来，
正面判据是 `align/旧项目文件的裁切字段按任意顺序到达都归一到同一组核心值`：用 DOM 把
`OverlapLength`/`AfterCropTop`/`BeforeCropBottom`/`CutY` 四个键按三种顺序重排、各读一遍，
要求核心值一字不变；再加"只留 `AfterCropTop=45`（删掉 `CutY`）时蓝线必须跟着走"这把正向对照，
否则"三趟同数"可能只是"这些键根本没被读进来"。



- 所有参数读写在 UI 线程。`Project` 不是线程安全的。
- 后台只跑两件事：**匹配计算**与**导出**。
  - 匹配：先在 UI 线程取一份 `CanvasLayout` 快照，后台只对快照算，结果回 UI 线程一次性 `Mutate`。
  - 导出：`ExportEngine.Run` 是同步方法，调用方放后台线程；它只读布局不写参数。
- `ISourceResolver` 的实现带缓存但约定"返回的实例只读"，多个片段共享同一实例。

## 第十四轮补：撤销把视口一起带回，读数层自己的代价量得出来

### 显示状态挂在历史条目上，而不是另开一个撤销栈

需求一给过两条路：要么"给视口建立单独的可撤销显示状态"，要么"在 Undo/Redo 完成事件中恢复
保存的 Viewport 快照"。选第二条，因为第一条会造出**两个栈**——用户按一次 Ctrl+Z，
参数与画面各自按自己的顺序回退，早晚会分叉（本工程最怕的就是"一个事实两处出口"）。

做法：`Project` 的撤销条目从 `(JSON, Label)` 变成 `(JSON, Label, HistoryDisplayState?)`。
那份快照对 Core 是**不透明附件**——Core 不知道视口是什么，只在 `Changed` 之后
raise `HistoryStepped(HistoryStep.Undo|Redo, display)`。顺序很重要：先换文档再发事件，
订阅方（画布）才能在"布局已经是撤销后的那一版"的前提下去换算目标位置。

`HistoryDisplayState` 只有四个动作：按下时填 `*Before`、提交时 `Complete(...)` 回填 `*After`、
按 `HistoryStep` 给出该回哪一个视口（`ViewportFor`）、把字段名摊成日志用的 snake_case
（`Fields()`，写进 `history.viewport.restored` 那行）。**没有第五个动作**，
因为一旦 Core 之外有人能改它，"快照与那一条历史同源"就不再成立了。

### 「没挪过屏就不许还屏」

`ViewportMoved => ViewportBefore != ViewportAfter`。画布只在这个为真时动屏幕。
理由不是省一次赋值，而是**撤销不许猜用户此刻想看哪**：
`Fixed=Before` 那一档拖动本来就不挪视口（见第十轮那条几何事实），
如果期间用户自己滚过一段，撤销把那一段"还"回按下时的位置，等于替他做了一次他没要求的跳转。
`guard/撤销若只换文档不带显示快照则视口停在补偿位置` 里那条反向对照量的就是这一族：
固定前段 + 用户自己 `+37`，撤销必须**不动**视口。

### 为什么快照必须是"这一次手势自己的基准"

同一缝连拖两次再撤销，回到的不是最初那个视口，而是**第一次拖完**那个。
如果判据写成"撤销后 == 屏幕最初那个位置"，它量的是第二次的效果、判的是第一次的账。
守卫格子里那句 `rect2BeforeSecond` 就是为这件事准备的：每一步的期望值现量，不许从别的趟抄。

### 读数层的代价用三个计数器记账，不用毫秒

需求三那句"调试 HUD 不得调用完整 `CanvasLayout.Build`"用散文写是判不出真假的，
所以加计数器：`CanvasLayout.BuildCountForTest`（进程累计，只有工装与判据读它，
产品逻辑不许读——它与 `CanvasComposer.WholeRunCountForTest` 同一地位），
加上画布自己的 `HudGeometryRebuilds` / `HudPanelRebuilds`。
需求三这一族判据现在共 **17 格**（`canvas/` 十格 + `guard/` 七格）把这六句话各自钉住：
静止 20 帧不重算布局 / 不整块清缓存 / 不重渲染瓦片；面板重建不超 10Hz；
每帧额外堆分配 ≤512 字节（实测 105）。

为什么"额外分配"而不是"总分配"：绘制通路本身每帧也要分配（分阶段耗时那个字符串等），
那部分与读数层无关，混在一个绝对数里要么"谁都过不去"要么"阈值只能放很宽"。
`guard/读数层若退回每帧排文本与重建位图则堆分配立刻翻红` 把旧写法当场复现一遍，
要求它每帧越过那条线数倍——**没有这格，512 这个数就是白写的**（改回旧写法可能仍"绿"）。

几何缓存的签名（`HudSignature`）照需求三第 4 条逐项点名：视口原点、缩放、控件尺寸、
选中哪条缝、修订号、Rect1/Rect2/带/切点/重叠/固定侧。
**预览布局生效期间绕过缓存**——那一族帧每一帧的矩形都不同，缓存签名只会白白失效一次，
绕过它并把"拖动期间不重算"这条判据限在稳态帧上。

### 帧耗时两档分开报

每帧记下两个数：整帧毫秒、其中读数层占的毫秒（`ShowDebugHud` 为真时夹一段 `Stopwatch`）。
于是 `HudSplitStats` 能给出 `HUD 单独耗时` 与"同批帧减掉 HUD 之后的画布部分"两组 P50/P95/max。
需求三要求两档不许混为一谈，靠的就是这两个数分开——第十轮那句"开着 F8 的 P95 超 33ms"
当时没法说清是读数层贵还是画布贵，现在能。

### 同一批帧还要按手势切段，否则"最慢帧"的归因会写错

样本池是一圈 4096 枚的环形数组（`FrameSampleCap`），**一趟真窗口手势只写进一两百枚，永远不会把它转出去**
⇒ 池里最慢那一枚一直是导入／首次绘制那几帧。第十四轮前半程据此写过"拖动时最慢 80ms"，那是错的归因。
修法不是把池子加大，而是让**产品自己的手势通路**封口：`BeginPan` 与对齐拖动起点各打一次
`MarkGestureFrames()`（记下按下时的环形下标与单调写入计数），`MouseRelease` 在提交重画之前记一次
`_gestureEndTotal`。于是 `DescribeDiagnostics()` 交出两行不同的读数——
「拖动段（自最近一次按下起）」含松手后的提交重画，「其中拖动中（按下→松手，不含提交重画）」才是纯拖动时间。
判据 `canvas/拖动段的帧读数只算最近一次按下之后的帧` 钉住"段就是尾巴那几枚"，
反证 `guard/拖动段若退回整个样本池则导入帧会冒充拖动最慢帧` 把"段＝整池"那种退化当场照红。
按这一层重量：关档段最慢 5.3–14.7ms、开档 12.3–16.7ms，而同一趟的池最慢仍是 69.1–86.9ms
⇒ 需求五那条 `单帧 ≤ 50ms` 在**拖动时间**上两档都过，它的红只出现在导入期，两句话不许并成一句。

### 调度读数一次给两笔：「求和」证明它在动，「最忙那条」说明谁在等

需求五那句"偶发 80–150ms 时记录 GC 与<b>进程调度信息</b>"，GC 那一半早就是计数器了，
调度那一半过去只有一句推论（"墙钟减进程 CPU 差出去的那截就是被抢占的"）。推论没错，
但那个差里混着后台解码线程的时间，<b>分不清是"谁"在等</b>。现在诊断出口多一行「线程与调度」
（出处 `Diagnostics/ThreadScheduling.cs`），一次报两笔，因为这两件事必须由两笔各自回答：

| 那一笔 | 是什么 | 它管什么 | 为什么不能拿它顶另一笔 |
|---|---|---|---|
| 求和 | 逐条线程的 用户＋内核 CPU 相加 | <b>证明这一行不是写死的</b>（反证格钉的就是它） | 后台线程一起算进去 ⇒ 实测 求和 438ms <b>大于</b> 本趟墙钟 250ms |
| 最忙那条 | 累计 CPU 最多的那条线程自己 | <b>拖动归因</b>：墙钟减它＝UI 线程在等（那趟是 78ms） | 两次取读数之间它可能换成另一条线程 ⇒ 只作读数、不进任何阈值 |

两条实测事实（下次别再猜）：

1. <b>.NET 8 的 `ProcessThread` 在 Windows 上给</b> `UserProcessorTime`／`PrivilegedProcessorTime`／
   `TotalProcessorTime`／`ThreadState`／`WaitReason`，<b>不给</b> `ContextSwitchCount`
   （那是 .NET Framework 的 Windows-only 成员，没移植过来）。要切换次数只能装性能计数器包，
   而本项目零 NuGet 依赖 ⇒ 出口把那一笔<b>明写成"按未量记"，不写成 0</b>。
   判据里还专门有一条判"不许出现 0 次"——恒为 0 的字段与"这趟真的没发生"在屏上长得一模一样。
2. <b>反证格第一次跑红，红出来的是判据选错了钉子</b>：第一版钉的是"最忙那条"，
   在一条本来就排不上第一的线程上空转 40 毫秒，它当然一动不动（1188ms → 1188ms）。
   那一次红是对的——它拒绝了一条"永远照不出退化"的判据。
   教训：<b>正向对照必须钉在"任何一条线程动一下它就动"的那笔上</b>，归因用哪笔是另一件事。
   判据 `canvas/交互诊断读数里需求五点名的进程调度那一笔必须从操作系统读来`（字面齐备＋"求和"
   落在工装自己逐条加出来的 [前, 后] 区间里），反证
   `guard/调度读数若写成固定值则空转攒够十五毫秒再取第二次它也不涨`。

还有一条口径纪律：这一行<b>只在诊断出口取</b>（枚举线程每一项都会分配），一帧都不许读——
放进 OnPaint 就成了"读数层自己变贵"那一族老毛病（需求三）。

### 每帧瓦片预算：冷活才算，稳态帧一帧都不许欠

`DrawTiles` 原来是"这一帧把视口里所有瓦片一次取完、一次贴完"。拖动档这样没问题（只在已经缓存过的带区里挪，
实测取数只有 1~3ms），但**滚轮不是这个形状**：20 格滚轮只换来 3~4 帧（`WM_PAINT` 会合并），
每帧要一次性取完新滚进来的那一屏。150% 真窗口量到的未限流形状是**一帧 55.6ms**——
取数 30.5 ＋ 贴图 20.1，没有回收标记、也不是抢占（同帧内最忙那条线程的 CPU 与墙钟同步在涨）。
`单帧 ≤ 50ms` 当场红，而且它每次滚进没见过的区域都会红。

于是把这一帧的活儿分成两种：<b>冷活</b>（这一帧第一次碰这块瓦片：`TileCache.Get` 里现取渲染、
以及 `BitmapOfTile` 里首次把 `RgbaImage` 拷成 GDI 位图，约 1MB/块）与<b>稳态活</b>（每帧必做的重采样贴图）。
预算（默认 12ms/帧）只管冷活：累计超预算就停手，欠下的块这一帧画成棋盘格，当场 `Invalidate()` 接下一帧。

| 一笔活儿 | 属于 | 计不计预算 | 为什么 |
| --- | --- | --- | --- |
| `_tiles.Get` 现取渲染（`TileRenders` 涨） | 冷活 | 计 | 只有第一次要渲，推给下一帧是真的少做 |
| `BitmapOfTile` 首次转换（`TileBitmapConversions` 涨） | 冷活 | 计 | 整块 1MB 拷贝，一次性的 |
| `g.DrawImage` 重采样（命中缓存的贴图） | 稳态活 | <b>不计</b> | 每帧都要重做，推给下一帧只是换个时间疼 |
| `DrawChecker` 棋盘格 | 稳态活 | 不计 | 一帧 1~2ms，且停手后还要为欠帧再画一遍 |

**这一族判据共 3 格**（`canvas/` 两格 + `guard/` 一格）：
`canvas/滚轮那一档一帧画不完的瓦片必须欠帧、追一帧、欠的那块画成棋盘格`
（预算压成 0.0001ms ⇒ 一帧只画一块、必须欠帧、必须追加要帧、欠的那块中心不许是画布底色）、
`canvas/瓦片限流连着画满的那一帧与不限流那一帧逐字节相同`（红线保命绳：限流只改节奏不改像素）、
反证 `guard/瓦片预算写得比一整屏还大时不许出现欠帧`（预算＝一百万毫秒时必须一帧画满，
证明前两格读到的"欠帧"是真按预算停手，不是写死的形状）。
`--gui` 的滚轮／缩放通道另把 `瓦片限流 = 预算 … 本趟追加要帧 … 最后一帧欠 …` 三笔一起打出来，
真窗口里"追加要帧 > 0 且最后一帧欠 0"才算这一改动在屏上闭环。

**第一条停手条件是被挂死逼出来的**：第一版把贴图也算进预算，于是全命中的稳定帧每帧都"超预算"
⇒ 每帧 `Invalidate()` ⇒ `Application.DoEvents()` 的队列永远排不空 ⇒ 工装整趟不动了七分钟。
凡是"这一帧做不完推给下一帧"的实现，都要给"下一帧"配一个**必然收敛**的条件，
这里用的是"这一帧确实做过冷活才许停"；电池那两格用极端预算（0.0001ms 与一百万毫秒）把两头钉住，
   停手次数天生跟着**一屏块数**走（块数 ≈ 视口尺寸 ÷ 缩放 ÷ 512）：`--at-zoom 100` 时一屏只有 1~2 块，
   冷活到不了 12ms ⇒ 滚轮一趟都不追加要帧；`--at-zoom 25` 时一屏 12 块 ⇒ 每趟追加要帧 5~6 次。
   所以"预算"这个数不绑百分比、绑的是块数，换缩放档量的时候别把它当成一个普适常数。
不依赖任何毫秒阈值，所以不会随机器心情红。

### 滚轮途中的重采样档：一次手势只补一帧

每帧瓦片预算管住的是"取数"那一段，剩下"贴图"那一段由另一件事决定：
GDI+ 把 512×512 的瓦片按缩放画到屏上时选哪一档重采样。产品里原本只把三种拖拽
（改切点／改对齐／平移画布）认成"正在动"，于是滚轮期间每帧都按"静止"给最贵的那档
（`HighQualityBilinear`）——35% 下同一屏的瓦片数与拖动档差不多，
拖动贴图 11~15ms、滚轮档 16~27ms，差就差在这一档。

现在的规则是三档，而且**只有显示层走它**：缩放 1.0 及以上一律 `Nearest`（放大看接缝必须看到真像素）、
途中 `Bilinear`、静止 `HighQualityBilinear`。导出与合成永远不读这个开关，
成品字节不受影响——钉住这件事的仍是 `align/关掉调试层不改对齐、蓝线、导出字节与命中区`
加真机 `--stitch` 逐行比对（红线三）。

"停手那一帧同质量"必须是**一帧**，不是一串。实现用一次性 `System.Windows.Forms.Timer`：
每次滚轮 `Stop(); Start();` 把它重启，于是最后一次滚轮 120ms 后只响一次、补一帧高质量、自己停下；
连续滚动期间一次都不响。试过并被量出来否掉的写法是"窗口内每帧 `BeginInvoke` 续排"：
那等于把停手那笔钱在滚动中途提前付掉，真窗口 35% 滚轮档合并池 P95 从 27.3ms 涨到 30.5ms、
25% 从 28.3ms 涨到 32.0ms——一次手势"补一帧"变成了"补 N 帧"。
这两枚涨回来的数是留着当反证的：判据不许只说"改实现后更快"，它得能量出这一改的形状。

**这一族判据共 2 格**：`canvas/滚轮途中走便宜插值、停手后只补一帧高质量`
（静止 HighQuality → 途中 Cheap → 停手恰好补 1 帧、再等 400ms 不补第二帧；
滚轮的平移与 Ctrl+缩放两档都要挂上计时器）、
`guard/滚轮补帧次数不许随滚轮格数线性增长`（1 格与 5 格都只补 1 帧：
撤掉补帧机制读到 0、改成按格排读到 5，两头各红一次）。

还有一笔账要留在这一节：**预算只能在块与块之间停手，一块瓦片内部的冷活拆不开**。
35% 冷缓存的真窗口第一趟读到过一帧 54.7ms（取数 37.5 ＋ 贴图 11.7；无回收标记，
同帧最忙那条线程的 CPU 与墙钟一起涨 ⇒ 真在算而不是被抢占）——
那正是"第一次滚进没见过的区域"时一整块瓦片的取数（含那张源图的首次解码）顶破 50ms——括号那半句第九改量了：真窗口最慢帧报 0 张／0.0ms 的形状；
同一形状重跑的第二批 5 趟全绿（途中最慢 18.4~20.6ms）。所以这一档的偶发红要这样记：
**它属"块内冷活拆不开"，不属"读数层变慢"**，真要消掉得动瓦片边长（块数与贴图段会跟着变），
不是把阈值放宽。

### 分阶段那一行必须加得满一帧（否则"没量出出处"是读数的缺陷，不是产品的谜）

需求六那句"卡顿发生在哪个阶段"靠的是一行分阶段读数。第十四轮在 HUD 开启档量到一枚 37.4ms 的帧时，
分阶段只加得出 20.4ms，当时文档写的是"剩下那一截没量出出处"。查下来这句话锅在**读数自己**：
`PaintCore` 只给取数／棋盘／贴图三段计了时（这三段在 `DrawTiles` 的循环里，天然有起止点），
而一帧里还有六段从没计过时的绘制——背景、重影对比层、拼缝线、补丁层、拖动角标、点选引导线——
再加上 OnPaint 自己开头那一小截（帧计数、时间戳入队）。

第三改当时补的是笼统一笔**其余 = 帧总时长 − 已计时的各段**；第四改把它按 `PaintCore` 的边界切成两笔：
**叠层 = PaintCore 总时长 −（取数＋棋盘＋贴图＋读数层）**、**帧前 = 帧总时长 − PaintCore 总时长**。
电池里现量的比例说明这几笔不是可选项：本批判据那一格第二帧 2.28ms 六笔齐（取数 0.00 ＋ 棋盘 0.31 ＋ 贴图 0.15
＋ 读数层 0.74 ＋ 叠层 1.07 ＋ 帧前 0.00），反证那一格前三段 0.60ms 只占整帧 3.53ms 的 17%。

**这一套帧样本看不见什么（口径的边界，必须跟读数一起写）**：帧的起点与终点都在 `OnPaint` 里面，
而 WinForms 把双缓冲位图贴回屏幕是在 `OnPaint` 返回**之后**，`WM_PAINT` 的派发与队列等待也在那之外。
第三改的文案把第二笔叫成"帧外"、还写上包括交换与派发，等于把没量过的东西算进账里——
它读 0.00ms 不能当成"派发没问题"的证据，只能当成"`OnPaint` 一进门那三行赋值不花钱"。
名字因此改成**帧前**；交换与派发那一族继续只能靠同帧的回收标记与调度那两行间接读。

| 这一笔 | 谁计时 | 为什么必须分开 |
| --- | --- | --- |
| 取数 | `DrawTiles` 里逐块瓦片取渲染前 | 冷活，进每帧预算、可停手 |
| 棋盘 | 欠下的那块画成棋盘格 | 限流的代价，只随欠帧出现 |
| 贴图 | 每块瓦片贴到设备矩形 | 每帧必做、不进预算 |
| 读数层 | `DrawDebugHud` 整段 | 需求三那两档读数的分母 |
| 叠层 | `PaintCore` 总时长减掉上面四笔 | 背景、对比层、拼缝线、补丁层、角标、点选引导线——**我们自己的代码**，要优化就优化这里 |
| 帧前 | 帧总时长减掉 `PaintCore` 总时长 | `OnPaint` 一进门那三行赋值；电池与六个缩放档的真窗口里恒读 0.00ms。**交换与派发不在这一笔里**（在 `OnPaint` 之外，量不到） |

**这一族判据共 2 格**：`canvas/最慢帧分阶段要把整帧的账加满`（六笔之和必须等于帧总时长、
每一笔都落在 0..帧总时长之内、开着叠层时"叠层"必须真的 >0）、
`guard/分阶段只报前三段时这一帧的账加不满`（前三段必须<b>严格小于</b>整帧，且缺的那一段正好由
"读数层 ＋ 叠层 ＋ 帧前"补上——退回旧格式当场红，把读数层重复计进叠层也当场红）。
判据读的是数值版出口 `StitchCanvasControl.StageNumbers`（一份 record），不去解析那句人读的文案：
解析文案的判据一改措辞就自己变红。

这一笔立刻在真窗口用上了：补量中间缩放档时 `--at-zoom 200` 量出一枚 62.0ms 的红，
它的分阶段是取数 0.0 ＋ 棋盘 3.8 ＋ 贴图 1.5 ＋ 读数层 0.0 ＋ **其余 56.7**，
同一帧带着回收标记、同趟 gen0 1／gen2 1，而调度那行给的是墙钟 594ms、全部线程 CPU 求和 610ms、
最忙那条只涨 94ms——UI 线程那 56.7ms 里绝大部分<b>不在算</b>。
于是这一枚记成"回收／派发那一族"，不再记成"没量出出处"。
**第四改（切成叠层＋帧前之后）重跑同一档**：`--at-zoom 200` 五趟三通道 **0 条红**，这枚 62.0 未复现；
同一批把最慢几帧拆开看到的是 **叠层 6.5~9.0ms ＞ 贴图 2.0~2.3ms** —— 高缩放档下一屏只盖住一两块瓦片，
钱花在没逐段计时的叠层笔画（拼缝线、角标、补丁层这类整屏几何）上而不是瓦片，
这是"叠层"这一笔第一次指出一个可优化的方向；帧前在六个缩放档的所有帧里都读 0.0。
<b>通用一条</b>：凡是"某一笔耗时解释不了整帧"的读数，先把口径补全再谈归因，
否则下一轮会把读数的洞当成产品的谜，或者更糟——当成环境的偶发。

### 叠层拆账：把"没逐段计时"那一段拆到能指认（第五、六改）

需求六那句"卡顿发生在哪个阶段"到第四改为止只能答到"叠层"这一层——它仍然是一整笔，
读到 0.4ms 与读到 56.7ms 是两种完全不同的事，可名字相同。于是把 `PaintCore` 里那六个从没单独计时的
调用各开一列（计时点只夹住调用本身，画法与坐标换算一个字节都没动）：

| 这一列 | 夹住的是哪次调用 | 现量（真窗口 200% 档最慢帧） |
| --- | --- | --- |
| 背景 | `DrawBackground`（＋空态那行提示） | 0.1~0.2ms |
| 预览 | `DrawOverlapPreview`（重叠带那半透明一层） | 1.8~3.6ms |
| 拼缝 | `DrawSeams`：每条缝的线、把手、状态标签，选中那条还含对齐层 | <b>4.2~6.8ms</b> |
| 补丁 | `DrawPatchOverlay` | 本批素材 0.0ms |
| 角标 | `DrawDragBadge` | 0.4~0.6ms（拖动通道才有） |
| 点选 | `DrawSplitPick` ＋ `DrawBandRect` | 0.0ms（本批没进点选态） |
| 残差 | 叠层 −（上面六列）＝ 取布局那一次与调用之间的空隙 | 0.0（200%）／1.3~1.8（HUD 开档拖动） |

**恒等式由产品自己减出来**：判据 `canvas/叠层那一笔要能再拆到底` 核对"六段＋残差 == 叠层"，
反证 `guard/拆账必须跟着开关动` 核对"关掉重影对比层，预览那一列必须掉到 0，而拼缝照旧有数"——
后者防的是六列其实是同一笔钱复制出来的（那样关掉开关它们不会跟着变）。

**这一族判据共 4 格**：拆账两格 `canvas/叠层那一笔要能再拆到底` 与 `guard/拆账必须跟着开关动`，缓存两格 `canvas/缝状态标签的宽度只量一次` 与 `guard/标签宽度缓存的键必须含字体与 DPI`。

**这一节改变了两句话**：

1. 高缩放档下一帧里最大的一笔是**拼缝线那一段自己的代码**（4.2~6.8ms，整帧才 12~13.7ms），
   不是瓦片，也不该记在回收头上——残差 0.0 说明这一笔真在 `DrawSeams` 里。
   顺着这条做的第六改只动**分配**：每缝每帧新建的笔/刷提到静态（当时 `Theme` 全是 `static readonly`、
   运行时不换主题；<b>第四十八改之后配色能运行时换档了</b>，这批静态画具改为各自订阅 `Theme.Changed`
   就地把对象的 `Color` 改掉——字段仍 `readonly`、对象仍是同一枚，"每帧不新建画具"与"能换肤"同时成立）、
   状态标签宽度走缓存表；矩形公式与颜色不变。复跑同一命令行：
   200% 三通道池 25 帧 平均 13.7 → 10.3ms、最慢 42.2 → 13.1ms，拼缝段 4.2~6.8 → 3.2~4.4ms。
2. **缓存的键必须把字体的全部维度算进去**：第一版写"文字 × 字体名 × DPI"，被自己刚加的反证格抓红——
   `Font.Name` 不含字号，同一句"已通过"在 8.5 与 20 号字下族名相同，缓存于是把 96px 的量结果当 44px 用，
   那正是"标签盒子比字窄、整行被截"那一族。补齐成 文字×字体名×字号×字形×单位×DpiX×DpiY。
   DPI 那一维反证判的是"有没有另开一格"而不是"宽度是否不同"——同一句标签在两个 DPI 下宽度可能恰好一样，
   判宽度会把这一半判成空绿。

### 按可见区取数：改"画多少"的那一族必须用像素验收（第七、八改）

拆账量到"哪一段最贵"之后，连着做了两笔降耗，两笔的形状不同，所以判据的形状也不同：

| 那一笔 | 裁的是什么 | 能不能裁 | 判据量什么 |
|---|---|---|---|
| 第七改：屏外的缝不画把手与状态标签 | **一个像素都不落地**的整块 | 能——屏上不差一像素 | 计数：`画` 与 `跳过` 各涨多少（＋反证"早退每帧重算"） |
| 第八改：对照层只取带里屏上那几行几列 | 画了、但**落在屏外**的像素 | 能——前提是行/列换算不错位 | **逐字节恒等式**（裁与不裁在同一块矩形上必须一模一样） |

第八改的动机是真窗口量出来的：`DrawOverlapPreview` 每帧按**整条重叠带**分配两到三张 `RgbaImage`，
而对齐拖动会让带随手势变长——25% 那一档读到过一帧 **316.2ms**，拆账里 `预览` 那一笔 **291.6ms**
（同帧 取数 7.7 ＋ 棋盘 1.1 ＋ 贴图 12.0 ＋ 读数层 0.0 ＋ 叠层 295.4 ＋ 帧前 0.0）。
现在取数前先 `band ∩ Viewport.VisibleCanvas()`，可见区量不出来时（`CreateControl` 之前、离屏夹具）**退回整条带**：
宁可照旧取整带，也不许因为"裁不出可见区"把这一层整个画没——那是删功能换性能。

**为什么这一族的判据不能是耗时**：一个**错行**的对照层照样很快，甚至更快。
所以 `canvas/对照层裁到可见区后每行像素不许变` 拿"不裁的整带"当参照，
要求裁出来的对照图（`RenderDebugSource` 那条路）与正常合成图（`RenderBand` 那条路）
都跟参照里**对应的那几行、那几列逐字节相同**；两个窗口各查一遍，第二个把视口横着挪 7 列，
这样 x 方向的偏移换算也被真量到。换算一律走产品自己的出口 `DiscardedCopyForTest`——
判据再抄一套换算，它证的就是判据自己写的第二份代码。

**这一族连红三次，三次红的都是判据或反证，不是产品**（都留在原地当反面教材）：

1. 主格第一版假设"只裁行、宽度不许变" ⇒ 现量打红（带 60 列、窗口 50 列：放大 8 倍一屏只有 50 列画布，
   横向本来也被切）。修的是假设，把 x 一起算进换算。
2. 主格第二版把 `Slice` 的**列数当字节数**（`Row(y)` 交回来的是字节跨度，一像素 4 字节）
   ⇒ 两根 span 长短不同，`SequenceEqual` 恒 false，报成"每行都错行"。
   列→字节的乘法只在这一处做一次，并写进注释。
3. 反证第一版是**假绿**：它数的是"相等的行数"却断言"有 N 行不同"（方向写反），又踩同一颗列/字节的雷
   ⇒ 两种错法都"抓到全部行"，看着有牙其实什么都没抓。
   现在先做正向对照（同一矩形 0 行对不上），再要求"错一行"和"整张放在 0 行"各有 62 行对不上，
   并把"窗口宽度本身就是被裁的量"钉成夹具自证。

**这一族判据共 4 格**：`canvas/屏外的缝不画把手与状态标签`、`guard/屏外早退不许粘住可见的那一条`、
`canvas/对照层裁到可见区后每行像素不许变`、`guard/对照层错一行必须被字节比较抓到`。

兑现的读数（同一命令行、同一机器、每趟冷缓存）：200% 空闲三通道池 25 帧 平均 10.3 → **8.8ms**、
最慢 13.1 → **10.4ms**、`拼缝` 段 3.2~4.4 → **2.0ms**；25% · HUD 开 · 拖动 5 趟池 **P95 30.4／最慢 31.8ms**
（同一档改前最慢 316.2ms），滚轮池 34 帧 P95 24.6ms 全绿；25% · HUD 关 · 三通道 17 条全过
（池 57 帧 平均 19.3／P95 26.8ms）。**没修好的也照写**：
25% 缩放通道 `本通道合并帧池 P95 ≤ 33ms` 读到 **33.1ms**（超 0.1ms）仍红——
同一批最后一趟复判时池涨到 21 帧又读到 23.5ms 转绿 ⇒ **这条判据读的是累计池，对帧数容量敏感**，
红的那三行是同一枚帧在不同容量下的复判，不是三枚帧；阈值与池的算法都不动，只把这个形状写下来；
HUD 开 · 35% 拖动这批 13 条全过但**余量只有 0.5ms**（池 P95 32.5ms），
而 25% 关档同一命令行连跑两批里前一批曾整批抬到 P95 61.7ms ⇒ 这两句都不许写成"已达标"。

### 归因也要开读数：第九改量的是"这句猜测有没有数"

第七、八改动的是"画多少"，第九改动的<b>一个字都没画</b>——它只把文档里一句猜测变成能红的读数。
来历是那句"一块瓦片内部的冷取数拆不开<b>（含那张源图首次解码）</b>"：括号从第四批改档那批起就挂着，
<b>从来没被量过</b>，只是那一族冷帧（40.3／41.9／45.4ms）最可疑的解释。

做法：`FileSourceResolver.Resolve` 里只夹 `Decode(path)` 那一次，毫秒与张数累加到 <c>[ThreadStatic]</c> 字段，
画布在 `PaintCore` 入口记起点、在帧结算时作差，报成 `取数里首次解码 X ms／N 张`。
三个形状是这格的设计约束：

- **线程内累计，不报进程累计**：分析与导入在别的线程解码，进程累计会把别人的钱算进这一帧——那正是"归因写错"的形状；
- **取数的子项，不是第七笔**：六笔加满整帧那个恒等式（`canvas/最慢帧分阶段要把整帧的账加满`）一点没动，
  新读数挂在括号里，所以拆多细都不会让账对不上；
- **反证要判三态**：`guard/解码归因不许跟着缓存命中涨` 判 首次 +1 张／命中缓存 +0／`Invalidate` 后必须重新算。
  只有前两条的话，一个"只在第一次 Resolve 计数"的实现也能全绿，而它报的数以后再也涨不上去。

**结论是否证**：电池里单张 64×400 PNG 首次解码 5.573ms（第二格；第一格 36.862ms 是 JIT 未暖）——量级足以顶红一帧；
真窗口 35% · HUD 开 · 三通道各 5 趟，<b>每一趟"最慢那帧"都报 0.0ms／0 张</b>，
因为 17 张源图在导入与分析阶段就解过、驻在 resolver 的 512MB LRU 里，滚动与缩放期间不再触发解码。
于是那几枚冷取数帧只能归给<b>瓦片渲染本身</b>（一块一块的 `RenderBand`）。
限流那句"只能在块与块之间停手、一块内部拆不开"<b>照旧成立</b>——这次改的是归因，不是把欠账删掉。

**通用一条**：文档里括号那句猜测要么量得出数，要么写清"没量过"。
挂着猜测当定论写了四批，比红一次贵；开完读数以后，"下一批再红"就直接报得出是谁花的。

**这一族判据共 2 格**：正 1（`canvas/取数那一笔要能报出首次解码占了多少`）＋反 1（`guard/解码归因不许跟着缓存命中涨`）。
第九改不省一毫秒，它省的是"下一轮再去猜这笔钱是谁花的"。

**同一批还红了一枚常驻反证，红的是它自己的量法**：`guard/分阶段只报前三段时这一帧的账加不满` 的第四项要比较
"开着叠层"与"关着叠层"两侧的<b>叠层</b>——两侧都是<b>减出来的残差</b>，真实差值一毫秒上下，单帧抖动就有 ±0.3ms，
于是那一批读到 开着 1.24 → 关着 1.57，报成"叠层不随绘制内容动"。随后连跑三批各 213／0 ⇒
<b>不是恒常不跟随，是单帧样本不够</b>。现在两侧各画五帧取平均再比，<b>比较仍是严格小于</b>、阈值一个字没动。
**通用一条（与上面那条像素恒等式并列）：残差型的比较不许拿单帧当两侧**——真窗口的 P95／最慢帧按"5 趟 × 合并池"报，
是同一个 estimator 问题；把判据放宽成"允许 ±0.5ms"才是拿容差把牙磨平，本轮没做那一步。

**第十改把同一把尺用在读数层自己身上**：第八改之后，读数层那一笔比叠层里任何一段都大，可它里面只有一列"描边"。
劈成两半以后形状就清楚了——<b>边界两笔</b>（永远要画：画布边界＋视口范围）与<b>命中区四笔</b>（只有选中缝才画：
整条带／蓝线上下容差／带首尾把手）。真窗口五趟一致：命中区 3.0~4.7ms > 边界 2.0~3.3ms，每笔约 0.15ms，
残差 0.0（残差为 0 才算这一笔拆到底了——第五改定的那条恒等式规矩在这里照用）。
**为什么本批不动画法**：再往下省只有三条路——虚线改实线、给命中框也加 10Hz 闸门、小缩放档不画两个把手——
三条改的都是调试层<b>在屏上长什么样</b>，而这一层的用途就是"让人一眼核对命中区到底在哪"
（需求四第 4／5／6 步全靠它）。这一类取舍要眼睛签字，不由实现方替读者定；
本批把数写清楚，画法一字未动——这就是红线那句"不许删功能换性能"在这一档停住的地方。

### 第十一、十二改：贴图那一笔拆到"转换／重采样"，然后把转换的实现换掉

**第十一改是纯归因**（加读数，不改一像素）。"贴图"那一笔在真窗口读到过 50.5ms 与 12~14ms，
可它里面混着两件<b>修法相反</b>的事：`RgbaImage → GDI 位图` 的首次转换（一块约 1MB，一次性）与
每帧必做的重采样（缩放档决定它多贵）。原本准备做的修法是"冷的那一帧走便宜档、静止那一帧补回高质量"——
复用滚轮那套机制；但如果 12ms 里 10ms 是转换，便宜档就是在省没有的那部分。
于是按第九改（取数里首次解码）同一个形状加一个<b>子项</b>：`_msBlitConvert` ＋ 块数，
分阶段那一行报 `贴图里首次转换 X.Xms／Y 块`，六笔加满整帧的恒等式因此<b>照旧不动</b>。
反证那一格不跟正判据共用"冷帧 >0、热帧 =0"这两条，而是<b>另找一个出处</b>对账：
子项块数必须等于产品自己的进程累计 `TileBitmapConversionsForTest` 在这一帧的增量。
为什么必须这样：一个"每块画出去的瓦片都记一笔"的实现，冷帧、热帧两态都能满足正判据那两条，
却会在滚进半缓存的一屏时把"换了 1 块"报成"换了 9 块"——下一轮就照这个数决定要不要分摊转换。
**这一族第五次验证了同一句话：判据要能被假象满足时，反证得换个独立的量去扎。**

现量结果把计划推翻了：真窗口逐趟最慢帧 贴图 12.4／5.2／12.2／14.1／13.1ms 里首次转换
12.4／1.7／9.6／10.8／13.1ms ⇒ <b>那一笔几乎全是转换</b>，重采样只占 0~3ms。便宜档那一改因此<b>没做</b>。

**第十二改动的是实现**，落在 `FileSourceResolver.ToBitmap`——<b>显示层专用</b>的那一支
（瓦片位图、缩略图、两处叠层位图），导出通路一张都不经过它，所以红线三不受影响；
`GdiplusJpegEncoder` 里另有一份同样写法，那一支在导出通路上，本批<b>没碰</b>（碰它得另开一批连字节核对一起走）。
两处：① 每次调用先 `new byte[stride×height]`（512×512＝1MB，直接进大对象堆）→ 改成按行缓冲（int[]＋byte[] 各 2KB）
逐行 `Marshal.Copy` 进锁定的位图内存——搬运总字节数没变，变的是<b>每块不再压 1MB 托管分配</b>
（这条有前账：回收的钱落在"它发生时正在被计时的那一段"里，带标记的帧曾把贴图顶到 62.1／68.3ms）；
② 换序从每像素 4 字节读写改成一次 32 位读、移位或、写（`MemoryMarshal.Cast<byte,uint>` 把一行当像素数组看）。
两个约束值得记：`Marshal.Copy` 只收 `byte[]`（不收 `int[]`），所以中间必须过一道 `Buffer.BlockCopy`——
要是为了少一次 memcpy 直接写 `Span<byte>` 到指针上，就得开 `unsafe`，而这一层的取舍是"可读、可核、不上 unsafe"。
判据两对：动像素的用<b>字节</b>钉（`canvas/首次转换出来的 BGRA 必须与独立复算逐字节相同` ＋
`guard/红蓝换序写反必须被逐字节判据抓到`——反证拿"复算自己写反"这一族摊开：同一把尺两头量，
错的期望必须散、对的必须整幅一致，否则"两份字节相等"能靠两份一起错来满足）；
动分配的用<b>分配</b>钉（`canvas/首次转换的分配量必须按行走而不是整块` ＋
`guard/分配量那把尺必须能量出整块写法`，实测 4232B/次 vs 1048600B/次，共用一个限值常量）。
**耗时一条都没进判据**——机器相关的数只做证据、不做闸门，这条从第五改起就是这一族的规矩。

### 第十三改：投进窗口的鼠标移动会被系统合并——能被两种形状满足的读数不能当证据

`--gui` 那批"拖动帧"是 `PostMessage` 投出来的。Windows 对**队列里还没被取走**的 `WM_MOUSEMOVE`
只做一件事：**合并成最后一条**。工装原来每 20 条泵一次消息循环，于是 100 条里真到达控件的常常只剩
"退回按下点"那一条——**它量的不是途中帧，是"按下＋松手"两帧**，而那两帧恰好是整批里最便宜的。
现在改成一条一条送（每投一条都等到控件计数涨了再投下一条），并把"送到几条"印成读数、
另加一道<b>只作用于工装自己</b>的门（限值 0 条没送到）；产品阈值一条没动。

这一改留下的一般教训比修的那处更值钱，两条：

1. **先问这个读数能不能被"手势没发生"满足**。新加的每趟读数印的是
   <c>重叠 120→120 · 设备位移 (0,0) · 对齐没变</c>，而拖动形状本来就是"先下去再回来、末点等于按下点"，
   ⇒ 净位移 0 时<b>这两种形状给出同一行字</b>。它因此不能当"拖动发生了"的证据；
   真正分开两者的是<b>帧数</b>（同命令行、产品未动：每趟 5~7 帧 → 81~86 帧）。
   这是本族"判据能被假象满足"的又一次前例，与第十二改那条"两份字节相等可以靠两份一起错来满足"同型。
2. **工装的输入注入自己会造手势**。`PostMessage` 按下时物理光标其实停在别处，
   Windows 给窗口设 capture 时会<b>补发一条物理光标位置的移动</b>——上一批那条"第 1 趟重叠 120→1071"
   （≈333 设备像素）就是它，真人做不出来。修法是把<b>起点站</b>显式送一条移动，让补发那条落在按下点上。
   另注：`MouseRelease` <b>不会</b>合成移动，所以松手点必须等于最后一条移动点，否则最后一腿丢在半路。

进程内同形状的来回拖补了两格：`align/来回拖同一趟（净位移 0）在小缩放档与固定后一段下也一字不改`
（参数、画布高、撤销记录三头都不许动）＋反证 `guard/来回拖那一格必须真进了对齐手势（正向对照在反证里）`
（把末点留在远处，量到 120→149）——**没有对照那一格，"参数没变"可以靠"手势压根没进对齐状态"来满足**。

### 第十四改：给读数层加读数，先被"每帧额外分配"那一格抓住

第十三改只答到"最慢那帧里读数层占 33.5ms"，再往下就是这一节的账。两件事值得单独记，因为它们都不是"性能"本身：

1. **累计出口不能直接当帧账用**。第十改那批开出来的 `HudBorderOutlineMs`／`HudHitsOutlineMs`／`HudBlitMs`…
   全是<b>进程累计</b>（工装自己一趟一次作差，报"这一趟"）。要做<b>本帧</b>的账，做法是在 `OnPaint` 入口
   记一次累计快照当基线、结算时作差——注意这跟"把累计抄进本帧"是两种实现，读数却都在动，
   所以配套的反证钉的是<b>计数</b>而不是毫秒：`guard/读数层那把帧尺分得清本帧增量与进程累计`
   要求"单帧面板重建 ≤ 1 次、而进程累计 ≥ 1 次"（重建点在画法里只有一处，一帧不可能重建两次）。
2. **共用的那一笔不许算进本段恒等式**。`EnsureHudRects` 是色块层与读数层<b>共用</b>的同一份设备矩形缓存
   （需求六"两层同一份画法"），先跑的那次在叠层里 ⇒ 它的毫秒落在读数层那两个计时点<b>之外</b>。
   把它写进"各笔加起来 ≤ 读数层整段"，恒等式天生为负——这不是拆得不够细，是<b>归属</b>不同，
   只能单列并注明"这一笔不属于本段"。同型的前例是第十一、十二改的"子项不进六笔恒等式"。
3. **加读数本身是有代价的**，而这一族的代价早就有常驻判据看着：第一次跑就红了
   `canvas/读数层每帧的额外堆分配：不新建 Brush、Font，也不重排文本`（限值 512B／帧，读到 1121B）。
   红得正是它该红的样子。修法是把每帧要写的账本做成 `readonly record struct`（值类型，不进堆），
   人读的那句文案改成<b>按需格式化</b>——工装一趟读一次，帧里不拼串。
   通用一条：<b>"我只是加了一行读数"在这一族里不算无罪</b>；判据没红不代表代价不存在，
   红了的判据也不该被"读数层就是要开销"糊过去。

量出来的形状（同命令行两批，都留着）：HUD 开档最慢那帧的读数层里<b>最大那路是面板重画</b>
（复用 4.1~5.0ms，其中"排那 14 行字" 2.7~3.1ms、清底 0.0~0.1ms），描边 1.0~1.5ms；
而第十改那句"命中区那半最贵"量的是<b>一趟累计</b>。两句各答各的问题，谁也不许划掉谁。

### 面板尺寸是量出来的，不是"行数 × 一个常量"估的

F8 那块文字面板是一张缓存位图：先按"这段读数该有多大"算出长宽，再 `TextRenderer.DrawText` 把字画进去。
**长宽算小了，GDI 不会把字挪出来，而是整行裁掉**——需求四那十二步在真窗口走查时看到的就是这个形状：
选中一条缝时该有 14 行，屏上只有前 10 行，帧耗时／HUD 单独耗时／分阶段／Paint 计数四行整行不见了。

病因是两条路不同源：高度是 `private const int HudLineHeight = 16`——
那是 96 DPI 下 Consolas 9pt 的行距。产品进程当时声明 `Application.SetHighDpiMode(PerMonitorV2)`
（第五十五改⑥ 起改 `SystemAware`，见 docs/精度红线.md 的偏差账——但 DPI 相关的尺寸账
在"主屏就是那档高 DPI"的场景下两档口径一致），
150% 屏上位图里的字每行 21~24 像素，于是框比字短。现在两头都从**同一支探针**量：

```csharp
Size need = TextRenderer.MeasureText(g, text, Theme.MonoFont);   // 含换行、含全角，一次量出宽高
int h = need.Height + 6;                                          // 高：量出来的整块
int w = 桶化(need.Width + 10);                                    // 宽：仍按 32px 分档，为了复用缓冲区
```

**宽度那头是同一族的第二个缺陷，改完这次复看才被抓到**：它当时走的是
"最长行的**字符数** × `MeasureHudCharWidth()`"，而那支探针量的是 `"MMMMMMMMMM"` 的**西文**单字宽——
读数里全是中日韩全角字（同一 DPI 下实测全角 14 像素 = 西文 7 像素的 2 倍），于是含全角字那行被系统性估窄，
真窗口 150% 上「分阶段 …（其中重新分配缓冲区 0 次）」只剩前半句。
证据不是看截图猜的：屏上那半行 ×「复制诊断信息」落到剪贴板的同源全文（50 个字符、27 个全角）
× 电池量出的真实占位 546 像素，三段对出来的。
现在宽高共用同一次 `HudTextExtent(text)`，估算那条路只留在 `HudWidthsForTest` 里给反证用
（`HudCharWidth` 如今只被这一条路引用——留着它是为了让反证能量出"旧写法差多少"，不是留一条还在生效的估算）。

**为什么电池 186 格全绿还留着这个缺陷**——这是本节最该记住的一条：Checks 进程没声明 DPI 感知，
它跑在 96 DPI，那里量到的行距只有 14 像素，写死的 16 反而宽裕 ⇒ 判据在那台环境里**恒真**。
所以这一族以后按两条记：正面判据 `canvas/F8 面板的背景框必须装得下它自己那些读数`（产品通路，
量"框 ≥ 文字真实占位"，两个方向都判），反证 `guard/面板行高若退回写死的 16 像素则在高分屏下切掉最后几行`
（把旧写法放到 288 DPI 下重算，要求它装不下，同时把"96 DPI 下旧写法本来就装得下"写成断言钉住）。
反证那一格刻意不走 `TextRenderer.MeasureText`：实测 `Bitmap.SetResolution(288,288)` 改不动 GDI 排出来的字高
（两档都量到 196）——**排版只认进程 DPI，进程不改，环境就模拟不了**；于是那一格改走
`Font.GetHeight(Graphics)` 这条纯算术的路，它跟着 `Graphics.DpiY` 走，才量得出"DPI 一变字就得变大"。
同一条纪律也写在精度红线 §3。

宽度那一处还多留了一条**更通用的教训**（它跟 DPI 无关，下一轮最容易再犯）：
正面判据当时只量「选中一条缝」那一档，而那一档旧算法只差 2 像素（579 vs 581），
被「宽度向上取到 32 的整数倍」那一步（→608）抹平 ⇒ 分档／取整／容差这类**故意留的余量**会藏住小差值，
所以反证要比的是**分档之后的框**（`HudWidthsForTest` 交回的就是它），不是裸估算。
而我把第二档加进正面判据的第一版，两档拿回来的是**同一段文本**——面板重建有 10Hz 闸门，
工装没等过闸门就读，"两档各核一遍"静悄悄退化成"同一档核两遍"。
⇒ 凡是"多跑几档形状"的判据，必须自带一条"这几档确实不同"的夹具自证（这里量的是
选中档不含「没选中拼缝」那句、没选中档含且行数更少），否则加档等于没加。

还有一条**量法上的机制事实**（是量出来的，不是推的）：字装不进框时，GDI 把它**裁掉**而不是画到框外——
把角标的框故意做窄一半，框内墨点从 2014 掉到 918，而框外始终是 0。
所以"框外面没有墨"根本证不了"字都在"；这一族判据一律比**墨数**：
按产品的算法算出框画一遍，再给一块大到装得下任何写法的画布画一遍，两个墨数必须一字不差
（角标三句：2014=2014、1162=1162、1269=1269；面板：21097=21097）。
画字用的 flags 也因此做成常量交出去（`BadgeFlags`、`HudPanelFlags`）——量的路与画的路必须同源。

### 读数层那一段再拆四层：7.9ms 里八成是一笔虚线

两档分开之后还剩一个问题：`HUD 单独耗时` 是一个总数，段里究竟贵在哪一层还是说不清，
而"贵在哪"这种话以前只能靠散文猜（精度红线那条"归因句要么有差分读数、要么不写"就是为此立的）。
所以控件里给这一段加了四笔各自独立的累计计时，`--gui` 每趟打成一行「读数层拆账」：

- `HudGeometryRebuildMs`：叠层几何换算。拖动预览那几帧走的是**绕过缓存**那条分支
  （临时布局的落位来自还没写进参数的覆盖值，签名看不出来），所以一帧要换算两遍——色块层一遍、读数层一遍；
- `HudTextBuildMs`：拼那段读数字符串（现量 14 行；每个 100ms 窗口一次，不管最后重不重画）；
- `HudOutlineMs`：那几笔虚线／实线描边；
- `HudBlitMs`：把面板位图贴到屏上那一次。

面板重建还再拆两条路各记一次毫秒（`HudPanelAllocRebuildMs` / `HudPanelReuseRebuildMs`），
并把"分配过几张"与"重建过几次"分成两个计数（`HudPanelAllocations` / `HudPanelRebuilds`）——
合成一个数就分不清"重画字贵"与"每次都新分配一张缓冲区贵"这两种形状。

短拖动 17 帧一趟读到的拆账：**描边 7.2ms/帧**、面板重画 3.3ms/次（摊到帧约 1.3ms）、
拼文本 0.15、几何换算 0.10、贴图 0.08ms/帧，而整段是 7.9ms ⇒ **八成多在那几笔描边上**。
出处是画布边界那条灰虚线：那个矩形在设备坐标里有上万像素高（成品 41532 行、35% 缩放也是
14537 像素），而**虚线的相位沿整条路径量**，屏幕裁剪不会让 GDI+ 跳过看不见的那几万像素——
于是每帧沿几万画素长的路径排一遍虚线，只为画出其中一屏的框。

改法是描边先与可见区求交再下笔（`VisiblePart`：可见区各边外扩半个笔宽 +1，
免得压在边界上那条线的半个笔宽一起被裁掉）。**代价写在注释里而不是藏起来**：路径变短之后
虚线相位会平移，那条灰框还是那条灰框、格子错开几像素；屏上看不出"裁与不裁"，
所以这件事只能由计数钉——`canvas/超出屏幕那几笔描边必须先裁到可见区 裁过才算数`，反证
`guard/描边若不裁到可见区则虚线路径代价翻红`（内存里同一条虚线笔两种画法各画 10 次，
判的是**比值**：整条 30000 高 vs 裁到可见区实测 30.9 倍——绝对毫秒会随机器负载假红，比值不会）。

改完之后读数层整段从均 7.9ms 降到 **2.2ms/帧（长拖动）／2.5ms（短拖动）**（文档定稿前在最终
构建上复量的一批是 2.3ms/帧、整帧 P95 28.9ms）；
开着读数层那两批的合并 P95 由改前的 36.4 / 40.2ms 变成 29.4 与 28.6ms ⇒ `P95 ≤ 33ms` 回到线内。
`单帧 ≤ 50ms` 仍会偶发红（改后短拖动这批一帧 51.6ms，其中读数层只占 8.3ms、画布部分 43.2ms）——
**消掉的是"开读数层就把 P95 顶过线"，不是"单帧偶发"**，这两句话分开写。

同一批拆账顺手把另一件事量清了，方向与预期相反：面板重画时"新分配一张缓冲区"与"复用同一张"
两条路的实测单价是 **4.0ms 与 3.3ms ⇒ 一次只省 0.6ms**，而一趟短拖动只有第一帧要走分配，
摊到帧上不到 0.03ms。所以"尺寸没变就复用那张 608×230（= 559,424 字节，过了 85KB 大对象门槛）
缓冲区"这条只记作**去掉一笔确定的大对象投放**，**不记成上面那 5.7ms/帧 的出处**——
把它写成性能优化就是散文。面板宽度按 32px 分档也是同一件事的另一半：不分档时最长行随数字位数抖，
宽度每次都变、复用永远命中不了。

### 第十五改：复用那条路改成按行增量重画——省下了行数，没省下毫秒

第十四改的逐帧拆账把最慢那帧最大的一笔指认到"面板重画里的排字"（每次 2.7~3.1ms），
而需求三第 5 条点名的正是"不要每帧绘制那 11 行文字"。所以下手的是：复用那张缓冲区时
不再把整段 14 行重新排版，而是先逐行比，**从第一条变了的行往下**连着重排（`PaintHudPanel` 里那条新路）。
三个形状要写清楚，因为这一改的教训比它的收益值钱：

**一、"省行数"与"省毫秒"是两件事。** 真窗口新增那行 `面板两条重画路` 报的是行级 21~33 次／整块 0 次、
每次只重排 **8.2~10.7 行**——行数确实少了（拖动中"命中类型／屏上矩形／重叠带"那几行也在变，
所以第一条变化行常在中间而不是最底下）。可每次复用的代价 5 趟是 4.3／4.4／3.9／5.4／4.5ms，
与上一批整块重排的 4.1~5.0ms 落在同一个带里，每次排字 2.8~3.1ms 也与上一批的 2.7~3.1ms 同数
（同机两批、阈值一条没动）。⇒ **排字那 3ms 不在"排几行"上，而在 GDI 每次排字的固定开销上**：
一条路上调用次数从 1 次变成 9 次，两头正好抵消。要真想省这一笔，得改的是"少排一次"
（比如把最常变的那几行留到屏上直接画、不进面板），不是"少排几行"。

**二、像素不许变，只能由字节判。** 这条新路的成立条件是它与整块那条路画出**一模一样**的像素
（判据 `canvas/面板走行级增量重画必须与整块重画逐字节相同`，反证 `guard/行级重画错开一行必须被逐字节判据抓到`）。
第一版写的是"只重排变了的那几行"＋用 `FillRectangle` 清那几条行带，当场量出 **218832 个字节不同**：
面板位图是 `Format32bppPArgb`，半透明底色用**填充**会与底下已有像素再做一次混合，整张 alpha 全变。
改成 `SetClip`（只允许那一条带以下被写）＋ `Clear`（**替换**像素）并要求从第一条变化行往下连着排之后，
同一把尺量到 0 个字节不同。"只画中间那一行"也不行——整块那条路是 GDI 自上而下排版，
某行的抗锯齿落点与它上面排过什么有关，跳着画就对不上。

**三、新路必须自己把那两笔账交出来。** 第十四改把面板重画拆成**清底**与**排字**两笔，
那两笔计时焊在 `PaintHudPanelInto` 里；新路绕开了它，于是真窗口第一次读到
"复用 7.9ms，其中清底 0.0／排字 0.0"——钱从有名字的桶搬进了没名字的桶，
而第十四改那条恒等式（"两笔子项加起来 ≤ 总额"）**天生挡不住**：0 + 0 永远满足它。
补的是两条判据（`canvas/行级那条重画路必须自己交得出清底与排字两笔` ＋
`guard/两笔面板计时只许跟着真重画涨整块那条路也一样`，后者换一个独立出处：整块那一路＋关掉读数层那一档），
并把两笔计时接进行级那条路。**通用一条：一边的不等式挡不住"尺没接上"，接账型判据必须两头都钉。**

还有一条口径订正：面板读数的**行数**是 14（选中一条缝）／7（没选中），
此前注释与三份文档写的"21 行"是把 150% 那档的**行距 21 像素**抄成了行数。
行级那条路靠一个算术闸活着（`行距 × 行数 + 6 == 面板高`，行距用两行探针量出来除二，量不出整除就报 0 把整条路关掉），
而 `--gui` 跑在没声明 DPI 感知的 Checks 进程里 ⇒ **本批只验过 96 DPI 那一档（行距 14）**，
150% 那一档没重跑，这一条挂在缺口里（要真开产品进程看屏，归人工那一族）。

**补：第十六改把这一路的调用次数收回 1 次，才真的省到单价。**
"省行数不省毫秒"这个形状分不开两种解释（每次调用有固定开销 / 少排几行本来就不值钱），
所以做了一笔一次性探针（同机、只做证据不做闸门，跑完就删）：同一张 608×202 的 PArgb 缓冲区上

| 画法 | 每次 |
| --- | --- |
| 整块 14 行，一次 `DrawText` | 4.88ms |
| 下面 6 行，一次 `DrawText` | 3.61ms |
| 逐行 6 次 `DrawText` | 3.95ms |
| 逐行 14 次 `DrawText` | 8.53ms |
| `Clear` 整张 | 0.015ms |
| `SetClip` + `ResetClip` | 0.0002ms |

⇒ 清底与裁剪都免费，钱在**每次调用**上：第十五改那条"逐行"的路把 1 次变成 9 次，正好把少排那几行的钱吃回去。
改法是同一条带（第一条变化行往下）拼成一个字符串、**一次多行调用**——落位仍由那道 clip 管住。
真窗口同一命令行 5 趟现量：每次复用 3.55／3.90／3.90／3.62／3.62ms，对上一批的 4.27／4.37／3.92／5.37／4.52ms
（**五趟全部落在下带**，每次排字 ~2.8→~2.0ms），字节判据照旧 0 个字节不同。
整帧分位<b>没跟着动</b>（本批池 P95 29.2ms；四批 41.2／28.8／25.9／29.2 全留着）：
重建一趟只有 23~40 帧，摊到 85~142 帧的池上分不出来，所以这句话只记账在"面板那一路的单价"上。
判据这边**没加格**，加的是一枚落在调用参数上的断言：合并成一次调用之后，
原来那枚按行数累加的 `HudPanelLinesRepainted` 是代码自己按 `lines.Length - first` 加的，
拿它断"只重排了那几行"是**自证**；于是产品交出 `HudPanelLastRepaintTopForTest`（那一条带的上沿），
`canvas/面板走行级增量重画必须与整块重画逐字节相同` 断它必须等于"第一条变化行 × 行距"。

### `--gui` 的口径：逐趟判，报最差那一趟

同一形状连跑 N 趟（验收固定 5），每趟单独记读数，**每条阈值按"趟趟都得过"判、报最差那趟**；
分位数另外把各趟样本合并成一个池子（单趟只有 5–6 帧，逐趟算 P95 站不住）。
每趟还打印三块归因料：GC gen0/gen2 增量、墙钟 vs 进程 CPU（所有线程）vs
UI 线程真正在画的时长（拖动帧求和）、松手收尾那一帧单独的耗时与清缓存次数。开着读数层时还多打两块：面板重建拆成"分配新缓冲区／复用同一张"两条路各多少次多少毫秒，以及「读数层拆账」那四项（几何换算／拼文本／描边／贴图，都是进程累计）。
需求五那句"不要把偶发环境抢占误判成代码稳定流畅"要靠第二块读——
`Process.TotalProcessorTime` 是**所有线程**的合计，会大于墙钟（后台分析与导出都算进去），
所以判断"这一趟慢在算还是慢在被抢"要看的是"UI 线程画了多少"，不是 CPU 总量。

一拖的**长度**由 `--moves` 决定（验收固定 100）。本轮把同一形状拉到 400 次移动、关/开各按需求五
那 5 趟量了一遍，补的正是文档原先写着"长时间连续拖动没量过"的那个形状：关着 97 帧合并 P95 28.2ms、
最慢 37.7ms ⇒ 九条全过；开着两批合并 P95 36.4 / 40.2ms ⇒ `P95 ≤ 33ms` 两批都红，而 `单帧 ≤ 50ms`
两批都过（最慢 47.7 / 43.8ms）。分档读数把两件事分开说清了：红的大头在画布"取数"那一段（那一帧
分阶段读到 取数 43.6ms，且样本带 GC 标记），而**读数层自己的代价随拖动变长从 6.3–6.5ms 升到
7.8–8.8ms**——带每帧都在动 ⇒ 叠层几何换算重算更频繁，这一笔是它自己的真实涨幅，不遮（全部读数
记在 README「诚实缺口」与精度红线 §三 第 5 条）。`每 100 次移动预览帧 ≤ 10` 那条始终按每 100 次折算，
所以调大 `--moves` 只是多取样，不会顺手把分母放大成放宽阈值。

还有一档 `--no-compare`：色块那一层（绿/黄/白/红箭头，`DrawAlignmentOverlay`）由画布画、**不在读数层的
计时段里**，而重影对比默认就开着，所以"开读数层多花多少钱"不能只靠 HUD 自己那一列说清。三个组合
（关+关、关+开、开+开）跑下来，整帧相减是读数层 6.3ms/帧、色块层 3.8ms/帧，与控件自计的 HUD 
均 8.0ms 同量级——两个口径互为对照。**这一档只为把归因量出来，不设阈值**（计时类的绝对数一设阈值
就会被机器负载假红，本项目只让计数与字节差进门禁）。

重影对比层自己也有两笔计时（`OverlayStrokeMs` / `OverlayFillMs`，`--gui` 每趟打一行「对比层拆账」，
两种档位都打，因为这一层是产品默认态）。实测：两张图的设备矩形描边 **0.13ms/帧**、重叠带填充＋描边
**0.50ms/帧**，而同 build 的两档相减是 2.7ms/帧 ⇒ **两笔只占四分之一，剩下约 2ms 在计时器读不到的地方**
（软件渲染下 GDI+ 是延迟提交：单笔调用只排队，钱在很多笔之后一次性付）。这一行既写了"量到了多少"
也写了"没量满多少"，就是为了下一轮别再拿 0.5ms 去解释 2.7ms。
机制上它反过来印证了读数层那一改：**同样有几万像素高的矩形，实线描边 0.13ms/帧、虚线描边 7.2ms/帧**
——贵的是"虚线沿整条路径排相位"，不是矩形大小、也不是 GDI 调用条数。所以那一层**不照抄**
"裁到可见区"这个修法：它没有虚线，被填充的带又本来就贴着视口。**同样的形状不等于同样的病因**。

### 色块为什么不包成位图（与需求三第 3 条的一处偏差）

那条建议列的是"颜色区域、文字面板、设备矩形等调试内容使用缓存位图"。现在的落实是：
**换算**全部缓存（一张 `HudRects` + 一个签名，`HudGeometryRebuilds` 计数），**文字面板**是缓存位图
（10Hz 闸门，`HudPanelRebuilds` 计数），而色块、蓝线、四块命中框仍每帧按缓存好的矩形 `FillRectangle`。
把后一类也包成一张整层位图，在**静止**帧上确实省几次填充调用，但在**拖动**帧上签名每帧都变
（视口原点/带矩形/切点都在动），等于每帧重建一张整层位图 + 每帧一次整层 alpha 合成——
比直接填充更贵，而拖动帧正是用户手感唯一在意的那一档。这条偏差写在这里、也写在 README 的
第十四轮一节里，判据量的是它要达到的目的（不重新换算、不重排文本、不新建画笔）与那两个分开的耗时数。

### 读自己正在写的日志：`FileShare.ReadWrite`

`DiagnosticLog` 是"一个开着的写句柄 + 批量刷"（第十一轮为了去掉每行开一次文件的开销）。
于是 `File.ReadAllText(日志)` 会抛 IOException：ReadAllText 用 `FileShare.Read` 打开，
等于声明"别人不许再写"，而那个"别人"正是自己进程里那支 `StreamWriter`。
导出会话改走 `DiagnosticLog.ReadSessionLog()`（`FileShare.ReadWrite`）。
这条不是查资料查出来的，是 `ui/导出当前交互会话：导出的文件必须含缓冲里最后几行`
第一次跑就红出来的——那格先证明那条缓冲行**此刻不在盘上**，再证明导出后的文件里**有它**，
两头都量，中间那句"先 Flush"才不是白判。

### 第四十三改：三个"唯一出口"——手势符号、界面刷新、内容居中

用户一次报了七条现场问题，其中四条的修法都落在同一件事上：**这件事过去有好几个写入口，每个只写自己那一半。**

**① 手势符号只有一个出处（第 1、2 条）。** 约定是 `ViewportState.PanByDevice(d)` ⇒ `TopLeft -= round(d/Zoom)`，
所以**正的 deviceDelta = 往回看**：往上滚 == 按 ↑ == 往回看，拖动跟手（自然反向）。
病根是 `ApplyWheel` 在入参上多写了一个负号，而 `PanByDevice` 自己已经是那个符号，两处各写一次就是两份会各自漂移的真相
（日志那一行 `canvas.pan.end` 的 `device_delta=` 还在字符串里又抄了一遍负号，一并改成同一个变量）。
触控板双指滚动在 Windows 上走的是**同一条** `WM_MOUSEWHEEL`（向下为负 delta），所以一处改完两路一起正——
这也是为什么这一条不需要为触控板单开一条通路。

**② 界面刷新只有一个闸（第 6 条）。** `BeginUiBatch`/`EndUiBatch` 按**深度**计数，所以可嵌套：
导入末尾会串起 `AnalyzeAll`，提前放闸会把半成品那一屏刷出来。批次里 `RefreshChrome` 只记一笔"欠着"
（`_uiBatchQueued`），放闸时统一刷；`EnsureSeams`/`Touch`/居中也都留在批次内，于是导入一整批只刷一次屏。
放闸落在 `finally`：循环里抛异常时唯一的出口就是它。

**③ 内容居中只有一个出口（第 7 条）。** `ViewportState.RecentreIfFits(content)`：**装得下的那一轴居中
（原点为负 = 两侧留白相等），装不下的那一轴保持用户此刻的位置。** 不是两轴一律居中——长截图纵向几十万行，
用户可能正看着第 8 万行，把他拽回中间或顶部都是丢工作；横向那条窄内容则必须永远跟着窗口居中，
这正是"无论窗口多大都得保持居中"。"装得下"当场判（`content.Width * Zoom <= DeviceSize.Width`），
不靠"居中原点是不是 0"反推：内容刚好铺满那一轴时居中原点也是 0，两种情形数值相同、语义相反。
`FitWidth`/`FitWhole` 改成设完缩放比就调它（原来一个写死 `TopLeft.X = 0`、一个写死 `IntPoint.Zero`，
就是"每次都左对齐"的出处）。画布那一头的出口是 `StitchCanvasControl.FollowContentCentre()`，三个时机调它：
导入结束、分析写回（写回改掉各段重叠量 ⇒ 画布总高变）、窗口／侧栏尺寸变化。
**尺寸变化挂在 `MainForm` 的 `_canvas.Resize` 上，而不是画布自己的 `OnResize`**：
画布一改尺寸就自己摆正的话，每个拿画布尺寸当夹具的判据起点都会跟着漂。

**④ 画法只有一个写入出口（第 5 条）。** "重叠对比画法"是三态（关／重影／差异标红），过去有三条写入路，
其中面板那条**只开画布的差异层、只把「对比」按钮的勾抹掉，却从不关画布上那层重影**（另一条路倒是两样都关，
两半不对称），而面板整块重建时又把两枚勾选框按写死的 `true`/`false` 起，把用户已经改出来的画法冲回默认——
用户看到的"按钮说没开、画布还在画，得再点一下才对上"就是这么来的。
现在收成 `MainForm.SetOverlapView(ghost, difference)`：一次写四处（画布两个开关 + 上方两枚按钮 + 面板两枚勾选框），
"两档同时开"在这个出口里**根本写不出来**。面板命令经 `ApplyOverlapCommand` 翻译（开某档 ⇒ 那档赢；
关某档 ⇒ 只撤自己、另一档维持现状）；面板回填走 `ToolPanel.SyncOverlapChecks`，里面压住 `CheckedChanged`
（**程序设 `Checked` 与用户点它走的是同一个事件**，不拦就绕成回路；`ToolStripButton.Checked` 反倒不触发 Click，
两类别按同一套直觉处理）；面板那两枚勾选框的初始值改成读跨重建留下的 `_ghostWanted`/`_diffWanted` 而不是常量。

**⑤ 删掉重复入口时不许把能力一起删掉（第 3 条）。** 顶栏那枚「添加图片」删了，左侧面板那枚留着
（`模拟UI需求.md` §3.1 首屏线框点的就是它），菜单「添加图片…」/`Ctrl+O`/拖文件进窗口三个出口不动。
画布空态那句提示原来写"点左上角「添加图片」"，跟着改成"点左侧"——**指错方向的提示比没有提示更坏**。
判据 `ui/添加图片在界面上只有一枚按钮` 走真实控件树（含 `ToolStrip` 里的项）数标题正好等于「添加图片」的按钮，
**总数与归属分开钉**：只数总数会放过"把左侧那枚删了、顶栏那枚留着"这种反着删的形状，只判归属会放过"两枚都在左侧"；
同一格还钉住菜单那句必须还在（它带省略号，与按钮标题不是同一个字面量，恰好能分开量）。

### 第四十五改：缝线自己会报状态，退编辑多一个出口

**① 缝线颜色＝匹配结论，线正中一枚方框＝结论的图章。** `DrawSeams` 按 `Seam.Status` 三档映射：
成功（`AutoPassed`/`ManualConfirmed`）蓝线＋勾框；有问题（`NeedsReview`/`ManualPending`）橙线＋警告框；
没结论（`Pending`/`Analyzing`）灰线＋空框——**不画勾也不画警告，免得把"没算"说成"算坏了"**。
线与方框任何缩放档都画（方框就是状态图章，收掉它就回到"看不见哪条有问题"）；缩小档收掉的只剩
带文字的状态标签盒子。六支状态笔与三枚底色刷全部静态；警告图章 `DrawWarnGlyph` 画几何
（三角框＋一竖一点），不引字体不引 emoji，任何 DPI 下不挤盒、不变豆腐块。
方框矩形与命中测试共用 `AdjustHandleRect`，点它照旧进微调模式（重叠带薄到几行时那是唯一入口）。
这一层只动显示：命中区、取数、导出一个字节都不变（红线三）。

**② 退编辑有两个出口，单击那一个带三道闸——作用域经用户裁定。** `Esc` 之外，空白处单击也退编辑
（`MouseRelease` 的平移分支）：没拖出 4px 阈值（平移中途松手不许把人踢回浏览态）、
按下时没命中任何缝／带／方框（点在线上那是"选这条"）、此刻确实在编辑态（浏览态单击空白保持无操作）。
退就退干净：退微调档＋取消选中，与 ✓ 和 Esc 同一口径，并留 `canvas.edit.exit reason=blank_click` 一条日志。

**这一条与第四十一改的"微调档里点带外＝点选上方／下方那张图"撞在同一下单击上**，两者只能留一个：
点蓝线那一下产品会顺手进微调档（`MousePress` 里 `Kind == CutLine ⇒ SetAdjustMode(true)`），
于是用户原话那条流程（点线条→什么都不做→点空白）落到的是选侧那一支，走不到平移分支的退编辑。
交用户裁定，用户选**保留选侧**。所以退编辑的作用域是"选着缝但没进微调档"那一档
（左侧列表点选、或 `Esc` 退档之后就是这一档）；微调档里退编辑仍走 `Esc`、✓（再点一次线上那枚方框）。
结构上这件事记在两处：`MousePress` 的选侧那一支优先级不变，`MouseRelease` 的三道闸第二条
（"按下时没命中任何缝"）顺带管住 `Shift+左键`——那一支在命中测试之前就转成平移，
`_seamUnderCursor` 还是上一次点线留下的旧值，少了这一条，`Shift` 按一下空白也会退编辑。
判据：`canvas/点过线条再点空白是选侧别不是退编辑`（裁定）、
`guard/带 Shift 的空白单击仍是平移不退编辑`（第二条闸的探针可红处）。

**③ 状态色那格的取数口径：数像素要挖掉同色的邻件。** 方框与线共用同一批状态色，
"这一帧有没有警告色像素"这种数法会被方框替线答到（变异探针当场量到：只改线的笔，判据不红）。
现在 `CountStatusPixels` 用产品自己的 `AdjustHandleDeviceRect` 把每条缝的方框挖掉，只数线自己的像素；
夹具也跟着放宽到 400 像素——默认 80 像素宽的内容缩到 30% 只有 24 像素，正好被 24 像素宽的方框盖满。

第 4 条（滑快了出现灰线）的落点与三格"没画到"的判据写在 `docs/精度红线.md` §二 末尾，这里只记结构上的那一笔：
缩小档那道闸加在 `DrawSeams` 里，**只影响显示层**，命中区、取数、合成、导出一条路都没碰。

### 第四十六改：菜单字体钉两头、灰线是边缘渗色、确认即退编辑、死按键出声、最小缩放档不糊墙

用户一次报回四条现场缺陷，四条的落点分属四个层：**渲染器／贴图参数／命令通路／欠帧策略**，
没有一条是算法或阈值问题。

**① 菜单字体：item.Font 与渲染器 TextFont 两头都要钉。** 四个顶级项本来就同构造器 new 出来，
屏上却一大三小——`ToolStripProfessionalRenderer` 在视觉样式可用时拿<b>系统菜单字体</b>画顶级项。
落点两处：`MainForm` 里四枚显式 `Font = Theme.UiFontSmall`；`DarkToolStripRenderer.OnRenderItemText`
里 `e.TextFont = e.Item.Font` 交回去。只修一头，另一头会把缺陷留着（变异探针两头各红一次）。

**② 缩放灰线：GDI+ 双线性往位图边缘外取样。** 边缘外按透明黑算，瓦片最外一圈设备像素混进透明、
深色画布底透上来＝瓦片交界与内容外缘一条灰带，混多少随缩放小数相位变（所以"只在某些档出现"）。
落点是 `DrawTiles` 贴图那一笔传 `ImageAttributes` 的 `WrapMode.TileFlipXY`（边缘镜像取样）。
**只动预览贴图参数**：导出走 `CanvasComposer` 的整数 blit，不经过这条路（红线三）。

**③ 确认拼缝＝退编辑：一条命令通路，两个出口各量各的。** 面板「确认拼缝」写完确认后发
`CanvasCommand("exit-edit")`，`MainForm.OnToolCommand` 接到走与 ✓／Esc 同一个组合
（`TryHandleEscape`：退微调档＋取消选中）。判据分两段：真按钮那一下在<b>不挂窗体</b>的面板上量
（窗体没 Show 过时 WinForms 的 CanSelect 把 PerformClick 挡成空转），主窗口路由那一段用面板事件原样触发量。

**④ 死按键出声：三处静默早退都改成"说一句＋记一条"。** `NudgeSelected` 的三处早退
（重叠 0 行／滑到重叠尽头／位移档到头）发 `NudgeNotice`（状态栏）＋写 `seam.slide.keyboard_silent`。
用户报的偶发死按键根因<b>未结案</b>：他按的时候这条日志还不存在；本轮只做到再发生一定出声，
结案条件记在 `docs/精度红线.md` §三 末条。

**⑤ 最小缩放档的棋盘格墙：欠帧策略加档位闸＋两处取交。** 瓦片网格在画布坐标里，10% 档一屏几百块，
预算限流后欠帧那一段把整屏画成棋盘格（用户图4 那一墙）。落点三笔：欠帧棋盘格加档位闸
（一块瓦片在屏上 < 64 设备像素时不画墙，欠帧留画布底色、后续帧补齐）；欠帧棋盘格矩形与内容设备矩形取交
（边缘瓦片整块矩形比内容宽）；瓦片遍历与内容矩形取交（欠帧块数因此等于内容内瓦片数，判据按这个数钉）。
看得清的档位照旧画棋盘格——"还没取到"的诚实标记只在它读得懂的档位画，删与留两头各一枚判据。

### 第四十四改：匹配专用取数、批次闸住三条订阅、缝线档位口径回修

用户复看第四十三改报回三条，三条的落点都在"取数／刷新的通路选错了"，而不是算法或阈值。

**① 匹配专用取数 `CanvasComposer.RenderMatchInput`（"全部重新分析整批归零"的病根）。**
裁切档里 `placed.Rect` 是蓝线切完之后真正进像素的那一块，被切掉的那几行——两张截图唯一公共的内容——
已经不在任何布局矩形里，`RenderBand` 永远取不到它们。首分析时重叠还是 0、蓝线还在带顶，碰巧没事；
一旦参数里有了重叠与切点，再拿切完的两块去匹配，两侧一行公共内容都没有，匹配器只能回答"重叠 0"，
于是"全部重新分析"把整批成果抹成堆叠。修法是给匹配开一条专用取数：取 `FullSourceRect`
（裁边之后、切重叠之前）的完整内容，再叠启用的清理补丁——与首分析看到的像素同一份，重分析因此幂等。
它**不进成品合成通路**（导出／瓦片仍走 `RenderBand`），也与 `RenderDebugSource` 那条调试出口不同
（那条不叠补丁、只服务屏幕比较视图）。两个调用点（`MainForm.TryAnalyzeSnapshot`、
`SeamAnalyzer.AnalyzeOne`）一起换，判据钉"在同一份参数上分析两次结论必须一字不差"。

**② 批次闸住三条直通订阅（导入闪烁的另一半）。** 第四十三改的界面批次只闸住了主窗口 `RefreshChrome`；
画布（`OnProjectChanged` 与视口 `Changed`）和左侧素材列表（`RefreshItems`）各自直通订阅 `Project.Changed`，
导入循环里那下 `PumpUi()` 把它们的 `Invalidate` 一张张泵上屏。现在 `BeginUiBatch`/`EndUiBatch`
在深度 0↔1 的边界同时挂起／释放这三家，挂起期间只记账、放闸时各补欠着的那一次。
量法上把"上屏帧"与"离屏取帧"分开：忙碌遮罩开工前拍现状走 `RenderFrameForTest`，用户看不见、不构成闪烁，
所以闪烁判据只读 `ScreenPaintsForTest`，`PaintCount` 保留旧口径给帧耗时那族读数用。

**③ 缝线档位口径回修（"分析结束后看不见蓝线"）。** 第四十三改把缩小档未选中缝整条不画，做过头了。
新口径：**线任何档位都画**，缩小档换成不透明 1 像素纯强调色实笔（半透明笔在浅色截图上混出来就是灰线），
只收掉把手与深灰底状态标签盒子；选中的缝任何档位带全套。仍然只动显示层。
判据那头是搬家不是消失：旧格改名改口径为"只画一条不透明实线"（笔数 == 缝数、收掉的盒子数 == 缝数、
命中区照旧点得中），另加一格逐像素反证钉"不透明"，100% 档那格原样保留证明不是"一律不画"。

### 第四十七改：布局"先量后摆"——写死的列宽与行高在别的 DPI 上必然重叠

用户报"导出界面很多元素都重叠了"。病根不在导出逻辑，在<b>布局是怎么算出来的</b>：
旧版每一列的横坐标是按 96 DPI 下某一种字体宽度估出来的常量（90／270／380／430……），
四行"摊开给人看"的读数还各写死一个 `Height`。150% DPI 上点字号渲染成 1.5 倍像素宽，
标签比预留的列宽出一截，尾巴被右边的控件盖住；警告文案一换行，写死的高度又压住下一行。

**关键判断：这不是"这次没调好"，是写死坐标这件事本身在别的 DPI／字体／语言下必然出错。**
所以修法不是把常量调大，而是让常量不存在：

| 旧写法 | 新写法 |
| --- | --- |
| 每列 x 是常量 | 每列宽＝`TextRenderer.MeasureText` 现量本列最宽那枚标签 |
| 每行 y 手工累加 | 整块装进一个 `FlowLayoutPanel`（TopDown + GrowAndShrink）自己叠行 |
| 读数行写死 `Height` | 一律 `AutoSize = true`，高度按换行现量 |
| 窗体 `ClientSize` 写死 | 宽＝最宽那一行的现量值，高由 `OnLayout` 按 `_body.Bottom` 收口（带变化闸防自激） |

DPI、字体、语言换任何一种，布局都跟着现量结果变——**重叠在结构上不可能再出现**。
判据因此量几何而不是看截图（`ui/导出对话框任何控件不许互相重叠也不许出界`）：
离屏构造（`CreateControl` + `PerformLayout`，不 `Show`）、递归取所有可见叶子控件的屏幕矩形、
两两不许有正面积交集且都必须落在窗体客户区内；夹具自证叶子数 ≥ 15。
截图对照只能证"这一台机器这一档 DPI 这一次看着还行"，几何判据证的是"结构上不可能重叠"。

这一课在第四十八改被直接复用：设置对话框与外观那一块从头就是"先量后摆"，
一个写死的坐标都没有（`ui/设置对话框任何控件不许互相重叠也不许出界` 用同一把尺子，两档各量一遍）。

### 第四十八改：外观档位——一根指针、一张翻译表、一个唯一出口

用户要「在设置中弄一个白天黑夜切换的以及是否跟随系统的按钮」。这句话落到实现上比看上去大：
在此之前本程序<b>没有任何设置界面</b>，也<b>没有任何跨启动的偏好存储</b>
（`RecentProjects` 那份只记最近打开过哪些项目，属另一件事）。所以是从零建四段通路，
而每一段都能"看起来做了、其实没接上"。

**① 颜色从字段变成指针。** 原来 `Theme` 的颜色是二十几个 `static readonly` 字段，进程一启动就定型。
现在颜色住在两个<b>不可变</b>的 `ThemePalette` 实例里，`Theme` 只留一批属性转发到 `_current`
（外加一张 `_remap` 翻译表）。换肤＝换指针＋广播一次，而不是逐个改写静态字段（那种写法迟早漏掉一枚）。
调用方一个字没变（还是 `Theme.Accent`），所以几百处引用不需要动。
`UsePalette` 对<b>同一套重复调用不广播</b>——跟随系统那枚轮询每 2 秒问一次注册表，
若每次都广播，整棵控件树会被白翻一遍、画布白重画一帧。

浅色档<b>不是把深色档反相</b>。反相出来有两个毛病：状态色在白底上不够对比，
以及"需检查"与"手动待确认"两枚本来靠明度区分的琥珀色会挤到同一档明度上再也分不开。
所以浅色档状态色重新挑过（全部压到白底 ≥ 4.5:1，两枚琥珀色拉开色相 20.3°）。
黑夜档除 `Danger` 外与改动前逐字相同——`Danger` 原值在面板底上只有 4.43:1，提到 4.73:1；
它只画左栏那个「缺」字角标，不进导出像素、也没有判据数它的像素，
而读数层那枚红箭头 `OverlayAlign` 保持原值（需求六逐字钉下来的合同色，两档同值）。

**② 换肤之后必须做的两件事**，都挂在 `Theme.Changed` 上，缺一件就会留下"换了一半"的界面：

- **控件树**：WinForms 的颜色是<b>构造期抄下来的值</b>，`BackColor = Theme.PanelBackground` 执行完
  控件里存的就是一枚具体 ARGB，此后 `Theme` 换了它也不知道。要么在每个构造点都改成"订阅变化再刷一次"
  （几十个文件、几百处，必漏），要么换肤时遍历一遍控件树统一翻译。选后者（`ThemeApplicator`）。
  为什么是"翻译"而不是"重新赋一遍标准色"：重新赋值得先知道每枚控件本来该是什么角色
  （面板底？列表底？输入框底？），那等于把几百处构造代码再抄一遍；翻译只需要一张
  "旧档 ARGB → 新档 ARGB"的表，认得的就换、认不得的原样留着，
  于是用户图片、透明色、以及故意写死的白字（选中行上的白字两档都压在强调蓝上）都不会被误伤。
  还单独走了一遍 `ToolStripItem`（顶栏「导出」那枚按钮不是 `Control`）与扁平按钮的
  `FlatAppearance` 三枚色（漏翻就会出现"浅色面板上还剩一圈深色边"）。
- **常驻画具**：`StitchCanvasControl` 与 `BusyOverlay` 里那二十几枚 `static readonly` 的 Pen/SolidBrush
  同样是抄下来的值，但它们各自订阅了 `Changed`，<b>就地把对象的 `Color` 改掉</b>——
  字段仍是 `readonly`、对象仍是同一枚，所以"画具提静态、不许每帧新建"那条红线一个字没动，
  每帧分配读数也不变。F8 面板是一张复用位图、颜色烤在里面，换肤要做的是
  "清掉比较基准让它走<b>复用</b>那条重画路"，不是重新分配一张（判据钉 `HudPanelAllocations` 不许涨）。

**③ 翻译表的幂等性是有前提的：两档颜色不许撞键。** 这一轮撞上<b>两枚</b>（都不是用户报的：
第一枚是构建前用 Python 复算整张表算出来的，第二枚是构建后判据红出来的）。
`ThemeApplicator` 的注释一开始把幂等当成天上掉的性质：
"翻完之后控件身上是新档的颜色，而表的键是旧档的颜色 ⇒ 再翻一遍什么都不会发生"。
这句只在<b>两档颜色集合互不相交</b>时成立。
<b>第一枚</b>：浅色档正文原本取 (28,28,30)，而它正是黑夜档的 `WindowBackground`——翻第二遍时
已经翻好的正文色被当成"旧档窗口底"再翻成 (243,243,245)，白底上的近白字，整段文字在屏上消失。
<b>第二枚</b>：浅色档面板底原本取<b>纯白</b>。产品里有八处把 `Color.White` <b>写死</b>当字色
（左栏选中行两枚、素材列表选中行两枚、菜单渲染器选中项、外观那枚选中按钮、预览条 chip、画布把手图章两枚），
设计上"两档都压在强调蓝上、永远不换"。翻译表的规矩是"认得才翻"，纯白一旦进了调色板它就"认得"了：
从白天翻回黑夜时那些白字被当成"旧档面板底"翻成 (38,38,40)，选中行上出现深灰字。
<b>角色冲突没法在翻译表里表达</b>（同一枚白色，当底色要翻、当字色不能翻），所以只能在源头消除歧义。
而"翻第二遍"在产品里<b>每次都走</b>：设置窗口开着换肤时，主窗口的 `ApplyEverywhere` 翻一遍所有开着的窗口
（含设置窗口）、对话框自己的订阅再翻一遍同一棵树、外观那一块还有第三遍。
两枚都修在调色板那头（正文改成 (26,26,28)、面板底改成 (252,252,253)；差两三档灰度肉眼分不出，
对比度反而更高——正文在面板底上从 12.69 升到 16.95），翻译层一个字没改；
前提由两格反证逐枚钉住：`guard/翻译表的目标色不许自己又是旧档的键`（两个方向各查一张表）与
`guard/纯白不许进调色板否则写死的白字会被翻掉`（两档各 19 枚具名色逐个查，再双向查一次翻译结果），
两格的尺子都先自证再上产品。

顺带一个不那么显眼的顺序讲究：深色档里 `Passed` 与 `OverlayBefore` 是同一个 ARGB、
`ManualPending` 与 `OverlayAfter` 也是。翻译表按键 overwrite（后写的赢），
所以 `Enumerate()` 把读数层那三枚合同色排在语义色<b>之前</b>——
反过来排就会出现"换到白天之后绿勾亮得刺眼"这种查半天的毛病。

**④ 跟随系统：零依赖那条路是读注册表。** 系统深浅色没有托管 API 直接给
（`Application.SetColorMode` 是 .NET 9 才有的），而 `DwmSetWindowAttribute` /
`ShouldAppsUseDarkMode` 都要 P/Invoke——本项目<b>产品内禁止 P/Invoke</b>。
Windows 把用户选的那一档写在
`HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize\AppsUseLightTheme`
（REG_DWORD，1=浅色），而 `Microsoft.Win32.Registry` 就在 .NET 的基础共享框架里，不引任何 NuGet。
不用 `SystemEvents.UserPreferenceChanged`（它常驻一条原生窗口线程，离屏工装里既不好收也不好判），
改由主窗口挂一枚 2 秒 `Timer` <b>只在"跟随系统"档开着时</b>问一次，外加窗口被激活时立刻再问一次
（用户从 Windows 设置切回来那一下不用等）。取数出口 `SystemTheme.Probe` 是可注入的 `Func<bool?>`，
于是这条通路能在不碰真注册表的离线工装里被量到。

**⑤ 档位、生效配色、写盘三件事只有一个出口。** `ThemeController` 是唯一写入点：
设置界面那三枚按钮、启动回读、跟随系统轮询三条路都汇到它。分散写就会出现
"界面说跟随、实际却是手动"这种两套真相（与本项目"重叠画法三个出口必须落在同一份状态上"同一课）。
`RefreshSystemReading()` 只在"跟随系统"档才换配色，但无论哪一档都把读数记下来
（设置界面要显示"系统当前：…"那一句）；<b>什么都没变就不广播</b>。
读不到就退回黑夜<b>并且说出来</b>：静默退回与"系统本来就是深色"在屏上一模一样，用户只会以为跟随坏了。
取消跟随时钉住的是<b>当前生效的那一档</b>，不是一律退回黑夜——
用户看着浅色界面取消跟随、结果界面跳回黑夜，那是他没要的那一下。

**⑥ 偏好落盘：纯文本一行，绝不进项目文件。** 存 `%APPDATA%\LongStitch\preferences.txt`，
内容是 `theme=dark|light|system` 加两行注释写明可以填哪几个词——本项目读者自认小白，
能打开记事本核对"我到底选了哪一档"比省几行解析代码值钱。认大小写、认中文写法、认连字符写法；
读坏了退回黑夜（枚举 0 档）<b>并且留一句说明</b>，写不进去同样出声但本次切换照样生效
（外观偏好是便利功能，不许因为它把启动搞崩）。
它<b>绝不进项目文件</b>（project.json / .lstickx）：那是跟着项目走、要能拷给同事的，
把界面习惯塞进去对方打开项目就会莫名其妙变色。隐私上这份文件只有档位名，不含像素、不含路径清单，
出错说明只写异常类型名不回显文件内容。

**⑦ 离屏电池永远从黑夜起步。** `ThemeController.Load()` <b>只在 `Program.cs` 里调</b>，
主窗口构造时不读偏好。否则工装那台进程会被开发者机器上的偏好文件影响，
几百条按深色底数像素的判据跟着"这台机器恰好选了白天"一起翻红——那不是产品的错。
判据那头每格都在沙箱里跑：偏好写临时目录、系统读数用注入的假探针、`finally` 里原样还回去。
<b>"写临时目录"这件事需要一枚产品侧的改道闸</b>：`AppPreferences.StoreOverride`（`string?`，null＝用真的
`StorePath`）。原因是界面上那三枚按钮调的是 `ThemeController.SetMode(mode)`——<b>不带路径</b>，
判据没有别的办法让它写到临时目录去。这一枚闸是<b>判据第一趟红出来才补的</b>：在那之前判据量临时文件
"写盘了没有"、产品却写了开发者真实那份 `%APPDATA%\LongStitch\preferences.txt`（两头都没错，错在缺闸）。
它是<b>测试专用接缝</b>，产品代码里一个字都没读它（产品进程里它恒为 null，真实用户看到的存储位置一个字都没变）。
<b>同一族的另一枚当时还漏着，已由第四十九改一起收口</b>：`RecentProjects` 也会写真 `recent.txt`
（一格更早的判据经产品保存项目，产品那头调 `RecentProjects.Add` 同样不带路径）——那一份按自己的类注释
是"我在哪些聊天截图上工作过"的清单，属隐私敏感。现在 `RecentProjects` 也有同形状的 `StoreOverride`，
而且<b>改道被提到工装进程入口</b>（`Checks/Program.Main` 一进来就在 `%TEMP%\LongStitch.Checks-<pid>\` 建沙箱、
把两个出口一起指进去，`finally` 里还回 null 并删目录）。提到入口而不是留在某一格的沙箱里，理由是<b>覆盖面</b>：
留在沙箱里只有那一格受保护，提到入口则 `--only`／`--gui`／`--stitch` 任何一条分流都漏不出去。
判据 `ui/离屏工装的两个存储出口都必须改道到沙箱` 钉路由（不量"真实那份有没有多一行"——那会把判据钉在环境上），
反证 `guard/改道判据的尺子必须能认出真实那份存储位置` 证明尺子不恒真；
尺子按<b>真实根 + 产品那两级子路径</b>做带尾分隔符的前缀比较，<b>不按"含不含 LongStitch 这个词"</b>
（沙箱目录名里也有 `LongStitch.Checks-`，按词判正反两枚会一起恒真）。

**⑧ 设置界面：即时生效，没有"确定/应用"。** 点白天／黑夜／跟随系统当场就换、当场就写盘，
只留「恢复默认（黑夜）」与「关闭」——少一枚"确定"就少一种"我明明点了怎么没变"的困惑，
关掉窗口也不会把选择回滚。外观那一块单独做成 `ThemeChooserPanel : Panel` 而不是直接写在对话框里，
是为了让判据能像量 `ToolPanel` 那样 new 一个出来<b>真点</b>（第四十六改已经实测过：
从没 `Show()` 的窗体上 `PerformClick` 是空转）。两枚档位按钮用 `Click` 而不是 `CheckedChanged` 订阅：
跟随档下某一枚可能<b>已经是选中态</b>（系统就是那一档），此时点它 `CheckedChanged` 不发，
用户看到的就是"点了没反应"——与第四十六改那枚死按键同一族。
`CheckBox` 没有 `PerformClick`，改 `.Checked` <b>就是</b>用户点下去那条通路。
预览条（`ThemePreviewStrip`）画的四种状态样本每枚旁边都有文字，且文字与产品自己的
`Theme.StatusText` 同源（`模拟UI需求.md` §1：不能只用颜色暗示质量）。

**与需求书的偏差**：`模拟UI需求.md` §1 写"预览背景采用**深色中性底**"、§6 写"**深色工作台**配中性灰侧栏"，
白天档与这两句直接冲突，由用户当轮原话裁定（他要的就是这个切换）。落法是把偏差收窄到最小：
<b>默认仍是黑夜档</b>（枚举 0 档，首次运行与读坏了都退回它），白天档要用户主动选；
§6 另外两句两档都遵守——图片永远保持原色（换肤只翻调色板里认得的那几枚，用户像素不在表里），
蓝色仍只用于选中与可交互的拼缝。另外<b>标题栏与系统的「打开／保存」框不跟着换肤</b>：
改它们要调 DWM 的窗口属性（P/Invoke），产品内禁止，所以设置界面里有一句原样说明。

**这一族判据共 14 格**（`ui/` 7、`guard/` 7），出处见 `checks/LongStitch.Checks/ThemeTests.cs`。

## 为什么不用 WPF / 为什么不用 GPU 加速渲染


WPF 的视觉树建立在 device-independent pixel（1/96 英寸）之上，坐标是浮点的。
"把某个源图像素放到某个屏幕像素"这件事在 125% 缩放下本身就要跟取整搏斗——
而本产品的核心承诺恰恰是这个对应关系不能错。WinForms 里画布控件的位图与整数平移完全由我们控制。

GPU 纹理常见上限 16384，而 5 万像素高的长图是本项目的主要场景。
任何"整张贴给 GPU"的方案都会在这里崩或静默降级，所以预览从一开始就是 CPU 瓦片。
