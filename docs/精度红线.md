# 精度红线

这份文档定义"一像素不出错"在本项目里**到底是什么意思、怎么被证明、以及哪些地方证明不了**。
改任何取数、合成、编码相关代码之前请先读它。

---

## 一、三条不变量

### 红线 1：几何只用整数

所有决定"像素去哪"的量——拼缝位移、裁切矩形、片段落点、导出尺寸——都是 `int`，
活在**源图像素坐标系**里。

浮点只允许出现在两个地方：
- 显示层把源像素换算成屏幕像素（`ViewportState`）；
- 用户主动选择缩小倍数时的盒式平均（`RowDownsampler`，且只接受**整数倍**）。

**为什么这么较真**：一旦坐标变成浮点，在 125%/150% DPI 缩放、或连续多次拖动之后，
会累积出肉眼看不见、但 `sha256` 一比就红的偏差。

这条不是靠自觉，而是靠类型：`RgbaImage` 与 `CanvasLayout` 的公开接口里
**没有任何接受 `float`/`double` 的方法**，想写错得先绕过类型系统。

`checks` 里的 `guard/逐步取整确实不同于整段取整` 是这条红线的"有牙齿"证明：
它量出 zoom=30% 时"每步取整"得 30px、"整段取整"得 33px，两者确实不同。
所以"拖动结束时才取整一次"这条实现约定不是同义反复，而是会真的影响结果的。

### 红线 2：预览与导出共享取数，但分离呈现

`CanvasComposer` 是**唯一**把参数变成像素的地方，它只做整数 blit。

- 导出：`ExportEngine` 按行带向它要像素，直接喂给编码器；
- 预览：`TileRenderer` 按 512×512 向它要像素，贴到屏幕上时才缩放。

红线要防的是"导出复用了带插值、带浮点坐标的显示路径"。共享一个纯整数合成器是安全的，
**共享一个缩放后的位图就是事故**。

### 红线 3：分块结果必须等于整块结果

长图必须分块处理（否则内存扛不住），但分块一旦与整块有任何细微差别，
用户看到的就是"预览没问题、导出的图接缝处多一行/少一行"，而且只在超长图上出现。

判据：`blit/分块 blit 与整块 blit 一致` 与 `export/分块导出与整块合成逐字节相同`。

## 二、怎么被证明

### 1. 字节级分片对比（不是整图对比）

导出结果的每一片，与**另一套独立实现**算出的同一切片做 `sha256` 比对。

为什么必须"分片"：整图哈希相同不代表每一段都对。分段导出本身就是"多段拼起来"的产物，
只有逐片比才抓得住"某一片被重复写了一次"。

为什么必须"独立实现"：如果用被测实现自己生成输入、再用被测实现读回来比较，
那只能证明"它和自己一致"，证不了"它对"。
所以 `Fixture.cs` 里自带一套**独立**的 PNG 写入实现（自己的 CRC32、自己的 zlib 封装），
并且借用系统 GDI+ 当第三方解码器交叉核对（`png/GDI+ 独立解码核对`）。

### 2. 坏输入必须响，不许静默通过

| 情况 | 期望行为 | 判据 |
| --- | --- | --- |
| PNG 数据被篡改 | CRC 校验失败并抛错 | `png/坏 CRC 必须被拒` |
| 16 位通道 PNG | 降位但**上报为有损** | `png/16 位降位必须上报为有损` |
| 带 ICC / gAMA | 不做色彩管理，并如实说明 | `PngFormatInfo.LossyNotes` |
| Adam7 隔行 | 第六轮起**支持解码**（七遍各自反滤波）；IDAT 字节数与七遍之和对不上必须拒绝并说清差在哪 | `png/Adam7 隔行解成与非隔行逐字节相同`（下面另有一行讲清"为什么各遍独立"） |
| PNG 带 `eXIf` 方向 | 两种端序都读出真值，坏块退回 1 | `png/eXIf 方向要从真 PNG 块里读出来`、`png/坏 eXIf 退回 1 且不抛` |
| 区域坐标写错（空交集） | 抛异常，不返回"空区域的合法哈希" | `RgbaImage.RegionSha256` |
| 行数不足 | 收尾抛错，不产出截断文件 | `png/行数不足时不留半成品` |
| 真机截图带 1–4 级像素噪声 | 判据用**结构差异**（偏差 >12 才计数），不许拿逐字节相同当判据 | `--stitch` 判据 1，噪声分布逐轮打印 |

| 清理检测"只问不改"的需求 | 【随同一功能下线】曾经要求在文档副本上跑检测（设置能还原、写进去的补丁还原不了）；现在 `--stitch` 的清理只剩滚动条，且它改不了几何 | 见 README「第四十改」 |
| 缩小导出的坐标系 | 计划里的 piece 是**输出坐标**，喂给合成器的必须是 输出×倍数 的**源坐标**；每片源起点恰好落在降采样分组边界上 | `export/缩小导出全链路逐字节对得上独立复算` + 守卫 `guard/缩小导出把输出坐标当源坐标必被抓到` |
| 拼缝命中测试 | 必须与绘制共用同一个 `CanvasToDevice` 换算（漏减 TopLeft 就会"看得见点不着"） | `ui/平移后拼缝命中与绘制位置一致` |
| 视口设备尺寸 | `SetDeviceSize` 必须接在控件 `OnResize`/`OnHandleCreated` 上，否则 VisibleCanvas 恒空、瓦片不画 | `ui/视口尺寸跟着控件客户区走` |

| 用户选"0=不分段" | 分段只由显式选择触发；查看器建议上限**只进提示文字**，不许拿它偷偷切文件 | `export/0=不分段必须兑现即使超出建议上限` |
| 源图缺失/被替换 | 导出**计划阶段**点名硬拦：`SourceMissing`、真实解析失败、尺寸与记录不符 | `export/缺失源图在计划阶段点名硬拦` |
| 后台分析写回 | 全量与单条同规则：轮次号 + Revision + 项目实例三重校验，旧轮次/已取消/已换项目的结果整批丢弃；有手动偏移的缝只刷新自动侧信息 | `layout/自动分析写回不盖手动显示状态`（竞态本身无自动化判据，列 NOT-RUN） |

| 打包容器里的原图 | **按字节拷贝**，不解码不重编码；打包不是第二个可能改动像素的地方 | `export/打包项目往返：原图字节进容器、换目录也能解码`（容器条目 vs 源文件 sha 同源比对） |

| 时间替换的作用范围 | 【随同一功能下线】曾经只许改框选区域内的像素（区域外改动数必须为 0） | 同上 |
| TIFF 条带布局 | 分块写出与整块写出必须产出同一字节序列；条带数据在文件里就是行主序 RGBA 原样 | `export/TIFF 分块写出与整块写出字节相同` |

| 蓝线被当成"图片移动线" | 【第四十一改换口径】这条红线**说的还是同一件事，但实现方向反过来了**：蓝线仍然是参照物、仍然拖不走，可"拖不走"不再靠"只改 `CutY`、其余全不动"兑现，而是靠 **O 与 Cut 一起动把画布行号对消掉**。旧的"拖它只改 `CutY`，总重叠/画布高/对齐/视口全部不动"那一句已经作废（它正是用户抱怨的"线条会跟着走、不适合人用"那个形状）；现在钉的是**蓝线的设备行号与画布行号**这一对读数 | `align/压着蓝线滑动下方那张图：蓝线的画布行号与视口都不动`、`align/在带里滑动下方那张图：带重算、蓝线画布行号不动、视口不动`、`align/滑动一张图时蓝线的屏幕行号一字不动`（三个缩放档 × 抓上/抓下两个方向各拖一趟，线不动而**必须有一张图真的动了**） |
| **第四十一改：把"线不动"实现成"什么都没动"** | 恒等式 `蓝线画布行号 = Rect1.Bottom − OverlapLength + CutY` 是唯一那一条：抓下方那张 ⇒ O 与 Cut **同减**（画布行号守恒）；抓上方那张 ⇒ 只动 O，画布行号被推走、由**视口补偿**顶回来。所以"抓上方那张"那一趟必须看得见 `ViewportChanged=True` 而 `line_device_moved=false`——只断言线不动，一个空实现也能绿 | `align/滑动两趟的日志各自齐备且互不覆盖`（同一族里两趟的 changed 标志正好相反，且第二趟的 `cutYBefore` 必须等于第一趟的 `cutYAfter`）+ `guard/来回拖那一格必须真进了对齐手势（正向对照在反证里）` |

### 3. 变异守卫（`guard/*`）

每写一条"能抓 bug 的断言"，就配一格故意注入缺陷、要求它必须变红。
守卫自己坏掉时会绿灯，这是验收体系最危险的失效模式。

注入缺陷只用**内存探针**，不改真实源文件——第九轮 `crop/` 组那三格就是三种形状：

- `guard/自动档蓝线被写到带外时修补回到自动结论那一格`：**绕过产品出口直接裸写核心字段**
  `seam.CutY = O + 500`（模拟将来某次重构里的一处直写），要求三处同时抓到——读出口夹回带尾、
  布局这本账标出「参数与落位不一致」（`CropsAppliedAsRequested=False`）、带高不受影响；
  随后 `NormalizeAlignment()` 把自动档的蓝线修补回自动结论那一格。
  这格守的是"每个出口都夹"这句话本身——少了它，那句红线只是文档里的一段话。
  （第十二轮之前这格是反射改 `_beforeCropBottom`/`_afterCropTop` 两个后备字段；那两个字段随着
  "只剩 `AlignmentOffset` + `CutY`"的重写一起消失了，判据随之搬家而不是删除。）
- `guard/异本标记不生效时被裁的行不进成品会空转`：同一处数法分别喂同本与异本，同本必须数到 1、
  异本必须数到 0。两边读成同一个数 ⇒ 标记形同虚设，"被裁的那几行不进成品"那几格就全成了空判据。
  这格守的是**样本**，不是代码——这类工装最容易悄悄退化的地方。
- `guard/位移档做出的同样去重量必被不相交判据抓到`：用竖拼 + `offsetY=140` 造出"看起来去掉 60 行"
  （高 340、总账也平），要求 `RectsDisjoint` 必须为假、两段高度之和仍为 400。
  这格证明"只看参数与总高"抓不住第九轮要消灭的那个形状，**不相交那一半判据不可替代**。
- `guard/撤销若只换文档不带显示快照则视口停在补偿位置`（第十四轮）：把"通用 Undo 只恢复
  `ProjectDocument`"这个**改造前的形状**在内存里复现（`ReplaceDocument(反序列化(基线), null)`），
  要求三段同时读到——参数与画布高**确实恢复了**、视口**确实没恢复**、现行通路撤销后回到
  **这一次手势自己的基准**（不是最初那一屏；拿第一次的期望值判第二次就是判据读反）。
  这格守的是正面判据 `align/固定后一段拖对齐后撤销：参数、画布高、视口、设备矩形一起恢复`
  不是空转：如果哪天有人把"带快照"简化成"只换文档"，正面那格必须能红出来。
- `guard/读数层若退回每帧排文本与重建位图则堆分配立刻翻红`（第十四轮）：正面判据是
  "开着读数层比关着每帧多分配 ≤512 字节"（实测 105）。这格把旧写法当场复现
  （每帧拼 11 行文本 + `MeasureText` + 新建 `Pen`/`SolidBrush` + 建一张位图重排文本），
  要求它每帧越过那条线数倍。**没有这格，512 这个数就是白写的**——退回旧写法可能仍然"绿"。
- `guard/隐私判据的探针：读数混进路径就必须被认出来`（第十四轮）：正面判据是两句"不包含"
  （读数里不许有路径、不许有像素块），而"不包含"最坏的失效方式是**谓词本身恒假**。
  这格喂四份脏样本（盘符 / UNC+`.png` / `LocalAppData` 目录名 / 64 位 base64）要求逐条命中，
  再拿两份干净读数做正向对照（不许误报）。隐私类判据以后一律按这个形状配反证。
- **判据的环境必须与产品的环境一致，否则它会恒真**（第十四轮末批，F8 面板切行那一课）。
  `guard/面板行高若退回写死的 16 像素则在高分屏下切掉最后几行` 守的正面判据是
  `canvas/F8 面板的背景框必须装得下它自己那些读数`。缺陷现场：产品进程声明 `PerMonitorV2`（150% 屏），
  面板位图里的字每行 21~24 像素，而框按每行 16 像素长 ⇒ 14 行读数只画得出前 10 行；
  **同一时间 186 格全绿**，因为 Checks 进程没声明 DPI 感知，它在 96 DPI 下量到的行距只有 14，
  那个写死的 16 反而宽裕。⇒ 这一格的反证不只钉"行高不许退回常量"，还**把"96 DPI 下旧写法并不出错"
  本身写成断言**——否则下一轮又会拿一次绿灯当"屏上没问题"的证据。
  同类形状以后一律这样处理：**凡是"量出来的东西跟环境（DPI／缩放档／字体）有关"的判据，
  反证必须能把那个环境挪动一档**（这一格走 `Font.GetHeight(Graphics)` 这条纯算术的路，
  因为实测 `Bitmap.SetResolution(288,288)` 改不动 `TextRenderer` 排出来的字高——
  GDI 排版只认进程 DPI，电池进程是无感知的，模拟不了）。
- **判据要覆盖的那一档形状，必须由产品真实会走到的那一档来定**（同一次复看的第二课，面板宽度）。
  上面那条把**行高**改成量之后，常驻判据 `canvas/F8 面板的背景框必须装得下它自己那些读数` 仍是绿的，
  而真窗口 150% 上「没选中拼缝」那一档第 6 行「分阶段 …（其中重新分配缓冲区 0 次）」只剩前半句：
  **宽度**那时还按「最长行字符数 × 西文单字宽」估，而读数里全是全角字（同一 DPI 下实测全角 14 = 西文 7 的 2 倍）。
  这一处 190 格全绿却活着，失效方式有两条，都要记下来：
  ① **判据只量了一档**（选中一条缝），那一档旧算法只差 2 像素（579 vs 581），
    被"宽度向上取到 32 的整数倍"那一步（→608）**抹平**——所以"分档／取整／容差"这类**故意留的余量**
    会把小差值的缺陷藏起来，反证要比的是**分档之后的框**，不是裸估算（这格就是这么改的）；
  ② 第一次把第二档加进判据时，**两档拿回来的是同一段文本**：面板重建有 10Hz 闸门，
    工装没等过闸门就读，于是"两档各核一遍"静悄悄退化成"同一档核两遍"。
    ⇒ **凡是"多跑几档形状"的判据，必须自带一条"这几档确实不同"的夹具自证**（这里量的是
    "选中档不含「没选中拼缝」那句、没选中档含且行数更少"），否则加档等于没加。
  反证：`guard/面板宽度若退回按字符数估则含全角字的行一定被截断`。
  顺带一条给人看的口径：屏上那 14 行只在"有下一帧且过了 10Hz 闸门"时才换，
  点列表选中一条缝后面板可能还写着"没选中拼缝"——那不是没选中，是那一帧没刷；权威读数走剪贴板与日志。
- **屏上读数必须跟着参数走**（第十一轮）。`ToolPanel.SeamId` 的 setter 在 Id 没变时早退，
  于是画布拖完一次切点，面板仍写着"刚选中那一刻"的数。现场就是用户那句"拖不动"：
  屏上「切 300」、参数其实已是 0 ⇒ 再往上一拖立刻顶到带边。
  判据 `ui/面板蓝线读数跟着画布拖动的结果走，不停在旧值` 量的是"屏上那格 == 参数里那个"，
  守卫 `guard/面板读数不跟修订号刷新则停在旧值` 反过来证明"刷新那一句是承重的"（不调就必须停在旧值）。
  **同类缺陷的形状**：任何"按 Id 相同就早退"的 setter，都必须另有一条按修订号判过期的刷新通路。
- **一次手势中途不许把视口推走**（第十一轮）。画布选中 → 主窗口同步列表高亮 →
  `SelectedIndexChanged` 反着回调 `SelectSeam(scrollIntoView: true)` → 刚按下去画面就跳。
  判据 `ui/画布点选拼缝不反向滚动视口` 在按下/拖动/松手三段各量一次 `Viewport.TopLeft`。
  双向通路（列表→画布、画布→列表）必须有旗子分开"用户点了列表"与"我在同步高亮"。
- **缓存失效粒度不许粗于变化粒度**（第十一轮）。切点移动只改带内像素，
  所以预览帧只许 `TileCache.DropRegion(带区)`；原先那句 `_renderRevision++` 等于每帧整块清空、
  把视口里所有瓦片从源图重 blit 一遍。这条"只丢带区"不是靠注释成立的：
  `crop/切点预览只改带内瓦片：带外逐字节相同` 把两版布局的带外瓦片逐块比过字节，
  并要求带内**必须**不同（异本标记），否则那格是恒真的空判据。
- **性能类修复的判据必须是计数，不是"感觉不卡"**（第十一轮）。
  `crop/100 次鼠标移动只换几帧预览：不整块清缓存、不逐帧写日志` 读三个数：
  预览帧数、`TileCache.FullInvalidations`、`DiagnosticLog.AppendRequests`；
  并配两条自证——"视口里真有瓦片可复用"与"带区瓦片真被重渲染过"，
  否则那个"整块清空 0 次"可能只是根本没画东西。
  日志计数读 `AppendRequests` 而不是数磁盘行：工装压根没开日志文件，数磁盘会恒得 0 而假绿。
- **命中区与显示区必须同一个出处、同一套换算**（第十一轮补的一条真凶）：
  30% 缩放下 60 宽的图在屏上只有 18 设备像素，判据原先按 1:1 那样点 X=30 就"点不到"——
  那不是产品错，是**判据自己没跟着缩放**。现在取"显示矩形的水平中心 + 带尾"，
  三档（0.3/0.5/1.0）各带一个非零视口原点，见 `align/30%·50%·100% 缩放下红框命中与显示同源，拖动折算仍按缩放`。
- **一条事实只许有一个写入口**（第十二轮，需求 §七 那条「不能让多个字段互相覆盖」当场抓出来的）。
  兼容旧项目留着的那对别名（`BeforeCropBottom`/`AfterCropTop`）都往 `CutY` 写，于是
  **JSON 里谁先出现谁说话**：`b=10` 把蓝线写成 50、随后 `t=10` 又把蓝线写成 10，落库的是顺序的产物。
  守卫 `guard/蓝线与对齐若共用一个字段则两条手势会互相顶掉` 把两条通路合成一个字段跑一遍，
  要求"拖蓝线那次重叠也跟着变"这件错事必须被读到；正面判据
  `align/旧项目文件的裁切字段按任意顺序到达都归一到同一组核心值`（DOM 重排那四个键、三种顺序各读一遍
  必须同数，另配"只读别名带矛盾值两趟都不改结论"与"删掉 `CutY`、只留 `AfterCropTop=45` 时蓝线真跟着走"
  两把对照——后者防的正是"三趟同数其实因为键根本没被读进来"）。
  产品侧只留 `AfterCropTop` 一个写入口，
  `BeforeCropBottom` 改纯派生。**形状同族**：任何"两个名字写同一个后备字段"的兼容层，
  都必须另外规定谁在读取时有最终解释权（这里交给 `NormalizeAlignment()` + 手动档旗子）。
- **两条手势要在日志里当场分得开**（第十二轮）。`seam.cut.*` 与 `seam.alignment.*` 由同一个
  `SeamEditTrace` 按 `AlignMode` 决定前缀，两族的 `cut_changed`/`alignment_changed` 与
  `canvasHeightBefore/After` 是否变化**恰好相反**——`align/滑动两趟的日志各自齐备且互不覆盖`
  就是拿这个相反关系当判据的。只有一条前缀（或两族字段互相抄）时，事后看日志根本分不清
  用户拖的是蓝线还是红箭头，那正是需求 §十一 要消灭的歧义。
- **会变高变矮的手势，失效粒度跟着变**（第十二轮）。蓝线只换内容来源 ⇒ 只丢带区那几块瓦片；
  对齐改的是重叠行数 ⇒ 带首以下**一直到画布底**的落位都可能挪，所以 `DropRegion([带首, 画布底])`。
  这仍然是局部丢弃，不是整块清空：`align/对齐拖动 100 次鼠标移动：不整块清缓存、只重画带顶往下且在视口内`
  读数 1 帧预览 / 整块清 0 次 / 重渲染 2 块（视口里总共就 2 块）/ 日志 5 行。
  注意判据取的是"视口内被重渲染的块数"而不是"被丢弃的块数"——丢弃范围超出屏幕是设计使然，
  不在屏幕上就不该花钱重画。
- **期望值本身钉错方向时，翻它必须连反证一起翻，并且要说清是谁判它错的**（第四十三改，用户第 1、2 条）。
  `canvas/普通滚轮只平移视口，不碰缩放与参数` 原来钉 `TopLeft == (0,-60)`，而同一格的注释写着
  "往下滚 = 往下看"——**意图是对的、断言抄错了符号，于是判据把错方向当成了合同**，产品改对它反而翻红。
  这一格允许改期望值，前提是：① 判定"这个行为错了"的人是**用户**，不是为了让判据变绿的实现者；
  ② 翻完必须**另开两格把方向钉死**，否则下一轮它还能再翻回去：
  `canvas/滚轮与方向键必须同侧：向上滚就是往回看`（拿用户从没抱怨过的方向键当参照物，
  两路的符号必须都非零且相等——只比符号会放过"滚轮一格挪一点点"）与
  `guard/滚轮方向两档各挪多少格必须说得出数`（一格 60、两格 120、上滚三格 −180）。
  ③ 第一版新格红过一次，红的是**工装自己的算术**（`↑` 那档的基准抄成了"两轮滚轮之前"的位置），
  改法是基准取"两轮之后"并把这句写进注释：方向没错，错的是量它的尺。
- **屏上"多出来的东西"要先量掉"该画的没画到"，才允许动显示层**（第四十三改，用户第 4 条：滑快了出现灰线）。
  "灰线"只有两种成因：**露出画布底色**（覆盖不全）或**多画了一条本来就存在的装饰**。
  前者配三格判据、各配一格反证，全绿才准往下走：
  `canvas/视口里每个内容像素都得被某块瓦片盖住`（问产品自己"这一帧贴了哪些块"——新开
  `CaptureTileRectsForTest`；判据不在工装里按取整规则重算一遍，复述出来的规则永远和自己一致）、
  `canvas/缩小浏览时内容区里不许出现整行底色`、
  `canvas/局部重画那一趟也不许留底色行`（真窗口滚动时系统发下来的更新区常常只是客户区的一块，
  必须新开 `RenderFrameForTest(bitmap, clip)` 才走得到这条分支，整块裁剪的量法永远走不到）。
  反证里 `guard/局部重画判据必须真的只画了那一块` **两头都钉**：裁剪区外必须与上一帧一字不差（证明没被重画）、
  裁剪区内必须真的变了（证明这一趟不是空跑）。
  还有一处**夹具形状**决定这三格以前绿得有没有意义：旧夹具内容只有 80×340，**纵向不足一块瓦片（512 行）**，
  "相邻两块瓦片之间会不会漏一行"这件事压根没被走到——判据绿着也不说明任何事（又是"建了不等于走了"）。
  现在换成 `TallRig(12)`（12 段 ⇒ 80×1740，一屏同时压着三四块瓦片）。
- **显示层的档位闸必须连"功能没被一起删掉"一起证**（同上一条的修法那半）。
  落点是每条未选中的缝都画一条 1 设备像素、alpha 150 的发丝线，再叠把手与深灰底的状态标签盒子：
  放大看是"缝在哪儿"的提示，缩到 30% 就只剩"图上莫名多出几条灰线"。修法是 `Viewport.Zoom < 1.0`
  时未选中的缝整条不画装饰，**只动显示层**（命中区、取数、合成、导出一个字节不变，红线 3）。
  判据（第四十五改再搬一次家后的现名 `canvas/缩小浏览时未选中的缝画状态色实线加一枚状态方框`）因此除了笔数还要**逐行扫命中区**，
  证明缝还点得中——0 命中就是把"找缝"这件事一起删了，那是删功能换绿灯；
  反证 `guard/放大到 100% 未选中的缝必须连状态标签一起画` 换同一份夹具到 1.0 档，必须画出笔来
  （只有前者会让"永不画"也拿绿）。
  **这一条要如实记账**：三格"没画到"的判据在**离屏 96 DPI**上量，修完的真机 150% DPI 观感**仍待眼判**；
  若灰线还在，下一轮该盯的是真窗口那条路（`BufferedGraphics` 复用、DWM 合成、DPI 换算），不是再改一次显示层。
- **合并刷新量的是次数，不是"还闪不闪"**（第四十三改，用户第 6 条）。
  逐张闪烁的病根不是解码，是**通知**：每追加一段都走一次 `Project.Mutate`（要进撤销栈，必须走），
  每次 `raise Changed` → `RefreshChrome` 把标题、撤销／重做、模式按钮、工具可用性、
  **拼缝列表（整条 `Items.Clear` 再重填）**、右侧面板、状态栏全刷一遍，循环里那下 `PumpUi()` 又真把它们泵上屏。
  批次按**深度**计数（可嵌套：导入末尾会串起 `AnalyzeAll`，提前放闸会把半成品那一屏刷出来），
  放闸落在 `finally`——循环里抛异常时唯一的出口就是它，留在正常路径上会让深度永久卡在 1、界面从此再也不刷新。
  `ui/导入一整批只刷一次屏` 数次数（真身 ≤ 2：放闸那次必然，另一次只可能来自分析写回，
  跑没跑完取决于判据这一趟泵没泵消息，所以写上限不写等号；现量 1）；
  `guard/逐张通知必须真的被批次接住` 把账算死：6 张 = 6 笔追加 + 1 笔重排 + 1 笔 `Touch` = **8 笔挂起**，
  少一笔是通知压根没发出来（拿"没刷"冒充"合并"），多一笔是放闸后又往批次里塞。
  **次数为 1 只是必要条件**：真机上"还闪不闪"仍要人看一眼。
- **算法要看的行，可能已经不在任何布局矩形里**（第四十四改，用户报"全部重新分析后一点都不拼合"）。
  裁切档里 `placed.Rect` 是蓝线切完之后真正进像素的那一块，被切掉的那几行正是两张截图唯一公共的内容——
  `RenderBand` 永远取不到它们。拿切完的两块去喂匹配器，两侧一行公共内容都没有，只能回答"重叠 0"：
  首分析碰巧没事（重叠还是 0、蓝线还在带顶），重分析就整批归零、段直接堆在一起。
  教训是：**任何"从布局取像素喂算法"的通路，都要先问算法要的那块内容在不在布局矩形里**；
  不在就得开一条专用取数（`CanvasComposer.RenderMatchInput` 取未裁重叠的 `FullSourceRect`），
  并且让"重跑一次必须得到同一个结论"成为常驻判据
  （`match/在已有重叠与切点上重新分析必须量回同一个重叠`）——幂等被打破时，用户看到的就是整批成果消失。
- **用户改口径时，判据要搬家，不许消失**（第四十四改，缝线那一族）。
  第四十三改把"缩小档未选中缝整条不画"钉成了合同；用户复看说"分析结束后一条缝都看不见，没法操作"。
  于是行为改回"线任何档位都画、只收掉灰的盒子"，判据跟着改名改口径
  （旧格「缩小浏览时未选中的缝不画发丝线」→ 第四十四改「只画一条不透明实线」→ 第四十五改现名 `canvas/缩小浏览时未选中的缝画状态色实线加一枚状态方框`），
  并补一格逐像素的反证（`guard/缩小档缝线颜色必须跟着匹配状态走`：把两种状态画成同一种颜色的喂法必须红）。
  旧名字在所有文档与产品注释里一并换掉——留着旧名就等于留一枚永远会红的钉子，删掉就等于判据消失。
- **闪烁的账要按"上屏帧"记，离屏取帧不算**（第四十四改）。
  `PaintCount` 过去把忙碌遮罩开工前拍现状那几帧（`RenderFrameForTest` 离屏取帧）也计进去，
  于是"导入期间画了几帧"这一格第一版量到 2——那两帧用户根本看不见。
  现在上屏帧与离屏取帧分开记（`ScreenPaintsForTest` vs `PaintCount`），闪烁判据只认前者；
  同时这一格不是空转门：导入循环自己每趟 `PumpUi()`，没闸住的话每一笔 `Invalidate` 都会变成一帧真画。
- **状态要画成"扫一眼全图就分得开"的颜色与图章，而不是只给选中那条看**（第四十五改）。
  过去缝的状态只写在选中那条缝旁边的文字标签里：100 条缝、76 条需检查时，用户得逐条点过去才知道哪条要管。
  现在缝线颜色＝匹配结论（成功蓝／有问题橙／没结论灰），线正中一枚方框＝结论的图章（勾／警告／空框），
  任何缩放档都画；缩小档收掉的只剩带文字的状态标签盒子。三个细节是红线级别的：
  ① **没结论不许画成有问题**——`Pending`/`Analyzing` 画灰线空框，把"没算"说成"算坏了"是界面在骗人；
  ② 图章是画出来的几何（三角框＋一竖一点），不引字体不引 emoji，任何 DPI 下不挤盒、不变豆腐块；
  ③ 判据逐像素核颜色时必须带反向对照：把全部缝改回"没结论"，两种状态色必须一枚不剩，
  否则扫到的像素可能来自界面别处碰巧同色，那两个 ">0" 就是假绿。
- **退编辑的出口不许只有一个键，但"单击退编辑"必须三条件缺一不可**（第四十五改）。
  用户原话："点击了线条但是没有做任何操作，那么我点击画布的空白处应该能退出编辑，而不是只能按 esc。"
  落点是 `MouseRelease` 的平移分支加三个条件：没拖出阈值（平移中途松手不许把人踢回浏览态）、
  按下时没命中任何缝／带／方框（点在线上那是"选这条"，不是"退编辑"）、此刻确实在编辑态。
  反证钉的是能喂绿它的实现："单击一律退编辑"会让点缝线也退编辑、选缝这条路断掉——
  所以另有一格从浏览态单击缝线，必须进编辑。
  **作用域经用户当场裁定**：点蓝线那一下产品会顺手进「微调模式」，而微调模式下点带外线外一律算
  "点选上方／下方那张图"（第四十一改为了不用瞄准薄到几行的重叠带而加的）——它与"点空白退编辑"
  是同一下单击，只能留一个。用户选**保留选侧**，于是退编辑只在"选着缝但没进微调档"那一档生效
  （列表点选、或 Esc 退档之后），微调档里退编辑仍走 Esc 与 ✓。这一处裁定不是实现细节，
  它写在 `canvas/点过线条再点空白是选侧别不是退编辑` 里：那一格量的是"选中与微调档都不许丢、
  而且那一下真把侧别选上了"，谁哪天把选侧那一支关掉，这一格就红。
- **像素级判据要挖掉与被量件同色的邻件，否则邻件会替它答到**（第四十五改）。
  "缝线颜色跟着状态走"第一版只数"这一帧有没有强调色／警告色像素"，而线正中那枚状态方框
  用的是同一批颜色——把线的笔换回单一颜色、方框照旧画，判据照样绿。变异探针当场把这件事量出来了：
  那条探针（只改线的笔）第一版<b>没红</b>。修法是把每条缝的方框矩形从扫描里挖掉，只数线自己的像素
  （现量：强调色 95 枚、警告色 95 枚），探针随后就红了。方框矩形走产品自己的
  `AdjustHandleDeviceRect`，判据不把 24×18 抄一份——抄了的话产品改尺寸判据照旧绿。
  连带一课：夹具尺寸要跟着判据的取数口径走。默认夹具内容只有 80 像素宽，缩到 30% 是 24 像素，
  正好被 24 像素宽的方框盖满——挖掉方框就一枚都不剩，那一格会变成假红。所以那一格把夹具放宽到 400 像素。
- **判据要走用户原话那条流程，不能用等价的程序化起步代替**（第四十五改）。
  同一件事"选中一条缝"，调 `SelectSeam(...)` 与用鼠标点蓝线是两条路：后者会顺手进微调档、
  还会把"光标下那条缝"这个内部值写成非空。第一版判据用 `SelectSeam` 起步，绿得很好看，
  而用户手上那条路（点线条→点空白）压根走不到退编辑那一支。改成照原话用鼠标点线之后，
  两枚新格第一趟就红，红出来的正是上面那条要交用户裁定的冲突。
  同一条纪律也管着反证：`guard/带 Shift 的空白单击仍是平移不退编辑` 之所以存在，是因为
  Shift+左键那一支在命中测试之前就转成平移，"光标下那条缝"仍是上一次点线留下的旧值——
  少了"按下时没命中任何缝"这个条件，Shift 按一下空白也会退编辑，而用 `SelectSeam` 起步的判据看不见这件事。
- **缩放档的灰线要往"取样取到图外"上查，不是往"画错了颜色"上查**（第四十六改）。
  用户报"放大缩小画布出现灰色线条"，第一反应是笔或混合模式；真因是 GDI+ `DrawImage` 双线性重采样
  会往位图<b>边缘外</b>取样，而边缘外按透明黑算——每块瓦片最外一圈设备像素被混进透明、
  深色画布底透上来，瓦片交界与内容外缘就是一条灰带。它"只在某些缩放档出现"是因为混多少取决于
  缩放的小数相位。修法是给贴图传 `WrapMode.TileFlipXY`（边缘镜像取样）。
  判据写法因此是<b>逐缩放档扫</b>（10%→200% 七档）＋<b>单色夹具</b>：内容设备矩形里每枚像素都必须
  等于那一种纯色，渗色、漏底、棋盘格、瓦片缝任何一种都会让某一枚不等——单色把"等于某色"变成精确判据，
  真截图夹具只能给容差，容差就会把 1~2 阶的渗色放过去。
- **显示层的"诚实标记"也有档位：删与留两头都要钉**（第四十六改）。
  欠帧棋盘格的本意是"这块还没取到，别以为内容丢了"。但瓦片网格在<b>画布</b>坐标里，缩到 10% 时
  一屏要取几百块，预算一限流就是<b>整屏宽、半屏高的一墙棋盘格</b>——用户图4 报的"缩小到最小渲染异常"
  就是这一墙。修法不是删标记，而是加一道档位闸：一块瓦片在屏上小于 64 设备像素时不画这一墙
  （欠帧只持续不到一秒，留画布底色比糊一整墙好读），看得清的档位照旧画。
  判据两头各一枚：最小档先<b>造出欠帧</b>（瓦片预算压到几乎为零）再量"整张只许有底色与纯色两种像素、
  欠帧块数等于内容内瓦片数减一"；50% 档同样造欠帧，量"内容里必须有棋盘格、内容外一枚不许有"。
  只钉一头的话，"把标记整条删掉"或"把墙糊回来"两种坏实现各能喂绿一头。
  同一段还量出第二处取交：边缘瓦片的<b>整块矩形</b>比内容宽，欠帧循环不取交就会把棋盘格铺到内容外
  （现量 424 枚）——瓦片遍历与欠帧棋盘格都不许越出内容矩形。
- **判据必须先造出它要量的那个状态，否则量到的绿是空绿**（第四十六改）。
  本批三处都是探针先抓出来的空绿：① 最小缩放档那一格第一版夹具太小（400×300），10% 档只有一块瓦片、
  根本不会欠帧——把"欠帧不画墙"删掉它照样绿；改成 1200×6000 并把预算压到 0.0001ms 才真欠 17 块。
  ② 「确认拼缝」那一格第一版在真窗体上 `PerformClick`：窗体从没 `Show()` 过时 WinForms 的 CanSelect
  会把点击挡成<b>空转</b>（方法一次都不进），红出来的原因却是"产品没写确认"——夹具按了一枚按不动的按钮。
  改成不挂窗体的面板量真按钮、真窗体只量路由那一段之后，两半才各自量到自己的东西。
  ③ 夹具自证要量"状态真的在场"：欠帧格断言 `TilesDeferredLastFrameForTest > 0` 与"内容里真有洞"，
  按钮格断言 `Enabled` 与"点击后 Revision 前进"——少了这些，"没画墙""没写确认"都可能是没发生。
- **"按了没反应"必须出声：静默早退是用户报"偶发失灵"的温床**（第四十六改）。
  用户报"有时候按上下键一点反应都没有，换一条缝又好了"。翻他当时的诊断日志：那几下<b>一条记录都没有</b>——
  产品在三处早退（重叠 0 行、滑到重叠尽头、位移档到头）里一声不吭，于是既没有反馈也没有证据。
  修法是三处早退都发 `NudgeNotice`（状态栏一句，说清是"重叠是 0 行"还是"这个方向到头"）＋
  写 `seam.slide.keyboard_silent` 日志。判据量两头：重叠 0 的夹具按方向键必须出声且切点一字不动；
  活夹具反方向按必须真动且一声不吭（否则"每次都喊"会把真移动也报成死按键）。
  诚实账：用户那一次到底是哪一族<b>仍未结案</b>——他按的时候这条日志还不存在；本轮只做到"再发生一定出声"。
- **菜单字体要钉两头：item.Font 与渲染器交出去的 TextFont**（第四十六改）。
  四个顶级项在代码里是同一构造器 new 出来的，屏上却一大三小——专业渲染器在视觉样式可用时拿
  <b>系统菜单字体</b>画顶级项，item.Font 只在那一枚走过 owner-draw 路径的项上生效。
  所以判据量两头：四枚字体四元组（族名／字号／单位／字形）互比＋与 UiFontSmall 比；再把渲染器真调一次
  （递进一枚 20pt 的错字体，出来必须被改回 item.Font）。只钉 item.Font 的话，删掉渲染器那一行判据照旧绿。
- **写死的列宽与行高在别的 DPI 上必然重叠：布局要"先量后摆"，判据量几何不看截图**（第四十七改）。
  用户报"导出界面很多元素都重叠了"。旧版每一列的横坐标是按 96 DPI 下某一种字体宽度估出来的
  （90／270／380／430……），四行读数还各写死一个 `Height`；150% DPI 上点字号渲染成 1.5 倍像素宽，
  标签尾就被右边的控件盖住，警告文案一换行又压住下一行。<b>这不是"这次没调好"，是写死坐标这件事本身
  在别的 DPI／字体／语言下必然出错</b>——所以修法不是把数字调大，而是让数字不存在：
  横坐标一律由 `TextRenderer.MeasureText` 现量（本列最宽那枚标签决定列宽），纵向交给自动容器叠行，
  窗体宽高由 `OnLayout` 按内容收口。
  判据因此量<b>几何</b>而不是看截图：离屏构造（`CreateControl` + `PerformLayout`，不 `Show`）、
  递归取所有可见叶子控件的屏幕矩形、两两不许有正面积交集且都必须落在客户区内。
  截图对照只能证"这一台机器这一档 DPI 这一次看着还行"，几何判据证的是"结构上不可能重叠"。
  夹具自证叶子数 ≥ 15——枚举空了的话"没有重叠"就是空话（这与第四十六改那条"先造出要量的状态"同一课）。
- **"翻译表"这类换肤机制的幂等性是有前提的：两档颜色不许撞键**（第四十八改）。
  换肤走的是"旧档 ARGB → 新档 ARGB"查表翻译，`ThemeApplicator` 的注释一开始就把幂等当成天上掉的性质
  （"翻完之后控件身上是新档的颜色，而表的键是旧档的颜色 ⇒ 再翻一遍什么都不会发生"）。
  这句只在<b>两档颜色集合互不相交</b>时成立。本轮现场撞上一枚：浅色档正文原本取 (28,28,30)，
  而它正是黑夜档的 `WindowBackground`——于是翻第二遍时已经翻好的正文色被当成"旧档窗口底"再翻成
  (243,243,245)，白底上的近白字，整段文字在屏上消失。而"翻第二遍"在产品里<b>每次都走</b>：
  设置窗口开着换肤时主窗口的 `ApplyEverywhere` 翻一遍、对话框自己的订阅再翻一遍、外观那一块还有第三遍。
  修在调色板那头（正文改成 (26,26,28)），翻译层一个字没改。
  教训是<b>凡注释里写"所以再调一次不会怎样"的地方，那个"所以"都是一条待验的前提</b>：
  判据 `guard/翻译表的目标色不许自己又是旧档的键` 直接查产品自己造的那张表（两个方向各一张、
  逐枚点名 a→b→c 三连），尺子先自证（手工造一张撞键表必须被点名、两档同值的合同色不许被误报）再上产品。
  用一枚 Label 跑一趟只能量到"面板底+正文色"这一对，调色板十九枚里任何一对撞键都要能被抓出来，
  所以这一格查表而不是查控件。
- **进程级静态状态要么不进判据，要么每格自己还回去**（第四十八改）。
  换肤这件事天生是进程级静态的（`Theme._current`、`ThemeController.Mode`、`SystemTheme.Probe`），
  而电池一趟要跑三百格，其中几百格按深色底数像素。若某一格把配色留在白天，后面全红，
  而红的原因看起来像产品坏了——那是工装最会骗人的一种失效。所以这一组每格都在沙箱里跑：
  偏好写临时目录（绝不碰用户真的 `%APPDATA%`）、系统读数用注入的假探针（绝不碰真注册表）、
  `finally` 里把探针与档位原样还回去（判据自己抛异常时若不还，污染会顺着整趟电池传下去）。
  另一半纪律在产品那头：`ThemeController.Load()` <b>只在 `Program.cs` 里调</b>，主窗口构造时不读偏好，
  于是离屏工装永远从黑夜档起步，不受开发者机器上那份偏好文件影响。
- **"读不到"不许静默当成"读到了默认值"：三态必须出声**（第四十八改）。
  跟随系统那一档读注册表，读不到（键不在／值不在／类型不对／权限不够／探针自己抛）返回 `null`。
  若把 `null` 静默当成"系统就是深色"，屏上与"系统本来就是深色"一模一样，用户只会以为跟随坏了。
  所以退回黑夜的同时必须留一句说明，界面原样显示；读到了要把上一轮那句撤掉，否则它一直挂着吓人。
  判据把三种现场并排量（`null` → 黑夜+出声；`true` → 白天+说明撤掉；探针抛 → 黑夜+出声），
  三条一起才证明那句说明不是"永远挂着"也不是"永远没有"。偏好文件那一头同理：
  "文件在但写坏了"必须出声，"文件压根不存在"（首次运行）不需要解释——两种都退回黑夜，
  但只有一种需要说话，把两者混成一句会让用户很快学会无视它。
- **判据要挂在能真按下去的那枚控件上；没有 `PerformClick` 的控件，改属性就是用户那条路**（第四十八改）。
  外观那一块单独做成 `ThemeChooserPanel : Panel` 而不是直接写在对话框里，就是为了让判据能 new 一个出来真点
  （第四十六改已经实测过：从没 `Show()` 的窗体上 `PerformClick` 是空转）。
  两枚档位按钮用 `Click` 而不是 `CheckedChanged` 订阅，理由是跟随档下某一枚可能<b>已经是选中态</b>，
  此时点它 `CheckedChanged` 不发——判据因此量到的是"按钮 → 控制器 → 配色 → 控件树 → 预览条"整条通路。
  `CheckBox` 没有 `PerformClick`，改 `.Checked` <b>就是</b>用户点下去那条通路（走 `CheckedChanged`），
  不必为了"看起来更像点击"去投鼠标消息。
- **自己挑的标准要写明它不是需求书里的**（第四十八改）。
  配色对比度那道 4.5:1（WCAG AA 正文）是本轮自己挑的尺——`产品需求.md` 与 `模拟UI需求.md` 通篇没有
  "对比度／WCAG"字样。挑它是因为"状态色够不够看得清"需要一把能算的尺，而不是一句"看着还行"。
  但既然不是需求条款，就必须写明出处，否则下一轮会有人把它当成需求红线去改实现；
  同理，量不到 4.5 的那一对（黑夜档白字压强调蓝 3.65:1）记成<b>偏差等人判</b>，
  而不是当场把那枚被几百格数着像素的蓝改掉换绿——那是拿"改期望值"冒充"修实现"。
- **`Control.Visible` 报的是"有效可见性"，不是"这一枚自己想不想画"**（第四十七改，构建后红出来的）。
  一枚从没 `Show()` 过的 `Form`，它整棵子树的 `Visible` <b>全是 `false`</b>（父级不可见，子级就"有效不可见"）。
  于是"只量可见叶子控件"那趟枚举到 <b>0 枚</b>，两两无交集、全在客户区内——<b>判据是绿的，量到的却是空集</b>。
  这就是"自证门"存在的理由：几何类判据必须先钉一句"叶子数 ≥ N"，枚举空了要当场红。
  修法是把窗体<b>真 Show 出来</b>（`UiSmokeTests.ShowOffscreen`：`Opacity = 0` + 挪到 (-32000,-32000) + 不进任务栏），
  量完 `HideOffscreen` 收掉。<b>凡"量屏幕上真形状"的判据，都不许拿没 Show 过的窗体当料。</b>
- **离屏量几何要等布局落定，否则量到的是"半路上"的坐标**（第四十七改）。
  第一次 `RectangleToScreen` 会<b>逼出窗口句柄</b>，句柄一出又触发一趟布局（字体这时才真正生效、行高被重算），
  于是屏幕坐标能与落定后的行内坐标差出 <b>2 像素</b>。本批实测：同一行里文本框与按钮的行内坐标是 492/492
  （正好相接、不重叠），屏幕坐标却报成「重叠 2×22」——<b>红在夹具量得太早，读出来却像产品又重叠了</b>。
  修法是在 `Show()` 之后补 `Application.DoEvents(); form.PerformLayout();`。
  **但这一枚要连着下面那条一起读**：修好边距之后，变异探针 P7（删掉这趟 `DoEvents`）<b>没红</b>，
  说明它对这一格已不再承重——它是稳妥做法，不是"已被证明必要的那一下"。
- **判据不许写用户真实的那份配置：产品那头不带路径的出口，就得给它加一枚整进程改道闸**（第四十八改）。
  面板那三枚按钮调的是 `ThemeController.SetMode(mode)`，<b>不带路径</b>；判据在临时目录里造了一份假偏好、
  然后量"写盘了没有"——产品却写了真的 `%APPDATA%\LongStitch\preferences.txt`。
  <b>两头都没错，错在缺一个改道闸。</b>修法是 `AppPreferences.StoreOverride`（null＝用真的那份），
  沙箱里设进去、`finally` 里原样还回去。<b>这一族的判据形状要记住</b>：
  凡"真点一枚按钮"的判据，先问这一下会不会落到开发者机器上的真实文件；
  会的话要么加改道闸，要么就别真点。<b>同一族的另一枚当时还漏着</b>：`RecentProjects` 也会写真 `recent.txt`
  （一格更早的判据经产品保存项目，产品那头调 `RecentProjects.Add` 同样不带路径），删两次、跑一趟就回来一次。
  它<b>不是"临时文件残留"那种小事</b>：按 `RecentProjects` 自己的类注释，那份列表等于一份
  "我在哪些聊天截图上工作过"的清单（需求 §6 才点名要它能清空）——判据把用户真实的工作痕迹
  往他机器上写一遍，与"诊断日志不许含像素"是同一条红线上的同一个方向。
  **第四十九改收口**：给 `RecentProjects` 补一枚同形状的 `StoreOverride`，并把改道<b>从某一组判据的沙箱
  提到工装进程入口</b>（`Checks/Program.Main` 一进来就建 `%TEMP%\LongStitch.Checks-<pid>\` 并把两个出口
  一起指进去，`finally` 里还回 null 并删目录）。提到入口的理由是<b>覆盖面</b>：
  改道写在某一格的沙箱里只有那一格受保护，写在入口处则 `--only`／`--gui`／`--stitch` 任何一条分流都漏不出去。
  判据 `ui/离屏工装的两个存储出口都必须改道到沙箱` 钉路由，
  反证 `guard/改道判据的尺子必须能认出真实那份存储位置` 证明那把尺子不是恒真；
  变异探针 P8（删掉入口那两行改道）当场翻红，<b>并且那一趟探针自己复现了它要防的后果</b>——
  跑完真实目录里出现了 63 字节的 `recent.txt`。
  **量"路由"而不是量"真实那份有没有多一行"**：后者依赖这台机器上恰好有没有那份文件、
  以及开发者本人有没有真在用这个程序，换一台机器结论就变，那是把判据钉在环境上。
  **尺子也不许按"含不含 LongStitch 这个词"判**——沙箱目录名里也有 `LongStitch.Checks-`，
  按词判会把沙箱也算成真实那份，正反两枚一起恒真、判据彻底空转。
- **`FlowLayoutPanel` 的默认 `Margin` 会与显式算出来的列宽"双记账"**（第四十七改）。
  WinForms 控件默认 `Margin` 是四边各 3 像素。若列宽由 `MeasureText` 现量、控件宽度又按
  `面板宽 − 列宽 − gap − 按钮宽 − gap` 反算，那么"默认边距"这一撮必须<b>显式写死成 0 或写进公式</b>，
  否则最宽那一行的账正好差在这几像素上——旧版的重叠就是这么攒出来的。
  本批还踩到它的<b>反面</b>：收尾那趟"把默认边距清零"的名单里带着「选择…」那枚，
  于是算文本框宽度时给它<b>预留</b>的 10 像素左缝被吃掉，实测两者相距 0 像素。
  <b>同一枚边距只许记一次账</b>：要么在构造时显式写死、收尾不再碰，要么交给收尾统一清零、构造时不预留。
- **预乘 alpha 的位图格式里，"清成某枚颜色"存进去的不是那枚 ARGB，而且往返有损、还与路径有关**（第四十八改）。
  F8 读数面板的缓冲区是 `Format32bppPArgb`。`g.Clear(WithAlpha(Theme.PanelBackground, 215))` 之后
  读回的不是 (215,38,38,40)；更坑的是<b>同一枚颜色在 1×1 探针位图上读回 (215,37,37,40)、
  在真面板上读回 (215,36,36,40)</b>——差一档，且这一档取决于那张位图是怎么来的。
  所以判据的口径必须改成<b>两档都量、只比关系</b>（变了／旧档那枚一枚不剩／新档占多数／明度朝浅的方向走／
  半透明 alpha 不变），<b>绝不自己复算预乘</b>。原来那枚"按公式算出期望像素再比"的辅助函数已删——
  它算出来的期望值本身就是错的，那属于"改期望值"的<b>反面陷阱</b>：<b>期望值算错时，红的是判据不是产品</b>，
  分辨办法是拿两条不同的路径量同一件事（探针位图 vs 真面板），两者不一致就说明公式这条路不能用。
- **变异探针"没红"也是读数，要如实写成"判据抓不到"**（第四十八改，P7）。
  七枚探针里六枚翻红，P7「离屏显示后不等布局落定」<b>没红</b>（`ui` 仍 48／0）。
  这不是可以省略的一行——它说明那处防护<b>当前没有判据能证明它必要</b>。
  两种处理都合法：要么补一枚真能红的判据，要么把它记成"稳妥做法但未被证明承重"。
  <b>不合法的是把"没红"写成"已验"</b>。打探针的机械纪律照旧：备份字节 + sha1 → 改坏 → 构建 → 只跑相关组 →
  还原 → 再核 sha1；本批七个源文件收工时与开工时<b>逐字节相同</b>。
  另注：探针要在 `-c Debug` 下打，因为运行中的程序<b>锁着</b> `bin/Release/.../LongStitch.dll`。

## 三、证明不了什么（诚实清单）

1. **JPEG 不是无损的**。它的承诺范围只有"接缝几何整数精确"。
   界面在格式选择处必须显示"有损格式"，测试判据也不对它做字节比对。
2. **源图本身是 16 位或带 ICC 时，导入必然改变像素值**。
   我们不做色彩管理（那会让同一张图在不同查看器里颜色不同且不可控），
   但会把这件事以"需检查"的形式摊开，而不是假装无损。
3. **匹配算法的正确性没有形式化保证**。它给的是"带置信度的建议 + 明确的原因"，
   低置信度时降级成 `! 需检查`。判据只保证"能分辨 1 像素"和"固定栏不会骗过它"。
4. **GUI 交互未经真机验收**。见 README 的 NOT-RUN 清单与「人工验收十二步」。
   冒烟工装只证明"控件树能构造、布局停靠正确、菜单项可点"，不证明手感与视觉。
   第十四轮把这件事从"没有工具"变成"有工具、有表、仍只有人能签字"：F8 那十二项读数、
   「帮助」里三个诊断出口（复制 / 打开日志目录 / 导出会话）都已落成并有判据
   （`canvas/交互诊断读数：需求四点名的十二项一个都不缺`、
   `ui/帮助菜单里三个诊断出口都在且可点`），但"跟不跟手"不在这台机器上被任何人看过。

   第十三轮起 `--gui` 在真窗口里量；第十四轮按需求五把口径改了：连跑 5 趟、逐趟结清、
   **阈值按趟趟都得过判、报最差那一趟**，另加 GC gen0/gen2、墙钟 vs 进程 CPU vs
   UI 线程真正在画的时长三块归因料。本机实测（17 张真截图、35% 缩放、±10 设备像素短拖动）：

     所以这一档能写的结论只有一句：**两档都不是每批必过**（开着时红得更频繁，开 5 批 3 红 vs 关 5 批 1 红），

     本机真出现过这一档：130.8ms（短拖动开着读数层）、85.4ms 与 78.7ms（长拖动开着读数层），

     报告写成"这台机器上偶发超标、归因到回收与取数"，**不写成"代码稳定流畅"**。

     同一 build 同一形状（短拖动 5 趟）跑三个组合 ⇒ 关+关 均 18.4ms、关+开（产品默认态） 均 22.2ms、

     同量级（两个口径互为对照）。结论：开读数层的钱确实全在读数层那一段，而色块层属默认产品态、
     不记在需求三这笔账上；面板贴图从"带尺寸的 DrawImage"换成不缩放贴图**没量到降幅**，
     只按"去掉一笔确定的浪费"记账，不当性能优化卖。
     **末批把这一段拆到能指出出处，红了的那条阈值也跟着好了**：控件里给读数层那一段加了四笔独立计时
     （几何换算／拼那 14 行文本／描边／贴图），面板重建再拆成"分配新缓冲区"与"复用同一张"两条路，
     `--gui` 每趟打成一行「读数层拆账」。短拖动读到的拆账：换算 0.10、拼文本 0.15、贴图 0.08ms/帧，
     面板重画 3.3ms/次（10Hz 上限，摊到帧约 1.3ms），**而描边 7.2ms/帧——整段 7.9ms 里占八成多**。
     出处是画布边界那一笔虚线：那个矩形在设备坐标里有上万像素高（成品 41532 行、35% 缩放也是 14537 像素），
     而屏上只看得到一屏；**虚线的相位沿整条路径量**，屏幕裁剪不会让 GDI+ 跳过看不见的那几万像素。
     改法是描边先与可见区（外扩半个笔宽）求交再下笔。代价如实记在这里：路径变短之后
     **虚线相位会平移**（那条灰虚线框还是那条框，格子错开几像素），屏上看不出"裁与不裁"，
     所以这件事由计数钉住——`canvas/超出屏幕那几笔描边必须先裁到可见区 裁过才算数`，反证
     `guard/描边若不裁到可见区则虚线路径代价翻红`（内存里两种画法各画 10 次：整条 30000 高 24.8ms
     vs 裁到可见区 0.8ms＝**30.9 倍**，判的是比值不是绝对毫秒，换机器不赖皮）。
     **改后重跑三批，每批仍按需求五连跑 5 趟**：开+长拖动（`--moves 400`）97 帧 均 22.5 /
     P95 **29.4** / 最慢 44.2ms ⇒ **十条阈值全过**，读数层自己 均 2.2ms（改前同一形状是 7.8–8.8ms）；
     开+短拖动 25 帧 均 23.8 / P95 **28.6**ms ⇒ `P95 ≤ 33ms` 过了，但那批仍冒出一帧 **51.6ms**
     ⇒ `单帧 ≤ 50ms` 红（那一帧里读数层只占 8.3ms、画布部分 43.2ms）；
     关+短拖动 25 帧 均 22.1 / P95 27.5 / 最慢 31.1ms ⇒ **九条全过**。
     定稿前在最终构建上复量一批（85 帧合并 均 21.5 / P95 **28.9** / 最慢 30.6ms，读数层自己
     均 2.3ms）⇒ 十条阈值全过，与上面两批同一量级。
     ⇒ 需求三那句"打开 HUD 时 P95 仍可能超过 33ms"这一改之后**在这台机器上不再复现**；
     **但单帧偶发没消掉**（60.6 / 73.8 / 51.6ms 分别出在改前改后，归因仍是画布取数与回收／抢占），
     也不许把"这一档过了"写成"长期稳定性已验收"。
     同一批读数里再记一条**改了、也量到了、但只值零点几毫秒**的：面板位图以前每次重画都释放旧的
     再新分配一张（量到 608×230 = 559,424 字节一张，已过 85KB 大对象门槛，10Hz 等于每秒往大对象堆
     扔几 MB）；现在尺寸没跨档就**复用同一张缓冲区**（宽度按 32px 分档，否则数字位数一抖就白分配一次）。
     两条路的实测单价：**分配那一次 4.0ms、复用那一次均 3.3ms ⇒ 一次只省 0.6ms**，而且一趟短拖动里
     只有第一帧要走分配 ⇒ 摊到帧上不到 0.03ms，**它不是上面那 5.7ms/帧的出处**。
     留着它的理由只有两条：去掉一笔确定的大对象投放，以及让"复用"与"每次分配"这两种形状在计数上分得开
     （`canvas/面板重画复用同一张缓冲区 重建多次但分配只涨必要那几次` ＋
     `guard/面板分配计数分得清复用与每次重建都分配`）。
     最后一批又拿 `--no-compare` 各跑了一趟（同 build：关+开 合并 25 帧 均 20.3 / P95 26.7ms，
     关+关 合并 29 帧 均 17.6 / P95 24.7ms ⇒ 色块层这批值 **2.7ms/帧**，与上一批的 3.8ms/帧 同量级）。
     这一层也补了两笔计时（`--gui` 新增一行「对比层拆账」）：两张图的设备矩形描边 **0.13ms/帧**、
     重叠带填充＋描边 **0.50ms/帧** ⇒ 两笔只占那 2.7ms 的四分之一，**剩下约 2ms 计时器读不到**
     （软件渲染下 GDI+ 延迟提交：调用只排队，钱在很多笔之后一次付掉，单笔前后夹表量不出）。
     这句按"没量满"写，不把那 2ms 派给某一笔。反过来它给了读数层那一改一个机制证据：
     **同样几万像素高的矩形，实线 0.13ms/帧、虚线 7.2ms/帧** ⇒ 贵的不是矩形尺寸也不是调用条数，
     而是虚线要沿整条路径排相位。所以这一层**不照抄**裁可见区那个修法（它没虚线、填充的带又本来
     就贴着视口）——同样的形状不等于同样的病因，这条判断本身就是量出来的。
     仍然没测的：换机器、把带一路拖到 0（整张画布重排）、比 400 次更长的连续操作、
     几十分钟不间断地用（本轮把趟数与形状都对齐了需求五那句"连续运行 5 次"，再往上就没人量过）。
     **"换缩放档"这一条本轮动了一半**：真窗口在 150% 那一档被 AI 走查过一遍（见下面第 7 条），
     量到的是一处显示缺陷而不是帧率数——那一档的 P95 只有面板上几枚读数，没有 5 趟口径的样本池。
     **顺带记一条口径边界（不改代码，只记账）**：`--gui` 跑在 Checks 进程里，那个进程没声明 DPI 感知
     ⇒ 它量的是 **96 DPI 那一档窗口**；产品进程声明了 `PerMonitorV2` ⇒ 用户 150% 屏上的窗口要画 2.25 倍像素。
     两边都开着读数层各看过一眼：`--gui` 那批 HUD 自己 2.2ms/帧、整帧 P95 28.6–29.4ms；
     真窗口 150% 那一趟面板读到 HUD 单独 均 3.7 / P95 9.1ms、整帧 P95 65.4ms、分阶段贴图 19–27ms。
     ⇒ 上面那批阈值数字描述的是 96 DPI 那一档，**不许当成 150% 屏上的手感承诺**；
     阈值一条也没因此放宽，让 Checks 进程也声明 DPI 感知没做（那会牵动一批按设备像素写死的格子）。
     **第五十五改⑥ 起这条记账换了前提（偏差账）**：产品进程的 `HighDpiMode` 已从 `PerMonitorV2`
     改成 `SystemAware`（用户图6/图7——PerMonitorV2 下把窗口在 2K 150% 与 1080P 100% 两台屏之间拖，
     文字忽特小忽特大，是 WinForms PerMonitorV2 对 GDI 自绘的重缩放通知支持残缺；用户图6/图7 的
     两张截图就是这个形状）。SystemAware 的口径：进程始终按**系统主屏**的 DPI 渲染一次，移到别的屏
     由 DWM 整窗位图拉伸——**"150% 屏上要画 2.25 倍像素"这句承诺在跨屏场景下不再成立**：只有当
     系统主屏就是那块 150% 屏时它才成立；窗口移到别档的屏后由 DWM 拉伸，像素数不重算。
     单屏（窗口待在主屏上）的 DPI 档位与 2.25 倍像素账**原样成立**。上面那些阈值数字的口径不变：
     Checks 进程仍是 96 DPI 那一档，产品单屏手感仍不能拿它们当承诺；变的是"跨屏移动"这一档
     ——PerMonitorV2 想做到每屏各画各的，实测反而崩出两档文字大小，SystemAware 用整窗拉伸
     换确定性。这条偏差没有判据可钉（跨屏复现需要两台不同 DPI 显示器，单机无法模拟），
     如实记为只有眼判能签的缺口。
6. ~~**"固定前一段/后一段"在屏幕上谁在动，没有完全兑现**（第十二轮）~~ → **第十三轮补上了显示补偿、
   第十四轮补上了撤销回滚**。原话那段几何事实仍然成立：本项目的落位永远把内容左上角归到 (0,0)

   "会不会像画面自己跳了一步"仍然是判断题，没人签。
7. **需求四那十二步已由 AI 在真窗口走查一遍，并因此抓到一处真缺陷**（第十四轮末批）。
   做法与边界：起真实 `LongStitch.exe`（17 张真截图当参数），Computer Use 注入真鼠标消息与按键，
   逐步截图看屏，同时让诊断日志做第二份证据（`seam.*.commit` / `canvas.pan.*` 里带着每一步的
   rect1/rect2/overlapRect/cutY/alignmentOffset/viewportBefore/viewportAfter）。
   抓到什么：**F8 读数面板只画得出 14 行里的后 4 行以外的前 10 行**——帧耗时、HUD 单独耗时、
   分阶段、Paint 计数那四行整行不见了，而需求四点名的"当前帧耗时""P95 帧耗时"正在被切掉那几行里。
   病因不在"字太大"也不在"行太多"，在**面板长宽按"行数 × 写死的 16 像素"算，而位图里的字按进程 DPI 排**：
   产品声明 `PerMonitorV2`（这台机器 150%），行距越过 16 之后框就比字短，出界那几行被 GDI 裁掉。
   **为什么 186 格全绿还留着它**：Checks 进程没声明 DPI 感知，它跑在 96 DPI，那里量到的行距只有 14，
   那个 16 反而宽裕 ⇒ 这一族判据在那台电池上**恒真**。修法是把行距也改成量出来的真实占位
   （`canvas/F8 面板的背景框必须装得下它自己那些读数`），反证是
   `guard/面板行高若退回写死的 16 像素则在高分屏下切掉最后几行`——它同时把"96 DPI 下旧写法并不出错"
   写成一条断言钉住，因为**"电池绿"与"屏上对"之间的这道缝本身就是这一格要守的东西**。
   改完在同一台机器同一个真窗口重看：14 行全在框里。
   还顺手核对了两件事：① 「复制诊断信息」在真窗口点通了，落到剪贴板那份**不含路径、不含像素**；
   ② 撤销那四条等式在真窗口成立（修订 26 的几何与修订 22 逐字相同，剪贴板那份里
   `Viewport.TopLeft=(0,137)` 正是那次拖动的 `viewportBefore`）。

   手感与观感那两栏仍然空着（见下面三档表）。截图里那两枚角标"像被截成半句话"这一处**已经量掉**：

   ⑤ 本轮新踩到两条工装陷阱，同属"自证其实没自证"那一族，记在这里免得下一轮再交一遍学费：
     **取数脚本的正则必须锚到自己那一行**——`P50 x P95 y 最慢 z` 这种不带行锚的写法会从**上一行**

   ⑦ 需求五那句"记录 GC 和<b>进程调度信息</b>"里的调度这一半，本轮从推算变成了实量。
     过去出口只有一句推论（"墙钟减进程 CPU 差出去的那截就是被抢占的"），而那个差里混着后台解码线程，
     <b>分不清是"谁"在等</b>。现在诊断出口多一行「线程与调度」：线程条数（此刻几条在等）·
     全部线程 CPU 求和 · 最忙那条单条 · 那一刻状态与等待原因；`--gui` 每趟另给这几笔的<b>本趟增量</b>。
     实量到的形状（`--gui test out --moves 100 --runs 2 --hud`，17 张真截图）：
     第一趟 墙钟 250ms／求和 438ms／最忙那条 172ms／拖动帧合计 107ms ⇒ <b>求和大于墙钟是后台在并行</b>
     （它与工装那行「进程 CPU 所有线程合计」一字不差，两份互相作证），
     而"最忙那条"比墙钟少的那 78ms 才是 UI 线程<b>在等</b>的时间——这句话过去只能猜，现在能读。
     两笔不许互相顶替：求和会跟着任何一条线程烧 CPU 而动（判据钉它），
     "最忙那条"才是拖动归因（它在两次取读数之间可能换成另一条线程 ⇒ 只作读数、<b>不进任何阈值</b>）。
     平台边界要写清：.NET 8 的 `ProcessThread` 在 Windows 上给 用户／内核／总 CPU 时间与状态、等待原因，
     <b>不给</b> `ContextSwitchCount`（.NET Framework 的 Windows-only 成员，没移植过来），
     要它只能装性能计数器包——本项目零 NuGet 依赖，所以出口把那一笔<b>明写成"按未量记"</b>，
     判据 `canvas/交互诊断读数里需求五点名的进程调度那一笔必须从操作系统读来` 里专门有一条判"不许出现 0 次"
     （恒为 0 的字段与"这趟真的没发生"在屏上长得一模一样）。反证是
     `guard/调度读数若写成固定值则空转攒够十五毫秒再取第二次它也不涨`，
     <b>它第一版红过，红出来的是判据选错了钉子</b>：钉的是"最忙那条"，
     而空转的这条线程本来排不上第一 ⇒ 永远不涨。那一次红是对的——它拒绝了一条照不出退化的判据。
     <b>同一格后来又红过一次，那次红在判据自己的窗口上</b>：空转写死 40ms，而那 40ms 整机被别的进程占满、
     这条线程 0ms CPU 都没攒到（复跑两遍全绿）⇒ 固定时间窗会把环境偶发写成"产品坏了"。
     现在改成"攒到 15ms 才停、最多等 400ms"（阈值没降），并加了一条<b>出口必须跟得上独立证人（差 ≤5ms）</b>
     ——只要求最低增幅时，一份每 100ms 才刷新一次的缓存值也能蒙过去。

  ⑧ **滚轮与缩放这两档手势本轮从"仍未量"变成"量到了"，并且量出一条真红**。
     测法：`--gui test --wheel 20 --zoom 8 --runs 5`（`checks/LongStitch.Checks/GuiGestureHarness.cs`），
     每趟先 `ClearTileCacheForTest()` 从<b>冷缓存</b>起量——本机瓦片缓存装得下整张画布（168 块 × 约 1MB，

     两档走的通路不同，口径必须分开写：滚轮是真把 `WM_MOUSEWHEEL` 投进那个 HWND；
     缩放只能直接调产品公开入口 `ApplyWheel(120, Keys.Control, device)`——`PostMessage` 改不动
     `ModifierKeys` 的键态，而合成 Ctrl 要往系统注入真按键，那会打到用户此刻在用的别的程序上。
     **所以缩放这一档不许写成"真按键滚轮已验证"**，它证的是"控件在上屏的真窗口里、重画真过了消息泵"。
     **未限流时量到的红**：冷缓存滚轮那一帧 **55.6ms**（取数 30.5 ＋ 贴图 20.1），顶破 `单帧 ≤ 50ms`；
     那一帧没有回收标记、也不是被抢占（同帧内最忙那条线程的 CPU 与墙钟一起涨）——是真在算，
     于是按铁律改实现：每帧画瓦片按<b>冷活</b>预算限流（默认 12ms/帧；冷活＝现取渲染 ＋ 首次
     `RgbaImage → GDI 位图` 转换），超预算就停手，欠下的块这一帧画成棋盘格、当场再要一帧。
     判据 `canvas/滚轮那一档一帧画不完的瓦片必须欠帧、追一帧、欠的那块画成棋盘格`、
     `canvas/瓦片限流连着画满的那一帧与不限流那一帧逐字节相同`（这条是红线保命绳：限流只许改节奏不许改像素），
     反证 `guard/瓦片预算写得比一整屏还大时不许出现欠帧`。
     **这一版差点死在自己的第一版上，形状值得记进红线**：第一版把"每帧必做的贴图"也算进预算，
     于是全命中的稳定帧每帧都"超预算" ⇒ 每帧 `Invalidate()` ⇒ `Application.DoEvents()` 的队列永远排不空
     ⇒ 工装整趟挂死七分钟。凡"这一帧做不完就推给下一帧"的实现，<b>必须给"下一帧"配一个必然收敛的条件</b>
     （这里加的是"这一帧确实做过冷活才许停"），并且工装要有超时兜着，别把挂死当成"跑得慢"。
     **限流之后、改重采样档之前**（同一批、逐趟判、报最差那一趟）：滚轮 5 趟逐趟最慢 **25.2 / 25.1 / 29.9 / 23.0 / 23.4ms**、
     合并 30 帧 **P95 27.3ms**，每趟追加要帧 2~4 次、最后一帧欠 0 块；
     缩放 5 趟逐趟最慢 **22.8 / 21.2 / 26.9 / 24.1 / 22.5ms**、池 **P95 26.9ms**；
     开着读数层重跑：滚轮池 P95 24.9 / 26.4 / 28.8ms、缩放池 P95 31.4ms，面板重建都在 10Hz 预算内
     （需求三那两档不许并成一个数）。
     **同一批里还红着的**：HUD 开启档的拖动第 2 趟一帧 **53.2ms**，`单帧 ≤ 50ms` 与池 `P95 ≤ 33ms` 各红一条；
     归因就写在该趟读数里——那一帧带回收标记、本趟 gen0 2／gen2 2，贴图段 40.6ms 里读数层只占 4.9ms，
     所以它是"整屏重画撞上两次 gen2 回收"，不是"读数层贵"。阈值一条没动，红继续记着。
     **第二改：滚轮途中的帧改走便宜重采样档、停手只补一帧高质量**（限流管住"取数"那一段，
     这一段管的是"贴图"那一段）。原来只有三种拖拽算"正在动"，滚轮期间每帧都按静止给最贵的
     `HighQualityBilinear`；判据 `canvas/滚轮途中走便宜插值、停手后只补一帧高质量`、

## 四、给改代码的人的检查清单

- [ ] 新接口有没有把 `int` 换成 `double`？有 → 停下来想清楚它会不会参与几何。
- [ ] 新渲染路径有没有复用显示层的缩放结果？有 → 违规。
- [ ] 改了分块逻辑？跑 `--only export`，确认"分块=整块"仍然绿。
- [ ] 加了新判据？在 `guard` 里补一格变异注入，否则那条判据可能是空的。
      第十四轮新增的四格各有反证：读数层那三格计数判据共用
      `guard/读数层若退回每帧排文本与重建位图则堆分配立刻翻红`，隐私那两句"不包含"配
      `guard/隐私判据的探针：读数混进路径就必须被认出来`，撤销带回视口配
      `guard/撤销若只换文档不带显示快照则视口停在补偿位置`；面板贴图必须 1:1 那格配
      `guard/面板贴图计数分得清不缩放与重采样两种贴法`（它用一条只走旧写法的测试通路证明
      那个计数分得清两种贴法，否则 canvas 那一格量的可能只是帧数）。      末批又加两格反证：面板复用缓冲区那格配
      `guard/面板分配计数分得清复用与每次重建都分配`（走一条产品不经过的"每次都分配"出口，
      要求分配计数跟着涨，否则"复用那格读到 0"只是计数没接上）；描边裁到可见区那格配
      `guard/描边若不裁到可见区则虚线路径代价翻红`（内存里同一条虚线笔两种画法各画 10 次，
      判的是**比值**：整条 30000 高 vs 裁到可见区，实测 30.9 倍，换机器不赖皮）。
      这两格与前面几格同一条纪律：**屏上看不出区别的性能缺陷只能靠计数钉**，
      而计数自己必须有一格证明它分得清两种写法，否则那就是一个恒绿的数。
      新格子的名字要避开 `，、）`——文档里的引用会被这三个字符截断，写进去就对不上注册行。
- [ ] **新建了电池文件**？必须把它加进 `checks/doc_cell_check.py` 顶部那个 `reg` 文件列表。
      漏了不会报错，只会让那一整份文件的格子**不进注册表**：文档引用全被判成查无出处，
      而源码注释里 `<c>…</c>` 也静默不参与校验（第十四轮起列表里已含 `HudCostTests.cs` 与
      `SessionDiagnosticsTests.cs`；`注册格子数` 那行要和电池末尾的总数一致，不一致就是漏登记）。
- [ ] 改了判据的名字或数量？跑 `python checks/doc_cell_check.py`：
      它把三份文档里 `组/格子名` 形式的引用、以及 `src/**/*.cs` 注释里 `<c>组/格子名</c>` 形式的引用，
      与 `Battery.Add` 的注册逐字对账，名字改了而文档没跟上，文档就会开始指认一个不存在的判据（比没写更坏）。
      代码注释必须用 `<c>…</c>` 包住名字：散文式写"判据 组/格子名 把它抓了出来"这种形式，
      机器分不清名字到哪里结束、只能整段吞掉，于是必然报"找不到"——第八轮就是这样揪出四处（其中一处还是个不存在的名）。
      第十四轮起它会**返回非 0 退出码**（一个不会红的门禁等于没门禁）。
      散文里写 `guard/*` 那种"整组"的通配引用现在会被核对：该组必须真有已注册的格子，
      组名打错（例如 `gurad/*`）照样报 MISSING——以前这两行是当"已知噪声"放过的，
      放过的代价是组名写错也没人管。
      它同时打印当前注册总数，README 里那个"多少格"以它为准。
- [ ] 声称"某条需求已经做了"？先跑 `python checks/round14_audit.py`：
      它把第十四轮那六条要求逐条指回真实文件里的字面（70 行必须逐字找到、3 行反证必须找不到，
      任一不符就非 0 退出）。这一格是现场撞出来的：按需求原文 grep `CutYBefore` /
      `Viewport.TopLeftBefore` 全是 0 命中，而需求一.1 那五个量一个都不缺——代码里它们叫
      `CutBefore` / `ViewportBefore`（对应关系就写在 `HistoryDisplayState` 的注释里）。
      **搜索词与被搜文件的真实字面不一致时，"已做"会被读成"没做"，反过来"没做"也会被读成"已做"**；
      以后新增需求条目请在这个脚本里加一行，别拿一次性 grep 当结论。
- [ ] 失败消息有没有写清"量的是什么、期望什么、实际什么"？
      只写"断言失败"的判据，下一轮没人敢信。
