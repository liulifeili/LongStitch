# 长截图重叠匹配算法

代码在 `src/LongStitch.Core/Matching/OverlapMatcher.cs`，
配套的行签名在 `Imaging/ImageSignature.cs`，固定带检测在 `Imaging/FixedRegionAnalyzer.cs`。

## 问题设定

给相邻两张截图 `before`、`after`，求一个**整数位移** `Offset = (dx, dy)`，
使 `after` 放在画布上该位置时，与 `before` 重叠的部分内容一致、且不重复也不吃掉唯一内容。

滚动截图是**纯平移**，没有旋转缩放，所以不需要特征点（ORB/SIFT 一类）。
特征点在这种场景下更慢，而且在重复列表项上更容易误配。

## 为什么不能直接拿像素比

1170×2532 的一对图，候选重叠位置约 2000 个，每个最多比 2500 行 × 1170 列 × 3 通道
≈ 170 亿次比较。暴力全分辨率搜索在普通桌面上要跑几十秒，
"导入 20 张后画布仍可响应"就无从谈起。

所以走**粗到细**：先用行签名把每行压成几十个数，粗搜定位到几像素内，再对少数候选做全分辨率精修。

## 五个阶段

### 1. 排除固定 UI 带（最关键的一步）

`FixedRegionAnalyzer.Detect(before, after)` 逐行比较两图**同一位置**是否几乎相同，
找出顶部与底部的"公共横带"。这些带在打分时**完全不参与**。

不做这一步会怎样：两张图的状态栏几乎逐像素相同。搜索会发现"把后一张整体上移 0 行、
状态栏对状态栏"是个得分极高的解，于是判定重叠 = 整张图高度 → **后一张被整张吃掉**。
这是长截图拼接工具最经典的一类错误。

判据：`match/固定栏陷阱不得判成整张重叠`。

保守性体现在两处：
- 宽度不同的两图直接不判固定带（逐行比较没有意义）；
- 带高上限 `min(340, 图高/3)`，且匹配行数太少就不认为有固定带——
  **宁可不排除，也不许把正文悄悄排除掉**。

### 2. 行签名

每行按列分成 `Bins`（默认 48）个块，每块存两个 0–255 的整数：

- **亮度均值**：`(r*77 + g*150 + b*28) >> 8`，Rec.601 的定点近似；
- **水平梯度均值**：相邻像素亮度差的绝对值平均。

只用亮度会在"整片纯色聊天背景"上产生大量并列候选；加上梯度后，文字行与空白行立刻分得开。
距离就是绝对差之和（SAD），全程整数，没有浮点、没有开方。

### 3. 粗搜：相似度曲线

对每个候选重叠行数 `d`，把"前图末尾 `d` 行"与"后图开头 `d` 行"按行配对，
等间隔抽样（默认最多 128 行）求平均归一化距离。采样行数不足 4 行的候选**直接不给分**，
而不是给个 0 —— 给 0 会让它在比较中"看起来完美"。

从曲线里取局部极小作为峰，峰间距至少 `PeakSeparation`（默认 12 行），
否则一个宽谷会被切成一堆"伪候选"，把"存在多个候选"这个信号刷得满屏都是。

### 4. 精修：全分辨率像素 SAD

只对最佳峰，在 `±RefineDy`（4）× `±RefineDx`（6）的小窗口里用真实像素比。
横向有位移时，可比对的列区间会同步收窄——不收窄就是在比不同的列。

窗口只开这么小的原因：粗搜已经把位置定在几像素内；窗口一大，
重复纹理就能找到"另一个同样好的位置"，反而把唯一正确解冲淡。

### 5. 结论与原因

三个量一起决定状态，任何单独一个都不够：

| 条件（按顺序判定） | 结果 |
| --- | --- |
| 重叠 < `MinOverlap`(24) | `! 需检查` · 重叠太短 |
| 相似度 < `PassSimilarity`(0.970) | `! 需检查` · 对齐后仍有明显差异 |
| 与次佳峰差 < `AmbiguityMargin`(0.004) | `! 需检查` · 存在多个候选 |
| 以上都不成立 | `✓ 自动匹配` |

界面显示的是**结构化原因 + 一句人话**（`Seam.CauseText`），
例如"重复内容有多个候选（最佳 99.2%，次佳 99.0%，相差不足 0.4%）：多为纯色区或重复列表项，请人工确认"。

**设计立场**：纯色区、重复列表项、动态内容确实会产生多解。我们不假装能自动消歧，
而是明确降级成"需检查"把决定权交回用户——这对应需求 §2.2「自动结果可见且可质疑」。

## 阈值标定：真图第一轮已跑（自监督，不需要人工标注）

原本要"30–50 组人工标注正确位移的真图"。用户给不了标注，所以换了办法：
**把一张真图按已知位移切成两屏**，正确答案由构造决定，于是能在真实像素
（真实中文字形、抗锯齿、照片区、重复列表项）上量出误差分布。

```powershell
dotnet run --project checks/LongStitch.Checks -- --probe     samples/local
dotnet run --project checks/LongStitch.Checks -- --calibrate samples/local
```

### 第一轮结果（6 张 iPhone 截图 × 5 对 = 30 对）

| 指标 | 数值 |
| --- | --- |
| 完全命中（0px 误差） | 27 / 30 = 90.0% |
| 误差 ≤1 像素 | 27 / 30 = 90.0% |
| 误差 ≤3 像素 | 27 / 30 = 90.0% |
| 明显错位 | 3 / 30 = 10.0%（全部来自 IMG_8153，误差恰好 4px） |
| 单对耗时 | Release 下 32–113 ms（IMG_8150 那张 16 位图 65–113 ms，其余 5 张 32–47 ms） |

### 这一轮最重要的发现：绝对拟合度**没有**区分力

第一版扫描 `PassSimilarity` 从 0.90 一直到 0.999，**结果一格不变**——
30 个样本（含 3 个错 4 行的）全部报"强度 100.00%"。
也就是说：只用拟合度当阈值，`✓ / !` 就是装饰。

原因很清楚：拟合度回答"贴得好不好"，不回答"**是不是只有这一个地方贴得好**"。
差 4 行在重复结构上照样贴得严丝合缝。

于是加了 **`Uniqueness`（唯一性）** = 最佳解与"精修窗口内相距 ≥2px 的最近对手"的归一化差距，
并与粗搜层面的次佳峰差距取小者。自动放行要求拟合度**和**唯一性同时达标。

### 唯一性门限扫描（拟合度固定 0.97）

| 门限 | 自动放行 | 其中 ≤1px | 精确率 | 覆盖率 |
| --- | --- | --- | --- | --- |
| 0（不设门限） | 30 | 27 | 90.0% | 100% |
| 0.00002 | 27 | 27 | **100.0%** | **100%** |
| 0.0005 ← 当前默认 | 27 | 27 | 100.0% | 100% |
| 0.001 | 27 | 27 | 100.0% | 100% |
| 0.002 | 25 | 25 | 100.0% | 92.6% |
| 0.005 | 22 | 22 | 100.0% | 81.5% |

0.00002 到 0.001 之间是一段**精确率与覆盖率同时满分**的平台。
默认取 0.0005：落在平台中段，两侧各有约 4–25 倍余量，比贴着边缘更抗噪。
**这个默认值是真图量出来的，不是猜的。**

### 顺带被真图抓出来的一个严重缺陷

第一次标定跑出"0% 命中、所有样本判定重叠都等于整张高度"。根因不在算法，
而在 `RgbaImage.Blit` 的越界求解漏了一个区间——只约束了"在本图内"和"在源图内"，
没约束"在**请求矩形**内"。于是"从大源图取一小块贴到目标左上角"会一路拷到目标底部，
把整张目标覆盖掉。

现有测试躲过它，是因为那些用例的 `srcRect` 都比源图大，另一条约束先收紧了。
已补常驻判据 `blit/拷贝不许越过源矩形`（三种落点，逐一断言矩形外仍是标记色）。

## 第二轮：真机连拍（17 张微信聊天截图，`--stitch`）

自监督标定量的是"算法上限"。第二轮用的是**真机连拍**：同一聊天页连续滚动的 17 张
1179×2556 截图（`test/`，含私密内容，已 gitignore），走产品同一条链路
（解码 → 项目 → 布局 → 匹配 → 清理 → 导出），**没有人标注过正确答案**。

没有标准答案时，"完美"落在四条互相独立、都能机器核对的性质上
（实现：`checks/LongStitch.Checks/StitchRealRun.cs`）：

| 判据 | 在量什么 | 实测 |
| --- | --- | --- |
| 1 重叠区自洽 | 按布局对齐后，**随滚动而变的行**结构差异必须为 0 | 16 条缝全部 0 行残差 |
| 2 一像素判别力 | 位移改成 dy±1，被破坏的内容像素必须显著变多 | dy 破坏 0%，dy±1 破坏 3.5%–8.5% |
| 3 行数守恒 | 画布高 = 各图高之和 − 各重叠之和 | 43452 − 15043 = 28409，实为 28409 |
| 4 内容守恒 | 每张图"只属于自己"的行在成品里逐字节出现 | 清理后 21931 行全部逐字节一致 |

外加导出核对：成品 PNG 读回的 IHDR 尺寸与三条抽样带哈希，与离屏渲染一致。

### 这一轮量出来的两个新事实

**① 真机截图的像素并不自洽。** 同一张图里背景左半 233、中段 237；相邻两张在同一坐标
还会再差 1–4 级（有损中间产物留下的低幅噪声）。所以"逐字节相同"在这种数据上永远红，
红了也说明不了拼缝错。判据改成**结构差异**：单像素最大通道偏差 > 12 才计数。
噪声实测全部落在 ≤12 级，而错位 1 行会产生几十到上百级的偏差——两者差一个量级，
门限放中间任何位置结论都一样（分布会打印出来供复核）。

**② 固定带检测器有个真缺陷。** 旧实现拿"每张 vs 第一张"比逐行平均差：状态栏时钟跨分钟时，
后半程截图在时钟那**连续二十多行**上全体不同意，同意率掉到 50%，"连续 4 行不匹配即停"
把 311 行的固定顶栏量成 75 行——少掉的 236 行在成品中间重复了 16 次，
还顺带盖掉每条缝 236 行真内容。改成**比相邻对**（时钟几乎只在跨分钟那一对里变）
+ 结构差异度量后，顶带 310/底带 261 与独立测量逐行对账一致。
当时的常驻判据是 cleanup 组那格「状态栏时钟块不许截断固定带检测」
（夹具里复刻了旧规则并证明旧规则在这组数据上量出 24 行、真值 50 行）。

本文件讲的**匹配侧**固定带降权（`FixedRegionAnalyzer`）不受影响，仍由
`match/固定栏陷阱不得判成整张重叠` 守着。上面那段读数是删除前量下来的，留着是为了说明
"逐行平均差"在这种数据上没有判别力——那条教训与今天仍然用结构差异的匹配同源。】

### 第三层核对：工程外的独立验证器

四条判据 + GDI+ 交叉核对都跑在同一个 C# 工程里，防不住"布局、裁边、导出三处
一起错成同一个样子"。所以补了一个**纯 Python 标准库**验证器
（`checks/verify_strip_independent.py`，zlib + 手写 PNG 反滤波，与工程零共享代码）：
它自己解 17 张源图与成品，自己找每对的滚动位移（粗扫 + 细扫 + ±4 行唯一性 + 窗口生长到
残差 0 的总长 ≥100 行才算数），自己推画布布局，再对成品逐带断言（每段开头 60 行、
每条缝上侧 60 行、末尾 60 行）。

实测结果：**16 个位移与 C# 工程逐个相同**（1615/1593/1653/1577/1646/1459/1598/1467/
1635/1796/1616/1844/1607/1507/1593/1647），独立推得的成品高度 27838 与实际一致，
34 带 × 60 行 × 1179 列比对 **0 带不一致**，退出码 0。

其中最窄的一条缝（IMG_8049→8050，d=1844）值得记一笔：两张之间页面内容变过，
互内容被 a 的内容尾行与 b 的头部固定带夹到只剩百余行，150 行的长探针永远探不进去——
40 行短探针定位（残差 0 且 ±4 行均更差）后向上下两侧生长到 ≥100 行残差仍为 0，
才放行这个位移。验证器自己的守卫：把它喂给**未清理**的 `stitched_raw_1.png`
（顶栏/底栏还在成品里）必须拒收——实测在"从成品反标顶带"一步就红（残差 1648 ≠ 0，
退出码 1），16 个位移全对也救不回来，证明成品核对不是空转。

### 仍然测不到什么

一轮连拍只覆盖一个机型、一个 App（微信）。不同 App 的顶栏高度/半透明程度、
不同机型的状态栏、"正在输入"与图片懒加载造成的**真·动态差异**都还没碰到——
那种差异会让重叠区出现局部对不上的块，判据 1 会红并指出行号，但阈值该怎么退让
（降为"需检查"还是容忍局部块）还没有数据支撑。GUI 交互同样未验（见 README 的 NOT-RUN）。

标定脚本：`checks/LongStitch.Checks/RealSamples.cs`（探针/自监督标定，不产出 pass/fail）、
`checks/LongStitch.Checks/StitchRealRun.cs`（真机连拍端到端，产出 pass/fail）、
`checks/verify_strip_independent.py`（工程外独立验证，产出 pass/fail）。
三者都**故意不并入电池**——它们依赖仓库外的真实截图，别人克隆下来跑不了；
混进电池只会让"跳过"看起来像"通过"。
